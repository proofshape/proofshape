## Why this exists

`UploadFrameRequest` (`contracts/openapi.yaml`) requires a `gyro` reading — `alpha`, `beta`,
`gamma`, all three — on *every* uploaded frame; it is not optional the way some capture features
are. On iOS 13+, reading device orientation at all requires an explicit,
`DeviceOrientationEvent.requestPermission()` call gated behind a user gesture — a platform quirk
that does not exist on desktop or Android, so it only surfaces on a real iPhone. If this does not
actually work there, no frame can ever be uploaded on the platform the whole product targets,
which makes it as load-bearing as the camera permission in C-02, not a secondary concern.

## Acceptance criteria

- On a real iPhone, tapping a button on C-01's page calls
  `DeviceOrientationEvent.requestPermission()` directly inside the tap handler; granting it shows
  live `alpha`/`beta`/`gamma` values updating on the page as the phone moves — the same shape
  `uploadFrame` requires.
- On a platform where this explicit request does not exist (desktop, Android), the page detects
  that and skips straight to reading orientation events, rather than getting stuck waiting for a
  permission API that platform never offers.
- Denial on iOS is tested too, and surfaces a specific, visible message rather than silently
  sending a zeroed or missing gyro reading — an `uploadFrame` call built on a fabricated reading
  would misreport the capture pose, and the contract requires the field regardless. What the user
  does next if genuinely denied (retry the prompt, abandon the session) is a real open question
  this story surfaces; it does not have to be solved completely here, but the case cannot be
  silently ignored either.

## Tests

Same reasoning as C-02: a device permission prompt on real hardware is the case `AGENTS.md`
names as genuinely unable to be economically automated. Record a written manual check — device,
iOS version, the steps taken, and the observed behaviour for both grant and deny — alongside
whatever of the platform-detection logic *can* be unit tested without a real device (for
example, that the code takes the "skip the explicit request" branch when
`DeviceOrientationEvent.requestPermission` is undefined, which is a plain feature-detection
check with no hardware dependency).

2026-10-01: Implemented in `capture/src/gyro.ts` (extended, not replaced —
`isOrientationPermissionRequestNeeded`, `describeOrientationError`, `mountGyroCheck`, alongside
C-01's existing `parseGyroInput`), built the same way @TabeenRaoof built C-02 (PR #72): everything
that doesn't need a real device is built and tested; the on-device grant/deny check is left as a
written manual-check template below for whoever has a real iPhone. **Not closing this story in
this PR** — `State` stays `Claimed`, same as C-02.

**Built directly on review lessons from PR #72**, not just read about them — I reviewed that PR
myself and found two real bugs plus a reuse problem; all three have a direct analog here, closed
from the start rather than repeated:
- C-02 called `getUserMedia`, assigned `srcObject`, but never actually started playback (no
  `autoplay`, no `.play()`) — and its test only checked the assignment, not that anything was
  actually happening, so it didn't catch it. The analog here would be requesting permission
  successfully but never attaching the `deviceorientation` listener. This story's tests dispatch a
  synthetic `deviceorientation` event and assert the DOM actually updates — the effect, not just
  the intermediate "granted" state — specifically to close that class of gap
  (`test_a dispatched orientation event updates the displayed values — not just status text`).
- C-02 had no guard against double-tapping "Start camera" before the first call resolved.
  `mountGyroCheck` disables the button synchronously for the duration of a pending
  `requestPermission()` call, and the `deviceorientation` listener is attached at most once (a
  `listening` flag scoped inside the mount closure, not module-level — a module-level flag would
  leak state across repeated mounts, e.g. in tests).
- C-02 copied `page.ts`'s three tiny DOM-assertion helpers into `camera.ts` almost byte-for-byte —
  the exact reuse finding I gave that PR. Added one shared `capture/src/dom.ts`
  (`requireElement`, generic `requireTyped<T>`) instead of adding a third copy here. `page.ts`
  itself is deliberately left untouched (same "don't touch already-shipped code for an unrelated
  concern" reasoning C-02 used for staying out of `page.ts`) — this only avoids *adding* a third
  copy, not retrofitting the first two; `camera.ts` could adopt `dom.ts` too, but that's not this
  story's call to make on another story's file.

**A real environment bug I caught myself while writing the tests, not something I assumed would
work:** my first attempt at simulating "this platform has `requestPermission`" used
`Object.assign(DeviceOrientationEvent, { requestPermission: fakeFn })` before `vi.stubGlobal`.
`Object.assign` mutates its first argument in place — that's the *real* global
`DeviceOrientationEvent` object, not a copy — so the fake method leaked into every later test
regardless of `vi.unstubAllGlobals()`, which only restores the global *binding*, not an object's
own mutated properties. Four tests failed with "Cannot read properties of undefined (reading
'then')" from state bleeding across tests before this was caught and fixed to stub a plain object
instead of mutating the shared constructor.

**Also confirmed directly, not assumed:** happy-dom defines a real `DeviceOrientationEvent`
global with no `requestPermission` by default (exactly the desktop/Android shape), and its
`new DeviceOrientationEvent(type, {alpha, beta, gamma})` constructor does *not* wire the init
dict to the instance's properties (same class of "happy-dom has real but incomplete DOM behaviour"
gap PR #72's review found for `getUserMedia`/`MediaStream`) — tests construct a plain `Event` and
assign `alpha`/`beta`/`gamma` directly instead.

**Typing the non-standard API without `any`:** `capture/tsconfig.json` has `strict: true` and
eslint's `strictTypeChecked` (bans `any`). `DeviceOrientationEvent.requestPermission` isn't in
TypeScript's DOM lib at all (it's iOS-only), so a local
`interface IOSDeviceOrientationEventConstructor { requestPermission?: () => Promise<"granted" |
"denied"> }` describes just the one optional static method, used via a single narrow cast.

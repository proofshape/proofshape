## Why this exists

R-10's acceptance criteria included "σ distribution reported per golden object." R-10 was
implemented and fully unit-tested against synthetic data in a session with no GPU/torch and no
local `fixtures/data/recon_runs`, so that could not be checked against real photographs in the
same session. Same shape of gap as R-06 through R-09's own splits: the σ computation itself — the
depth-residual spread, the downgrade logic, `compute_sigma_distribution`'s summary statistics —
is done and covered by synthetic tests; what's missing is running the full chain on real golden
objects and reading off the real numbers.

## Acceptance criteria

- For each of the five golden objects, the full chain (R-01 → R-02 → R-04 → R-06 → R-07 → R-08 or
  R-07 directly → R-09 → R-10) is run on real captured photographs, producing a real
  `observations.npz`/`mesh_provenance.glb` for `recon/uncertainty.py`'s `uncertainty_run` to
  consume.
- `compute_sigma_distribution`'s stats (count, min, max, mean, median, p90) are recorded per
  object in this story's notes, using `recon.uncertainty.DEFAULT_SIGMA_DOWNGRADE_THRESHOLD_MM`
  unless a real reason to override it turns up while running this.
- If the real distribution suggests `DEFAULT_SIGMA_DOWNGRADE_THRESHOLD_MM` (3.0 mm, an unmeasured
  assumption) is clearly wrong for real data (e.g. downgrading nearly everything, or nothing),
  record that as a finding here rather than silently tuning it — changing a story's own default
  based on one real-data run deserves a note explaining why, not a quiet edit.

## Tests

Same manual-check exception as R-17/R-18: reading off a real statistical summary from real
reconstructions is not something an automated test asserts — `recon/uncertainty.py`'s own logic
is already fully covered by synthetic-data unit tests written alongside it in R-10
(`tests/test_uncertainty.py`). This story is only the real-data run those tests cannot stand in
for.

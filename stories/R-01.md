## Acceptance criteria

- A script loads a golden capture folder and runs VGGT on the pod.
- Writes per-frame camera poses, depth maps and a point cloud to disk.
- Wall-clock time recorded per run.
- Succeeds on at least one golden object.

## Notes and decisions

_Written while working. What you tried, what surprised you, what you chose and why._
_If a decision here governs later work, add it to `docs/decisions.md` with a number._

2026-09-25: Implementation written and unit-tested locally; **not yet run on the Studio** — the
acceptance criterion "succeeds on at least one golden object" is still open until someone runs it
on the shared Tesla T4 and records the real timings here (no numbers exist yet, so none are
quoted).

- `recon/vggt_runner.py` is the script. Everything except the model call is plain NumPy and
  unit-tested (`tests/test_vggt_runner.py`); PyTorch/VGGT are imported lazily inside
  `run_vggt_model`, so CI and the Mac bootstrap never need them.
- Output per run (`fixtures/data/recon_runs/<sample>/`, git-ignored): `poses.npz`, `depth.npz`,
  `points.ply`, `run.json` (per-stage timings, device, dtype, frame list). R-11 and R-12 should
  emit this same layout so R-04 can consume any backend behind the config flag (D-009).
- The point cloud is built by unprojecting the saved depth maps with the saved poses, not from
  VGGT's separate point-map head, so it is exactly what R-04/R-07 could rebuild from the files.
- dtype is chosen explicitly: fp16 on the T4 (compute capability 7.5, no fast bf16) and on Metal
  (D-011); bf16 only on capability >= 8.0.
- VGGT is not on PyPI, so `requirements-gpu.txt` pins an upstream commit. VGGT declares
  `numpy<2`, so `requirements.txt` now pins `numpy==1.26.4` (needed for the tests anyway).
- Poses and depth are in VGGT's arbitrary scale — not metric. R-04 fixes scale.
- Open risks to check on first real run: phone JPEG EXIF orientation is not applied by VGGT's
  loader; the model-weights licence for `facebook/VGGT-1B` should be checked before any
  non-course use; weights should live under a Teamspace Drive `HF_HOME` (D-036).

2026-09-25 (later): Studio prepared for the real run. (Superseded by the 2026-09-26 entry below:
the run has now been done.)

- `requirements-gpu.txt` installed cleanly on the Studio; the preinstalled torch 2.8.0+cu128 was
  left untouched, as intended. All 51 unit tests pass there.
- Golden capture: `download_golden_capture.sh` hit Google Drive's "too many accesses" limit
  part-way through s-04 on the first attempt. A retry after a Studio restart downloaded s-04 and
  s-05; all five samples now pass their count and content-hash checks. Anyone re-downloading may
  hit the same limit — retrying later is the fix, not editing the manifest.
- EXIF orientation is a real case, not hypothetical: s-02 has 27/30 frames and s-03 has 2/27
  frames tagged orientation 6 (phone held portrait); s-01 has none. VGGT's loader ignores EXIF
  and feeds the raw 5712×4284 sensor buffer. That is deliberately kept: every frame then shares
  one sensor geometry, and a portrait-tagged frame is just a camera rolled 90°, which VGGT's pose
  output can represent. Applying the EXIF rotation instead would mix portrait and landscape
  frames and trigger VGGT's white padding. To check on the first real run: the rolled frames
  should come out with roughly 90° roll relative to the others.
- Weights licence answered: the `facebook/VGGT-1B` model card declares **CC-BY-NC-4.0**
  (non-commercial). Fine for the course; it would block any commercial use of this backend.
  Weights revision downloaded: `860abec7937da0a4c03c41d3c269c366e82abdf9`.
- Weights currently sit in the Studio's own `HF_HOME` (`~/.cache/huggingface`), not Teamspace
  Drive — no Drive mount was visible under `/teamspace` from the Studio. D-036 is not yet met here.
- The first run attempt failed loudly because the Studio had come back on a CPU-only machine
  ("PyTorch cannot see a GPU"). It needs to be switched back to the T4 before
  `python -m recon.vggt_runner fixtures/data/golden_capture/s-03` can produce the timings.

2026-09-26: **First real runs on the Studio's Tesla T4 — all three PASS.** torch 2.8.0+cu128,
fp16, VGGT-1B weights revision `860abec`, input resized to 392×518, `--min-confidence 0`.
One run each, so these are single measurements, not averages (seconds, from each `run.json`):

| Sample | Object | Frames | Points | model_load | preprocess | inference | unproject | write | total |
|---|---|---|---|---|---|---|---|---|---|
| s-04 | yellow triangular prism | 30 | 6,091,680 | 22.14 | 14.70 | 16.11 | 1.15 | 2.49 | 60.92 |
| s-01 | metal padlock (reflective) | 26 | 5,279,456 | 16.01 | 12.58 | 12.46 | 0.79 | 2.13 | 47.04 |
| s-03 | rounded rigid object | 27 | 5,482,512 | 17.16 | 13.00 | 13.18 | 0.77 | 2.19 | 49.22 |

s-04 was the first run after the weights were cached, which probably explains its slower
model_load. The weights had been downloaded the day before, so no run includes download time.

- How the clouds look (rendered as 2D projections, not yet opened in MeshLab): s-04 shows the
  yellow prism standing on the ChArUco board, and board and table form one thin plane side-on,
  so the 30 views agree. s-03 is a clean dome with its painted face visible. s-01 (reflective
  padlock) is recognisable but visibly noisier, which fits it being the hard case.
- Confidence: VGGT's depth confidence bottoms out at 1.0, and on s-04 the median pixel sits
  there (10th/50th/90th percentile 1.0 / 1.0 / 6.56). Keeping only the top ~10–15% removes most
  of the loose table points and keeps board and object. The CLI default still keeps everything;
  choosing a threshold remains R-04+ work, as noted above.
- EXIF check on s-03: IMG_3965 (tagged portrait) came out rolled 90° from frame 0, as
  predicted. IMG_3964 (also tagged portrait) did not. A likely explanation is that phones set the
  tag unreliably when pointing down at a table. Either way the cloud is coherent, which supports
  feeding raw buffers rather than applying EXIF. s-02 (27/30 portrait) has not been run yet.
- Outputs are in `fixtures/data/recon_runs/{s-01,s-03,s-04}/` (git-ignored, about 112 MB per run
  for s-04).

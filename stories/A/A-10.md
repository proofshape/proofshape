## Why this exists

Generative shape completion is never cut (D-017), but nothing names the model beyond the
proposal's "Diffusion-based shape completion, K samples", with "coverage-only guidance" as
the fallback (§9). Its GPU needs and input and output formats are unknown, so A-04 can't be
estimated until one model has actually run on our data.

## Acceptance criteria

- 2–3 diffusion-based shape-completion candidates are tried on a real golden-set segmented
  reconstruction, not only on their own training classes. For each: whether it runs at all
  on the Lightning T4 (16 GB, shared with VGGT) or the M2 Max; its input and output format;
  time per sample; whether two seeds give different surfaces; whether its licence fits a
  public academic repository.
- The choice is recorded as a decision in `docs/decisions.md`. Or, if none fits, the negative
  result is reported and taken to the team, since completion is never cut (D-017) and the
  proposal's fallback is coverage-only guidance.

## Tests

Manual-check exception: this story's output is a measured comparison and a decision, not code.
Spike scripts are throwaway and stay out of the repository; the exact commands and results go in
the notes so the run can be repeated.

## Notes and decisions

- Timeboxed at 4 h. Diffusion completion repositories often need custom CUDA operations; if
  a candidate won't build inside the timebox, that is a result, recorded as such.
- Many candidates are trained on everyday object classes. Mechanical parts on a board are a
  different distribution, which is why the test is on a real golden-set part.
- Shape completion passes the generative test by construction: different seeds give
  different surfaces. The spike checks that it actually does on our data.

### Result (2026-11-01 to 11-02): LaS-Comp runs on a T4 and was chosen (D-057)

**Scope, by the owner's choice: one candidate was run, not 2–3.** The criteria ask for 2–3
candidates to be tried. LaS-Comp was the only one that fitted every constraint on paper, so it was
the only one run; the rest were screened out for the reasons below. Only Hunyuan3D-Omni is a
judgment call rather than a hard fail. Running it would take about 2 h more, past the 4 h timebox,
so whether to run it is left to the review, as a possible follow-up story.

| Candidate | Why not run |
|---|---|
| Hunyuan3D-Omni | **Judgment call, not a hard fail.** Its licence doesn't apply in the EU, UK or South Korea, and forbids using its *outputs* there too (`License.txt` §1, §5c). That's usable for this US team, but a worse default than MIT for a public repo. Technically it would likely run: a photo plus a point cloud in, about 10 GB, torch 2.5.1/cu124, no compiled extensions in its code. Its seed is fixed at 1234 in `inference.py`, and it normalises its output, so both would need changing |
| SDFusion, PVD, PDR | Trained only on ShapeNet or MVP classes; old CUDA stacks |
| LION, SDS-Complete | NVIDIA non-commercial licence |
| DiffComplete, Diffusion-SDF | No released weights found |
| Shap-E, TRELLIS, TRELLIS.2 | Image or text input only, no partial shape; TRELLIS.2 needs ≥24 GB |
| GenPC, ComPC | Too heavy for a shared T4, or optimisation code not released |

**"Diffusion-based."** LaS-Comp's generator, TRELLIS, is a rectified-flow (flow-matching)
model, part of the diffusion family: it samples from noise, so different seeds give different
outputs. Hunyuan3D-Omni is a flow-matching model too.

**Model.** [LaS-Comp](https://github.com/DavidYan2001/LaS-Comp) (CVPR 2026), commit
`0da46f2569b484986d3737d97213428db962161f`. It is zero-shot: no training of its own, built on
`microsoft/TRELLIS-image-large` at revision `25e0d31ffbebe4b5a97464dd851910efc3002d96`. Input is a
partial point cloud (PLY) plus one photo of the part. Output is a mesh, which the runner wrote as
PLY in the input's own coordinates, so millimetres are kept.

**Hardware.** It ran on a Google Colab free-tier Tesla T4, the same GPU model as the Lightning T4.
Lightning has had no credits since Oct 7 (D-049). It cannot run on the M2 Max: the code calls
`.cuda()` directly, and spconv, kaolin, `pytorch3d._C` and xformers are CUDA-only. That was
established from the code (`run_lascomp_image_condition_single.py`, `trellis/pipelines/samplers/
flow_euler.py`, `trellis/representations/mesh/point_mesh_dist.py`) and not attempted.

**Input: s-04, the yellow triangular prism.** The served model came from a fresh run on `main`
using MPS on the M2 Max (`PROOFSHAPE_RECON_DEVICE=mps python scripts/smoke_r14.py
fixtures/data/golden_capture/s-04 --data-dir <dir>`: 59 s, metric, `observed_fraction` 0.24).
- The partial cloud is 20,000 points sampled from the model's *observed* faces. Only faces whose
  vertices fall in the largest DBSCAN cluster (eps 4 mm, min 10) of observed vertices more than
  6 mm above the board were kept.
- The cloud was then rotated 180° about x, so z points up out of the board (`diag(1,-1,-1)`,
  det +1).
- The photo is IMG_4080, cropped to the part.
- **The 6 mm cut also removed the bottom 6 mm of the part's sides.** It was there to drop the
  board skin (see "Found along the way"). As a result, no completion reaches below about 6 mm.
  This is a flaw in the input preparation, not in the model.

**Results** (five seeds, no Y/Z swap):

| Measure | Value |
|---|---|
| Runs on the T4 | Yes |
| Peak GPU memory | 11.06–11.26 GB of 15 GB |
| Time per sample | 295.5–297.9 s |
| Model load | 47.5 s, once per process |
| Observed points within 1 mm of the completion | 94.5–100% (median distance 0.17–0.35 mm) |
| New surface (>2 mm from anything observed) | 6–26% of each completion |
| Seed-to-seed distance, new region | median **1.19 mm**, p90 4.22 mm, max 9.91 mm |
| Seed-to-seed distance, observed region | median 0.36 mm, p90 0.84 mm |
| Pairwise Chamfer between seeds | 0.48–0.81 mm (median 0.68 mm) |

So **different seeds do give different surfaces on our data**, and the differences sit in the
surface the camera did not see, which is what A-05's disagreement map needs.
- The orientation check on seed 0 favoured no swap. With no swap, 99.9% of observed points lay
  within 1 mm and 11% of the surface was new. With the swap, those were 97.6% and 33%.
- Bounding boxes were 65 × 32–34 × 24–25 mm, against the CAD's 60 × 26 × 30. That is
  plausibility only, never a verdict (D-005). The size comes from the observed shell, and the
  height is short because of the 6 mm cut.

Until LaS-Comp adds a LICENSE, nothing of it is copied into this repository. It is installed at
build time instead (D-057).

**Two undocumented setup steps**, both needed to run it:
- The TRELLIS `pipeline.json` must list `"sparse_structure_encoder":
  "ckpts/ss_enc_conv3d_16l8_fp16"`. The weights include that file, but the official config doesn't
  list it, so loading fails with `KeyError: 'sparse_structure_encoder'`.
- Its `requirements.txt` is a `pip freeze` with local wheel paths, so it can't be installed as-is.
  The working set is below.

The spike's own runner loaded the pipeline once and looped over seeds, timing each sample. It
called the same functions as the script above with LaS-Comp's defaults: `alpha_eta` 0.1,
`rescale_t` 3.0, 100 sparse-structure steps and 25 SLAT steps. The runner, the analysis script and
the outputs stay out of the repository.

**What this means for A-04** (recorded in D-057 and in A-04's notes):
- **Cost.** At about 5 min a sample on a T4, the proposal's final-pass K of 8–10 takes 40–50 min.
  The in-loop K of 3–5 can't run during capture at all.
- **Memory.** 11.3 GB on a 15 GB T4 can't share the card with VGGT at the same moment.
- **Environment.** It needs Python 3.10 and torch 2.4. The project needs Python ≥3.11, and the
  Lightning Studio ships torch 2.8.

**Found along the way, outside this story:** the served s-04 model still contains a thin board
skin, 3–5 mm above the board, across the whole 160 × 120 mm area. The fusion mesh also has walls
the size of the volume. Both are for the reconstruction lane; this spike worked around them by
isolating the part.

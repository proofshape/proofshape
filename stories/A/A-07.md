## Why this exists

Proposal §6.7: "The capture session is run by a tool-calling LLM loop. It holds the session
state, decides what happens next, and speaks to the person holding the phone." It calls five
already-built, deterministic tools (`score_next_view`, `check_frame`, `vlm_inspect`,
`coverage_report`, `finish_session`): "**What the agent does that the geometry cannot.** It
decides *when* to invoke the scorer rather than computing direction itself; it interprets why a
frame failed and rephrases the reason for a non-expert; it adapts when the user is clearly
struggling... and it explains at the end what was captured and what was not." "**What it must
never do.** It does not compute geometry... The agent orchestrates and communicates; the maths
stays deterministic." "**Fallback.** If the agent errors, times out, or loops, capture falls
straight back to the deterministic policy: fixed orbit plus the scorer. The session always
completes." A-06's own notes state the dependency directly: "Defining them first, with no
language model involved, gives both the agent (A-07) and its deterministic fallback (A-08) the
same footing. The agent is the largest generative-AI item (the proposal's 30 h) and nothing has
started it." Both A-06 and A-08 are now Done, so this story's structural blockers have genuinely
cleared — this is no longer titles-only for lack of a foundation, only for lack of the loop
itself.

## Acceptance criteria

- A tool-calling LLM loop that calls only A-06's five typed tools, never computes geometry
  itself, and falls back to A-08's deterministic policy on error, timeout or loop detection, so
  "the session always completes" — the exact guarantee A-08 was built first to satisfy.
- Handles `check_frame`/`vlm_inspect` returning `unavailable` gracefully — today's real, measured
  state (D-054: the phone's frame-gate result doesn't yet reach the server) — rather than
  assuming real-time gate telemetry that doesn't exist.
- Interprets a rejection reason in plain language for the supplier, and explains at session end
  what was captured and what wasn't, per the proposal's direct language.
- Honestly passes the generative "run it twice" test: the same session state can produce a
  different utterance or tool-call ordering across runs, which is what distinguishes this story
  from A-06/A-08's deliberate determinism.

## Tests

Written alongside the loop: a mocked/stubbed model response harness exercising the fallback path
(forced error, forced timeout, forced repeated tool call) and confirming the deterministic policy
takes over in every case; `check_frame`/`vlm_inspect` always-`unavailable` handled without a
crash or an invented result.

## Notes and decisions

- **Unusually large for one story.** The proposal's own component table gives the capture agent
  30 h total; A-06 (5 h) and A-08 (5 h) already account for 10 h of it, leaving about 20 h here —
  well past this project's usual story size ("one story is one pull request... if growing past
  one or two work sessions, stop and split," AGENTS.md). Whoever claims this should seriously
  consider splitting it (e.g. the tool-calling loop itself vs. the conversational/phrasing layer)
  rather than taking the full 20 h as one pull request.
- No model has been pinned for the agent anywhere in the repo; proposal §9 names no specific
  model for this row, unlike A-01/A-03's Gemini Flash-Lite pin. A pin, and its recording as a
  decision, is this story's own job.
- Whether the agent's conversation view is a new phone UI surface or an extension of the existing
  capture shell is not decided anywhere; the sprint plan names "the agent conversation view" as
  its own capture-lane line item, separate from A-05's next-view arrow.

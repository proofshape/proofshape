## Why this exists

Proposal §6.7: "The capture session is run by a tool-calling LLM loop. It holds the session
state, decides what happens next, and speaks to the person holding the phone." It calls five
already-built, deterministic tools (`score_next_view`, `check_frame`, `vlm_inspect`,
`coverage_report`, `finish_session`): "**What the agent does that the geometry cannot.** It
decides *when* to invoke the scorer rather than computing direction itself; it interprets why a
frame failed and rephrases the reason for a non-expert; it adapts when the user is clearly
struggling... and it explains at the end what was captured and what was not." "**What it must
never do.** It does not compute geometry... The agent orchestrates and communicates; the maths
stays deterministic." "**Fallback.** If the agent errors, times out, or loops, capture falls
straight back to the deterministic policy: fixed orbit plus the scorer. The session always
completes." A-06's own notes state the dependency directly: "Defining them first, with no
language model involved, gives both the agent (A-07) and its deterministic fallback (A-08) the
same footing." Both A-06 and A-08 are now Done, so this story's structural blockers have genuinely
cleared — this is no longer titles-only for lack of a foundation, only for lack of the loop
itself.

**Split from the original A-07, on review (@TabeenRaoof, #302):** the original draft was one
~20 h story — several times this project's usual size. This story is now the core loop and
fallback only, built and tested against a recorded or mock model response; the conversation view
is C-22 (a capture-lane item, per the sprint plan's own separate budget bucket), and the live
model pin and real-model check is A-13.

## Acceptance criteria

- A tool-calling LLM loop that calls only A-06's five typed tools, never computes geometry
  itself, and falls back to A-08's deterministic policy on error, timeout or loop detection, so
  "the session always completes" — the exact guarantee A-08 was built first to satisfy. Built and
  tested against a recorded or mock model response, not a live API call (that's A-13's job).
- Handles `check_frame`/`vlm_inspect` returning `unavailable` gracefully — today's real, measured
  state (D-054: the phone's frame-gate result doesn't yet reach the server) — rather than
  assuming real-time gate telemetry that doesn't exist.
- Interprets a rejection reason in plain language for the supplier, and explains at session end
  what was captured and what wasn't, per the proposal's direct language — the text the loop
  produces, independent of how it is eventually displayed (C-22's job).
- **Needs a contract change it doesn't yet have:** the agent runs server-side, and the phone has
  to show its messages — a new field or route, the same shape as A-11's hint addition. This is a
  D-031 round, which merges only at a sprint boundary (the next one after Nov 13 is Dec 2); name
  it now rather than discover it mid-implementation.

## Tests

Written alongside the loop: a mocked/stubbed model response harness exercising the fallback path
(forced error, forced timeout, forced repeated tool call) and confirming the deterministic policy
takes over in every case; `check_frame`/`vlm_inspect` always-`unavailable` handled without a
crash or an invented result.

### Built (2026-11-12)

`recon/agent_loop.py` is the "caller" `agent_tools`/`agent_policy` each name in their own
docstrings but don't implement. `run_agent_turn(record, store, session_id,
schedule_reconstruction, model_caller, *, min_frames, ...)` is the entry point.

- **Why one internal loop per turn, not one model call per turn:** the proposal names three
  distinct fallback triggers — "errors, times out, or loops." A model can only meaningfully
  *loop* if it can chain several tool calls before giving a final answer, the shape every real
  LLM function-calling API actually has. So each turn asks the model repeatedly (bounded by
  `max_steps`), executing whatever it asks for, until it is done, asks to finish the session, or
  one of the three triggers fires.
- **The three triggers, as code, not just prose:**
  - *errors* — `model_caller` raises, or its reply doesn't parse (`parse_model_decision`, which
    mirrors `recon.vlm_check.parse_response`'s duck-typing on a `.text` attribute — no SDK, no
    network, a plain `SimpleNamespace` in tests).
  - *times out* — a declared wall-clock budget, `timeout_s` (default 10.0 s), the same kind of
    stated-not-measured bound D-055 already set for A-01.
  - *loops* — the model asks for the same tool more than `max_repeated_calls` times in a row
    (default 2, i.e. tripped on the would-be third identical request). Every tool's result is
    gathered once and is static for the whole turn — nothing can change mid-turn without a
    separate `upload_frame` call, outside this function's scope — so repeating the same read-only
    tool is never productive. Running out of `max_steps` without resolving is folded into this
    same `"loop_detected"` reason rather than invented as a fourth category.
- **The session always completes, structurally.** `agent_policy.Finish`'s own docstring says
  "the caller now calls `agent_tools.finish_session`" — this function is that caller, on both the
  model-driven path (the model names `finish_session` as its tool) and the fallback path (`Finish()`
  from `agent_policy.next_action`). Whichever path reaches it, `finish_session` is only ever called
  once per turn.
- **Plain-language narration is split by path, not invented twice.** On the model-driven path the
  mock/recorded model supplies its own `message` (that is its job per the proposal); on the
  fallback path, which by definition has no model to ask, `describe_action_for_supplier` renders
  each of `agent_policy`'s six `Action` variants into one deterministic sentence.
- **Reused, not reimplemented:** `agent_policy.ToolResults`/`.next_action`/`.Action`, and all five
  of `agent_tools`'s functions — no copy of their logic anywhere in this file.
- **Tests (`tests/test_agent_loop.py`, 21 tests):** the three forced triggers (error, timeout via
  an injected fake clock, repeated tool call) each land on the right `fallback_reason`; a
  `max_steps` exhaustion that never repeats still reports `"loop_detected"`; the fallback's
  `Finish()` action is proven to actually call `finish_session` (via a monkeypatched
  `coverage_report` forcing a fully-covered orbit, rather than hand-deriving exact gyro angles
  for 13 real orbit slots) in both the success and the session-not-found cases; the normal path is
  exercised over several steps before finishing; `check_frame`/`vlm_inspect` being unavailable
  (D-054's real, current state) is asserted not to crash either path; the fallback path is
  deterministic for the same input, the same property A-08's own tests check.
- **Not built here, as scoped:** no live model call (A-13), no phone-facing display or contract
  change (C-22/a future D-031 round, named in this story's own acceptance criteria above), no
  wiring into `recon/service.py`'s HTTP routes — nothing there calls `agent_policy.next_action`
  from a live route either, so there was no existing convention to match, and the loop is a
  standalone, directly-testable component exactly like A-06/A-08 already are.

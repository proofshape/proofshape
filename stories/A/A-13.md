## Why this exists

Split out of the original A-07 on review (@TabeenRaoof, #302), the same way A-10/A-12 are split
from A-04 for shape completion and A-01 is split from A-11 for VLM supervision: A-07 builds and
tests the agent loop against a recorded or mock model response; this story is what actually pins
a real model and checks it live, the same pattern A-01 used ("a pinned Gemini Flash-Lite model").
No model has been named for the agent anywhere in the repo — proposal §9 names no specific model
for this row, unlike A-01/A-03's Gemini Flash-Lite pin — so this story's first job is choosing
and recording that pin as a decision, not assuming one.

## Acceptance criteria

- A specific model is chosen and pinned (a stable snapshot, never `-latest`, following A-01's
  precedent), recorded as a decision with the reasoning, not silently defaulted.
- A real, live run of A-07's loop against that pinned model is checked and recorded — same
  pattern as A-01's manual check, a written result, not a unit test, since a live model call is
  exactly the kind of thing D-052/this project's testing norms treat as a written-check exception.
- This is the check that actually makes the agent component satisfy AGENTS.md's "run it twice,
  can it give two different answers" generative test end to end, since A-07 alone is deliberately
  built against a fixed recorded response.

## Tests

Written-check exception: a live model call is not economically unit-testable the same way as the
rest of the loop (A-07 already covers that against a recorded response); this story's check is a
written record of a real run, following A-01's manual-check pattern.

## Notes and decisions

- No cost, latency or accuracy is claimed beyond what this check actually measures (lane-wide
  D-003 rule).
- **Implementation choice (D-068):** A-13 has its own `gemini-3.5-flash-lite` pin, using the
  existing `google-genai==2.33.0` Developer API dependency. `GeminiAgentCaller` serializes only
  capture/reconstruction status, requested tool results and turn history; the API key is passed
  explicitly and never included in the request or output. The provider schema uses one `action`
  field so it cannot ask for a tool and mark itself done at the same time.
- **A-07's eager-tool question is resolved:** normal model turns invoke only the read tool the
  model requests and cache that result; the deterministic fallback still gathers its full
  snapshot. This makes the choice to call `score_next_view` meaningful and avoids running it on
  every model turn. The `check_frame` tool remains honestly unavailable per D-054.

## Live model check (2026-11-12)

**Operator and data:** @dalwalyk, local macOS checkout, using the existing `GEMINI_API_KEY` from
the ignored `.env`. The credential value was not printed or recorded. Two independent A-07 turns
used the same three synthetic accepted-frame gyro readings; no photos, supplier data or model
weights were sent. Command, from the repository root:

```bash
set -a
source .env
set +a
PYTHONPATH=inspect .venv/bin/python scripts/check_agent_model.py
```

Both runs received valid model responses. Requested and returned model were
`gemini-3.5-flash-lite` for every response. The model-generated tool/message traces differed:
one run said "Please capture the first view of the part to begin the session." while the other
said "Let's inspect the current view to ensure proper alignment and visibility." The API reported
1,162 total tokens in the first run and 1,200 in the second; these are run totals, not cost,
latency or accuracy claims.

Both turns then repeated the unavailable `vlm_inspect` tool and were caught by A-07's
`loop_detected` fallback, which returned the deterministic "Keep going" message. This records
the observed behavior rather than claiming the model completed a non-fallback turn. The live
variation is in A-07's model-authored tool/message transcript; the final fallback narration is
deterministic. D-054's unavailable tool state is included so a follow-up can evaluate prompt
adherence with a real VLM result.

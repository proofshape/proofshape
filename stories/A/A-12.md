## Why this exists

A-04 builds the completion stage around a runner it can only test with a stub. LaS-Comp needs
Python 3.10, torch 2.4 and CUDA (D-057), and neither CI nor the M2 Max has them. Until a real
runner meets A-04's contract, no reconstruction gets real completion samples, and A-05's
disagreement map has nothing real to work from. K and the time budget that A-04 declares stay
provisional until this story measures them.

## Acceptance criteria

- **The runner.** `scripts/lascomp_runner.py` runs under Python 3.10 in the LaS-Comp environment
  and meets A-04's request and result contract (`recon/completion_contract.py`). It:
  - loads the pipeline once;
  - loops over the request's seeds while the budget allows;
  - maps LaS-Comp's normalised output back to the input's millimetres;
  - writes each sample as the contract's mesh file;
  - reports the pins it actually ran.
- **The setup.** `scripts/setup_completion_env.sh` builds that environment on a CUDA host (Colab
  or Lightning) from A-10's working package set. It:
  - checks CUDA;
  - clones LaS-Comp at D-057's commit and verifies it;
  - downloads the TRELLIS weights at D-057's revision;
  - applies the `pipeline.json` `sparse_structure_encoder` fix idempotently.

  Nothing of LaS-Comp is copied into this repository (D-057).
- **Measured, then set.** A Colab T4 run on s-04 and s-02, whose photos carry an EXIF rotation where
  s-04's don't. It is prepared on the Mac with A-04's `prepare`, run on Colab, and brought back with
  `ingest`. It records the model load time, time per sample, peak GPU memory and the seed-to-seed
  spread. A-04's provisional K, budget and overrun allowance are then replaced with values chosen
  from that measurement. It also checks whether fewer sampling steps keep the spread (D-057).

## Tests

Unit tests, written alongside the code (D-029):
- the runner's budget loop, request handling and output writing, with LaS-Comp's pipeline faked so
  they run in CI under the project's own Python;
- a static check that the setup script's pins match `recon/completion_contract.py`'s.

The GPU run itself can't be automated, because CI has no CUDA. It is the written check in the third
criterion, with the commands and figures in the notes.

### The rule for a speed lever (written 2026-11-04, before any measurement)

The owner chose to measure two speed levers alongside the core runs, and to keep the proposal's
K = 8 with the budget sized from measurement. This rule is fixed here first, so the numbers can't
shape it.

**What is measured.** Per sample:
- t, the runner's `time_s`;
- M, peak reserved GPU memory;
- F, the share of the partial cloud's points within 1 mm of the completed mesh, point to triangle,
  as in A-10's analysis.

Per pair of samples on the same part:
- U, the median seed-to-seed distance where the camera did *not* see (more than 2 mm from the
  partial);
- O, the same where it did.

**How each is computed** (fixed 2026-11-06, still before any run). A-10 kept the code for its F but
not for its spread figures, so "as in A-10" is written out here:
- Every distance is point to triangle, against the other mesh's surface (Open3D's
  `RaycastingScene.compute_distance`), in the contract's z-up millimetres, on the meshes as the
  runner wrote them.
- F counts the 20,000 points of the folder's own `input/partial_zup.ply`.
- U and O for a pair (a, b): 50,000 points are sampled uniformly by area on each mesh, seed 0.
  A point is *unseen* if it lies more than 2 mm from its nearest partial point, *seen* otherwise.
  Each point is measured to the other mesh, both directions are pooled, and U and O are the medians
  of the unseen and the seen distances. Pooling makes U(a,b) = U(b,a), so no pair's order matters.
- "median U(D)" and "max U(D)" are over D's three pairs (0,1), (0,2) and (1,2).
- t is `result.json`'s `time_s`; M is `lascomp_metrics.json`'s `peak_reserved_gb`.
- The cold load is the largest `load_s` of the default runs. Each run is a fresh process.
- The shutdown gap is a run's wall time, launch to exit, minus the runner's own `total_s`. The
  service's hard timeout counts from launch, so the gap has to include interpreter start-up and the
  last write as well as the exit. The runner can't time its own exit, so the Colab cell that
  launches it does.

The baseline D is s-04 at LaS-Comp's defaults (100 sparse-structure / 25 SLAT steps, blocking
launches), seeds 0, 1 and 2.

**Blocking launches off (B0, seed 0).** This changes no computation, only how kernels are queued.
It is adopted only if all of these hold:
- t(B0) is less than min t(D) by more than max(5% of median t(D), 3× the range of t(D));
- F(B0) ≥ min F(D) − 0.005;
- U and O between B0 and D1 or D2 stay within D's maxima;
- M(B0) ≤ max M(D) + 0.25 GB;
- the runner's own check confirmed launches really were non-blocking.

Whatever the outcome, U and O between B0 and D0 (same seed) is recorded as the noise floor. Any
spread A-05 relies on has to exceed it.

**Fewer sparse-structure steps (S0 and S1 at N steps, seeds 0 and 1).** This changes the algorithm.
N = 50, fixed before the run, because each experiment's folder is prepared in advance. The reason: the
sparse-structure stage runs 100 steps, each with up to three model passes plus a backward pass,
against SLAT's 25 single passes. If the stage timings show it doesn't dominate, the lever simply
fails the time criterion below. It is adopted only if all of these hold:
- mean t(S) ≤ 0.8 × mean t(D), since a smaller saving isn't worth leaving LaS-Comp's tested
  default;
- min F(S) ≥ min F(D) − 0.01;
- 0.5 × median U(D) ≤ U(S0,S1) ≤ 2 × median U(D), and O(S0,S1) ≤ max O(D) + 0.1 mm;
- U(Sk,Dk) ≤ max U(D) for k = 0 and 1, so fewer steps moves a sample no more than a new seed does;
- no sample is rejected at ingest.

If adopted, it is marked "s-02 unverified", since only s-04 is run at N steps. **Any miss keeps
LaS-Comp's default.**

**The budget,** whatever is adopted, comes from the slowest measured configuration: defaults, on
both parts. Rounding is up to the next 30 s.
- `budget_s` = cold load + 8 × the slowest default sample × 1.05. The 1.05 is a declared allowance
  for T4 speed varying between sessions.
- `overrun_allowance_s` = max(2 × (the largest rise in `time_s` from one sample to the next + the
  largest shutdown gap), 0.2 × the slowest sample).

An adopted lever then only shortens real runs; it never enters the cap.

## Why this exists

The proposal (§6.7): "If the agent errors, times out, or loops, capture falls straight back
to the deterministic policy: fixed orbit plus the scorer. The session always completes. This
fallback is built first, at M1, so the agent is layered onto something that already works."
It is also the baseline S6 measures the agent against: "does the agent actually beat the
deterministic policy?"

## Acceptance criteria

- **A policy over A-06's tools.** Given a session's state, it returns the next action from a
  closed set (shoot the next orbit slot, explain a rejection from a fixed table of messages,
  request extra views, finish). The same state always gives the same action, and it never
  calls a language model.
- **"Plus the scorer" in batch mode.** Capture is batch-only (D-002), so the scorer can only
  run after a first reconstruction. Whether that means one recapture round (the scorer
  proposes extra views, requested once, then finish) or the scorer's views are simply
  reported, is decided and written down here. If a second batch needs a contract change, the
  D-031 request is named, not made silently.
- **Every session completes.** Every path through the policy ends in `finish_session`,
  including all frames rejected, no reconstruction, and a tool returning `unavailable`.

## Tests

13 unit tests in `tests/test_agent_policy.py`, written alongside the code (D-029): a normal
session (orbit coverage drives `ShootNextSlot`, then `Finish` once covered), repeated rejections
(`ExplainRejection`, same code/message every time), a failed reconstruction (`ReportFailure`,
including a missing failure dict), a completed reconstruction with and without a remaining
under-observed count (`ReportComplete`), and every tool unavailable including a hypothetical
unavailable `coverage_report` (falls through to `Finish`, never raises). Determinism checked
directly: the same `(record, tools)` input asserted to give the same action twice.

## Notes and decisions

- Not generative, on purpose. It is the floor the agent (A-07) stands on and the baseline it
  is judged against.
- C-09's capture loop already walks a fixed orbit on the phone. This story is the server-side
  policy that decides what comes next and when the session is done; it doesn't replace C-09.
- The A-10 "completion-driven recapture round" on the unmerged September branch was a
  version of this question; it is superseded, and this story decides it afresh.

2026-10-24: Implementation. Both decisions this story's own first two acceptance criteria
required were confirmed with the team before any code:

- **`ExplainRejection` stays in the closed action set, documented as currently inert.** The
  proposal's own table says `check_frame()` returns "the local gate result: blur, exposure,
  duplicate," but D-054 (A-06's own review-driven fix) made `check_frame` always `unavailable` —
  the client-side gate's rejection never reaches the server. `recon/agent_policy.py`'s
  `next_action` keeps a real, tested branch driven by `check_frame`'s result (the exact
  `accepted`/`code`/`message` shape it produced before D-054 reverted it for a different reason
  — the wrong data *source*, not the wrong *shape*), but since that tool is always `unavailable`
  today, the branch is practically dead in production until a future story adds real gate
  telemetry. Not silently dropped, not silently pretended to work.
- **No recapture round; gaps are reported, not re-captured.** The frozen v1 contract is
  single-shot per session, so an actual second capture cycle would need a new D-031 contract
  change, which nothing today needs badly enough to spend speculatively — same call A-06 already
  made. Once a reconstruction exists, `next_action` only ever returns `ReportComplete` (or
  `ReportFailure`), carrying whatever `score_next_view` still finds under-observed; it never
  orchestrates another capture cycle.
- `vlm_inspect` gets no decision branch at all, not even an inert one: A-01 doesn't exist yet,
  so there's no real result shape to branch on — inventing one would be designing A-01's output
  format here instead of there.
- `next_action` is a pure function of `(record, ToolResults)`; it does not call A-06's tools
  itself. The caller (eventually A-07, or a test) calls them and hands in the results, the same
  no-I/O-in-the-decision-logic style `recon.agent_tools` already uses.
- Mutation-tested the rejection-detection guard by hand: replacing the condition with `if False`
  fails exactly the two tests meant to catch it (`test_explains_a_rejection_when_check_frame_
  reports_one`, `test_explains_the_same_rejection_every_time_it_repeats`), nothing else.

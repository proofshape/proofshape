## Why this exists

Proposal §7.4: "The buyer describes what matters in prose — 'the four mounting holes need to
line up within about 2 mm, and the sealing face has to be flat' — and an LLM converts it into the
structured spec the system already needs:
```
{ features: [ { name, kind: hole|face|edge|overall, tolerance_mm, critical } ],
  assumptions: [ ... ] }
```
That structure feeds the ingestion pre-check directly... **The buyer confirms before anything is
used.** The parsed spec appears as an editable table, and every field can be corrected. The model
proposes; the human approves." §9's component table pins the model: "LLM (inspection spec) |
Gemini Flash-Lite API, structured output | Manual tolerance form | Tier 2" — the manual form is
the guaranteed fallback, not this story's competitor. C-16 (buyer setup page) already settles
which of the two is primary: its own acceptance criteria state the buyer page "takes... an
editable table in §7.4's shape... **A-03 later fills the same table and never bypasses it.**" So
the manual table is the guaranteed Tier-2 path; this story is an additive convenience that must
populate the exact same table, never a separate or bypassing one.

AGENTS.md lists the natural-language spec as one of five generative-AI components that are never
cut, with the same protection as Tier 1. C-16 (the page this story's output lands in) is itself
`Blocked` on R-34's contract round. The parsing core — prose in, validated §7.4 JSON out — needs
none of that: it is a pure function over text, testable against the schema directly. Splitting
the parser from the page it feeds keeps this never-cut component alive and startable now, rather
than silently waiting behind C-16/R-34's Nov 13/Dec 2 contract-boundary timing.

## Acceptance criteria

- Given free-text buyer prose, produces exactly the §7.4 JSON shape (`features:
  [{name, kind, tolerance_mm, critical}], assumptions: [...]`), with `kind` restricted to the
  proposal's four values, checked against the schema directly — no dependency on C-16's page
  existing to validate against. `tolerance_mm` is a positive number **or `null`** when the
  buyer's prose gave no figure for that feature — never invented to satisfy the schema, which
  would otherwise force a model guess into I-09/I-07's Pass/Fail decision (AGENTS.md's hard
  rule: "a model's guess must never approve or condemn a component"); a null must be recorded
  with a matching plain-language assumption, checked (a null with zero assumptions at all is
  refused), not merely asked for in the system instruction. Caught on review (@TabeenRaoof,
  #320) in two rounds: the first draft required a positive number unconditionally; a second
  pass found the fix's own wording ("state or clearly imply a number") still let the model
  reason its way back to an invented figure, and that the "matching assumption" half was asked
  for but never enforced.
- Uses Gemini Flash-Lite with structured output (the pinned model per proposal §9), following
  A-01's precedent for pinning a stable model snapshot, never `-latest`, recorded as a decision.
- No cost, latency or accuracy is claimed for the parse (lane-wide rule); any quality claim needs
  a manual check, following A-01/A-10's pattern.
- **Needs a contract change it doesn't yet have:** the Gemini key can never reach the phone app
  (D-042: "the phone app cannot hold a secret", the same rule A-01 follows), so the parse must run
  through a server route, not directly from the buyer's browser. This is a D-031 round, which
  merges only at a sprint boundary (the next one after Nov 13 is Dec 2) — name it now rather than
  discover it mid-implementation, and consider letting it ride the same D-031 request as R-34's
  contract round.
- **Wiring the output into C-16's editable table is C-16's own acceptance criterion, not this
  one** (moved there on review, @TabeenRaoof, #320, so this story can be honestly Done on the
  parser core alone rather than Done with an unmet criterion of its own). C-16 also owns
  requiring the buyer to fill every null `tolerance_mm` before submitting — the parser's job
  stops at producing an honest, possibly-incomplete spec for a human to complete and confirm.

## Tests

Written alongside the parser core: a handful of example prose inputs with known expected
`features`/`assumptions` shapes, checked for schema validity (not semantic correctness, which is
the human reviewer's job per the confirm-before-use rule); a structurally invalid model reply is
rejected rather than silently coerced into the table. The wiring step is C-16's own test to write,
once that page exists.

### Built (2026-11-12)

`recon/spec_parser.py`, following `recon/vlm_check.py`'s own shape exactly — the only existing
precedent in this codebase for "call an LLM, get structured output, test without a network call":

- **`InspectionSpec`/`SpecFeature`** are the one real definition of §7.4's shape anywhere in the
  codebase today (checked directly: `contracts/openapi.yaml` marks the tolerance-table schema
  `x-proofshape-extends-at` on purpose, D-032; R-34's future order store takes the spec as an
  opaque JSON blob with no internal validation) — not a duplicate of something defined elsewhere.
  `features: list[SpecFeature]` (`name` non-empty, `kind` one of `hole|face|edge|overall`,
  `tolerance_mm` strictly positive **or `null`**, `critical` a bool — mirroring C-16's own
  stated validation rules, now extended for the null case the first draft missed, see below)
  and `assumptions: list[str]`. `assumptions`'s element type is genuinely unspecified anywhere
  the proposal or any story states it (`assumptions: [...]`) — `list[str]` is this story's own
  declared choice, recorded as such rather than presented as a fact found elsewhere.
- **`tolerance_mm` is nullable, fixed on review in two rounds (@TabeenRaoof, #320).** The first
  draft required a positive number unconditionally, which would have forced the model to invent
  a figure for "the sealing face has to be flat" — the proposal's own example sentence, which
  names no number — and that invented figure would have flowed straight into I-09/I-07's
  Pass/Fail decision: exactly the "a model's guess must never approve or condemn a component"
  hard rule (AGENTS.md). Verified directly before fixing: the first draft's own test fixture
  silently invented `0.1mm` for that feature, with no assumption recorded. Now `tolerance_mm:
  float | None`.
  - **Round two caught that the first fix's own instruction still left the door open.** "Never
    invent a tolerance the buyer did not state *or clearly imply* a number for" lets the model
    reason that "flat" clearly implies a small number and put one back in — the exact failure
    this fix exists to close, and one a recorded-reply test can't catch since it tests the
    parser, not the model's reasoning. Reworded to "only put in a number the buyer actually
    wrote."
  - **Round two also caught that "a null is recorded with a matching assumption" was asked for
    in the instruction but never checked.** A null `tolerance_mm` with `assumptions: []` still
    parsed. Added a cheap, code-level check: a spec with any null tolerance and zero assumptions
    at all is `unparsed` (`reason="missing_assumption_for_null_tolerance"`). Matching one
    specific assumption to one specific feature is free text and can't really be checked in
    code — this is the practical middle ground the review itself suggested.
- **An empty `features: []` is `"unparsed"` with `reason="no_features"`, fixed on review (same
  PR).** The first draft accepted it as a vacuously `"parsed"` empty spec; naming it tells the
  buyer something an empty table alone would not.
- **`SpecParseResult`** mirrors `FrameCheck`'s checked/unchecked discipline exactly (a
  `model_validator` enforcing the same consistency rule): `"parsed"` with a spec and no reason,
  or `"unparsed"` with a reason and no invented spec — never a silent coercion, this story's own
  explicit acceptance criterion.
- **`parse_spec_response`** is a pure function, duck-typing on the response object exactly like
  `parse_response` does — no SDK, no network, testable with a plain `SimpleNamespace` the same
  way `test_vlm_check.py` already does.
- **`GeminiSpecParser`** mirrors `GeminiInspector`: explicit key, finite transport timeout, no
  SDK retry, `response_json_schema` set to `InspectionSpec.model_json_schema()`. The model pin is
  **D-067**, its own decision independent of A-01's `MODEL` constant (not imported from
  `recon.vlm_check`) — both happen to name the same snapshot today (proposal §9), the same way
  A-10/A-12 each pin independently for shape completion; see D-067 for why these are two
  decisions, not one shared constant.
- **Tests (`tests/test_spec_parser.py`, 14 tests):** the proposal's own example sentence ("the
  four mounting holes... the sealing face has to be flat") parsed correctly, with the sealing
  face's `tolerance_mm` null and an assumption recording the gap, not an invented number; a
  feature with no stated tolerance staying null; a null tolerance with zero assumptions at all
  rejected (`reason="missing_assumption_for_null_tolerance"`); an empty feature table rejected
  as `"no_features"`; assumptions passing through as plain strings; an `overall`-kind feature
  with no named part; seven rejection cases (a zero or negative `tolerance_mm`, a `kind` outside
  the four values, an empty `name`, a non-numeric `tolerance_mm`, a missing required field, an
  unexpected extra field) each asserted `"unparsed"` with `reason == "invalid_reply"`, never
  coerced; the same blocked/empty/incomplete/malformed-reply cases `test_vlm_check.py` already
  covers.
- **No cost, latency or accuracy is claimed** — this story's own lane-wide rule. No live call was
  made; `GeminiSpecParser` is untested against the real API, the same deferred-quality-claim
  pattern A-01/A-10 already use (a manual check, if ever done, is separate future work, not part
  of this story).
- **Not built here, as scoped:** no HTTP route, no contract change (D-042/D-031, named in this
  story's own acceptance criteria above, not built). Wiring into C-16's table is C-16's own
  acceptance criterion now, not this story's at all (moved there on review, above) —
  `docs/manual.md`'s existing "Planned" line for this feature is left as-is, since a buyer still
  can't reach this end to end without C-16/R-34.

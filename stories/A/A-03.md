## Why this exists

Proposal §7.4: "The buyer describes what matters in prose — 'the four mounting holes need to
line up within about 2 mm, and the sealing face has to be flat' — and an LLM converts it into the
structured spec the system already needs:
```
{ features: [ { name, kind: hole|face|edge|overall, tolerance_mm, critical } ],
  assumptions: [ ... ] }
```
That structure feeds the ingestion pre-check directly... **The buyer confirms before anything is
used.** The parsed spec appears as an editable table, and every field can be corrected. The model
proposes; the human approves." §9's component table pins the model: "LLM (inspection spec) |
Gemini Flash-Lite API, structured output | Manual tolerance form | Tier 2" — the manual form is
the guaranteed fallback, not this story's competitor. C-16 (buyer setup page) already settles
which of the two is primary: its own acceptance criteria state the buyer page "takes... an
editable table in §7.4's shape... **A-03 later fills the same table and never bypasses it.**" So
the manual table is the guaranteed Tier-2 path; this story is an additive convenience that must
populate the exact same table, never a separate or bypassing one.

## Acceptance criteria

- Given free-text buyer prose, produces exactly the §7.4 JSON shape (`features:
  [{name, kind, tolerance_mm, critical}], assumptions: [...]`), with `kind` restricted to the
  proposal's four values and `tolerance_mm` a positive number — the same validation C-16 already
  specifies for manually typed entries.
- Output lands in C-16's existing editable table and never bypasses buyer confirmation — every
  field stays editable after parsing, matching "the model proposes, the human approves."
- Uses Gemini Flash-Lite with structured output (the pinned model per proposal §9), following
  A-01's precedent for pinning a stable model snapshot, never `-latest`, recorded as a decision.
- No cost, latency or accuracy is claimed for the parse (lane-wide rule); any quality claim needs
  a manual check, following A-01/A-10's pattern.

## Tests

Written alongside the parser: a handful of example prose inputs with known expected `features`/
`assumptions` shapes, checked for schema validity (not semantic correctness, which is the human
reviewer's job per the confirm-before-use rule); a structurally invalid model reply is rejected
rather than silently coerced into the table.

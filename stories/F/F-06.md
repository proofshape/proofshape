## Acceptance criteria

- At least three rigid objects, **one with a glossy or reflective surface**.
- Each shot on a printed ChArUco board, 25–30 frames, from a phone.
- At least one object shot under two different lighting conditions.
- Stored outside git behind a download script; the script and a checksum are committed, the images are not.
- A reference CAD model committed for at least one object.

## Why this matters

This is the single most important story in Phase 1. Because nobody is building the capture app yet, this set is the *only* source of real photographs for the entire backend push. Shooting it badly poisons two months of work and adds unnecessary rework of much of the project.

## Notes and decisions

2026-09-20: Golden capture evidence verified in the project's shared Google Drive. There are five
capture sets representing four physical shapes; `s-01` and `s-02` are the same reflective
metal padlock captured under visibly different lighting/background conditions. Frame counts are:
`s-01` 26, `s-02` 30, `s-03` 27, `s-04` 30, and `s-05` 29. Representative frames show
the printed ChArUco board under every object.

The remaining three shapes are a rounded rigid part (`s-03`), yellow triangular prism
(`s-04`), and red rectangular prism (`s-05`). The shared Drive also contains STL reference
models for `s-04` and `s-05`; the `s-04` triangular-prism STL is committed to this branch as
the required in-repo reference CAD.

The photograph bytes remain outside git. `fixtures/golden_capture_manifest.json` records the
Drive folder IDs and expected inventory; `fixtures/golden_capture_manifest.sha256` locks that
inventory; and `fixtures/download_golden_capture.sh` downloads the five sets, validates the
expected JPEG counts, and generates local per-image SHA-256 hashes after download.

This is more than the minimum capture requirement: four shapes instead compared to three planned, five capture sets,
one reflective object, and one object repeated under two lighting conditions.

2026-09-21: Review round two, addressed on this branch:

- The `.gitignore` exception for `fixtures/reference_cad/*.stl` didn't actually work — `fixtures/**`
  already excludes the `reference_cad` directory itself, so git never descended into it to apply
  the file-level negation, and the already-committed STL had only gone in via a force-add. Added
  `!fixtures/reference_cad/` ahead of the file pattern, plus `tests/test_fixture_ignore_rules.py`
  as a regression test.
- The Drive folders were not shared as "Anyone with the link," so `download_golden_capture.sh`
  failed with a 401 for anyone but the owner. Sharing fixed; re-verified live against the real
  `s-01` folder.
- The only committed checksum covered the manifest JSON, not the photograph bytes — a same-count
  file swap or corruption on Drive would have passed silently. Added a `content_sha256` per
  sample to the manifest (a hash over each sample's own per-file SHA-256 hashes, keyed by
  filename) computed from the actual Drive content, and the download script now verifies it
  after the count check.
- `sha256sum` isn't available on stock macOS, the project's documented native dev path
  (D-010/D-012). The script now prefers `sha256sum` and falls back to `shasum -a 256`.
- Added `tests/test_download_golden_capture.py`, mocking `gdown` on `PATH` so no network/Drive
  access is needed: covers the happy path, a frame-count mismatch, a content-hash mismatch (same
  count, different bytes), and the missing-`gdown` early exit. The content-hash-mismatch test is
  the regression check for the checksum gap above — it fails against the pre-fix script.
- Resynced with `main` after PR #21/#23 merged (F-05 Done, F-07 Ready); the merge briefly reverted
  F-05's row in `stories/README.md` to its pre-merge text, since this branch had been synced
  before that merge and both PRs touch nearby lines in the same table — resolved by hand, taking
  main's F-05/F-07 rows and this branch's F-06 row.

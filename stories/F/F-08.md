## Why this exists

The golden-capture downloader has four problems (#196):

- it prints "content hash verified" for a sample whose manifest entry has no hash;
- it loops over a hard-coded sample list instead of the manifest;
- it deletes a verified copy before downloading a new one;
- its test's reference hash orders lines differently from the script and only agrees by luck.

`.gitignore`'s photo rules are lowercase only. On Linux and the Lightning Studio, `IMG_0001.JPG`
or a `.HEIC` file outside `fixtures/` isn't ignored, and photographs must never be committed
(#197).

Since I-01 the image copies `inspect/inspection/`, but the image workflow's path filters don't
include it. An inspection-only merge therefore neither tests nor republishes the image (#198).

## Acceptance criteria

- The downloader fails when a sample has no hash, loops over the manifest, and downloads into a
  temporary folder that is swapped in only after verification.
- Photo patterns ignore uppercase extensions.
- `inspect/inspection/**` is in both of the image workflow's path filters.

## Tests

- the downloader's test pins a literal expected hash, or orders lines by path as the script does,
  and covers `main()`;
- the manifest is checked against its `.sha256`;
- uppercase photo names outside `fixtures/` are ignored;
- every Dockerfile `COPY` source is covered by the workflow's path filters.

All of these use fake files, as `tests/test_download_golden_capture.py` already does. No real
photographs, even temporarily.

pattern as `expected_count`/`expected_folder_id`/`expected_content_sha256`) drives `main()`'s loop

2026-11-02: Review of PR #226 caught four real gaps, one of them a genuine regression:

1. The no-hash case swapped the download in with a warning instead of failing — the AC's own
   wording ("The downloader fails when a sample has no hash") is explicit that it must fail.
   Fixed; the test that had asserted the old (wrong) behaviour now asserts the new one.
2. **Real bug introduced by this PR itself**: `done < <(sample_ids)` is a process substitution,
   whose exit status is invisible to both `set -e` and `pipefail`. Reviewer reproduced it with a
   manifest whose `captures` key was misspelled: `sample_ids` raised `KeyError`, the loop ran
   zero times, and `main` printed "Golden capture download complete" and exited 0 anyway — worse
   than the hardcoded-list bug this story was fixing. Fixed by capturing into a variable first
   (`samples="$(sample_ids)"`, kept on its own line so `local` doesn't mask the exit status, the
   same bash pitfall this fix itself could have reintroduced), with an explicit empty-list check.
   Two new tests drive this through `main()` end to end: a misspelled `captures` key, and an
   empty `captures: []`.
3. The story's own Tests section asked for "uppercase photo names outside `fixtures/` are
   ignored" as an automated test; it had only been checked by hand with `git check-ignore`.
   Added one to `tests/test_fixture_ignore_rules.py` — then found `core.ignorecase=true` (the
   default on this Mac, and common on Windows) makes `git check-ignore` match case-insensitively
   regardless of what `.gitignore` says, so the test passed even with the fix reverted. Forced
   `-c core.ignorecase=false` so the test is deterministic on any contributor's machine, not just
   by accident of CI running on Linux.
4. Non-blocking but real: a temp folder left behind by an older failed run of the same sample
   kept getting listed in `SHA256SUMS.local` forever, since nothing cleaned it up. Fixed by
   clearing `$dest.tmp.*` for that sample at the start of its own next attempt; new test
   reproduces a stale temp folder from a different PID and confirms a later successful run
   clears it.

All four mutation-tested the same way as the first round: each fails exactly the test(s) built
for it, nothing else (confirmed for #2 by reverting to the exact original `done < <(sample_ids)`
and watching both new end-to-end tests fail). Full suite 661 passed (was 657).

## Why this exists

The golden-capture downloader has four problems (#196):

- it prints "content hash verified" for a sample whose manifest entry has no hash;
- it loops over a hard-coded sample list instead of the manifest;
- it deletes a verified copy before downloading a new one;
- its test's reference hash orders lines differently from the script and only agrees by luck.

`.gitignore`'s photo rules are lowercase only. On Linux and the Lightning Studio, `IMG_0001.JPG`
or a `.HEIC` file outside `fixtures/` isn't ignored, and photographs must never be committed
(#197).

Since I-01 the image copies `inspect/inspection/`, but the image workflow's path filters don't
include it. An inspection-only merge therefore neither tests nor republishes the image (#198).

## Acceptance criteria

- The downloader fails when a sample has no hash, loops over the manifest, and downloads into a
  temporary folder that is swapped in only after verification.
- Photo patterns ignore uppercase extensions.
- `inspect/inspection/**` is in both of the image workflow's path filters.

## Tests

- the downloader's test pins a literal expected hash, or orders lines by path as the script does,
  and covers `main()`;
- the manifest is checked against its `.sha256`;
- uppercase photo names outside `fixtures/` are ignored;
- every Dockerfile `COPY` source is covered by the workflow's path filters.

All of these use fake files, as `tests/test_download_golden_capture.py` already does. No real
photographs, even temporarily.

2026-11-02: Implementation. All four downloader bugs fixed: the no-hash case now reports "no
content hash recorded" instead of a false "verified"; a new `sample_ids()` (same python-one-liner
pattern as `expected_count`/`expected_folder_id`/`expected_content_sha256`) drives `main()`'s loop
from the manifest instead of a hardcoded `s-01 s-02 s-03 s-04 s-05`; `download_sample` now
downloads into a sibling temp directory and only swaps it into `$dest` on success, leaving it in
place (not cleaned up) on any failure. The test file's own bug in the same issue — `_content_sha256`
sorted the combined `"<hash>  <name>"` strings, primarily by hash, while the real script sorts by
filename first and only then hashes each file — is fixed too; verified directly against the real
bash script with fixture data chosen so the two orders actually disagree (the fixed helper matches
the script's real hash exactly, the old one doesn't).

Added a test for a Tests-section item that had no test yet: the manifest is checked against its
committed `fixtures/golden_capture_manifest.sha256`.

`.gitignore` gets the uppercase variant of each photo pattern (`*.JPG`, `*.JPEG`, `*.PNG`,
`*.HEIC`); verified with `git check-ignore -v` against scratch uppercase filenames, not committed.
`inspect/inspection/**` added to both of `recon-image.yml`'s path filter lists; new test in
`tests/test_container.py` (reusing its existing `DOCKERFILE`/`_workflow` fixtures) parses every
directory `COPY` source and asserts each has a matching entry in both lists, so this can't drift
again the same way.

Folded in #106 (confirmed with the user): `gdown` was never declared as a dependency anywhere.
Added to `requirements.txt`, which `scripts/bootstrap_dev_env.sh` already installs from — checked
it installs cleanly with no conflicts against the project's other pins first.

Mutation-tested every fix by hand: the no-hash branch, the `sample_ids` loop (added a real

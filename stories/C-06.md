## Why this exists

`contracts/openapi.yaml`'s frozen `ErrorCode` enum already reserves `frame_rejected_blur`,
`frame_rejected_exposure` and `frame_rejected_duplicate` — R-14 returns them today when R-02/R-04
flag a problem server-side, but nothing on the client has ever computed them, so every frame
currently uploads sight-unseen. The proposal's own description of this feature ("blurry, dark or
duplicate frames are rejected on the phone with a reason... milliseconds, no server round trip")
is specifically about catching this *before* upload, not after — the opposite of what happens
today.

## Acceptance criteria

- Given a captured still as image data, a blur check (Laplacian variance) and an exposure check
  (histogram clipping) each return pass/fail and, on failure, which frozen code applies
  (`frame_rejected_blur` / `frame_rejected_exposure`), with the threshold as a named, overridable
  constant — not a magic number, matching this project's existing house style
  (`recon/uncertainty.py`'s `DEFAULT_SIGMA_DOWNGRADE_THRESHOLD_MM` is the precedent).
- A duplicate check compares a new still against the last *accepted* one (gyro delta plus image
  difference, per the proposal) and returns `frame_rejected_duplicate` when the phone hasn't
  moved enough for a second photo to be worth taking.
- All three checks are pure functions — image/gyro data in, pass-or-reason out — callable from
  synthetic test fixtures with no live camera and no device, so this story is buildable and fully
  testable independently of C-05 landing first.

## Tests

Fully automatable: synthetic `ImageData` fixtures (sharp vs. deliberately blurred, correctly vs.
over/under exposed, identical vs. genuinely different frames) drive every pass/fail branch. No
device-specific behavior is involved — unlike every other capture story so far, this one needs no
manual-check exception; say so explicitly rather than leaving the Tests section looking
incomplete.

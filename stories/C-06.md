## Why this exists

`contracts/openapi.yaml`'s frozen `ErrorCode` enum already reserves `frame_rejected_blur`,
`frame_rejected_exposure` and `frame_rejected_duplicate` — R-14 returns them today when R-02/R-04
flag a problem server-side, but nothing on the client has ever computed them, so every frame
currently uploads sight-unseen. The proposal's own description of this feature ("blurry, dark or
duplicate frames are rejected on the phone with a reason... milliseconds, no server round trip")
is specifically about catching this *before* upload, not after — the opposite of what happens
today.

## Acceptance criteria

- Given a captured still as image data, a blur check (Laplacian variance) and an exposure check
  (histogram clipping) each return pass/fail and, on failure, which frozen code applies
  (`frame_rejected_blur` / `frame_rejected_exposure`), with the threshold as a named, overridable
  constant — not a magic number, matching this project's existing house style
  (`recon/uncertainty.py`'s `DEFAULT_SIGMA_DOWNGRADE_THRESHOLD_MM` is the precedent).
- A duplicate check compares a new still against the last *accepted* one (gyro delta plus image
  difference, per the proposal) and returns `frame_rejected_duplicate` when the phone hasn't
  moved enough for a second photo to be worth taking.
- All three checks are pure functions — image/gyro data in, pass-or-reason out — callable from
  synthetic test fixtures with no live camera and no device, so this story is buildable and fully
  testable independently of C-05 landing first.

## Tests

Fully automatable: synthetic `ImageData` fixtures (sharp vs. deliberately blurred, correctly vs.
over/under exposed, identical vs. genuinely different frames) drive every pass/fail branch. No
device-specific behavior is involved — unlike every other capture story so far, this one needs no
manual-check exception; say so explicitly rather than leaving the Tests section looking
incomplete.

## Notes and decisions

2026-10-07: Implemented in `capture/src/frame_gate.ts` — `checkBlur` (Laplacian variance),
`checkExposure` (histogram clipping at the sensor extremes), `checkDuplicate` (gyro delta plus
image difference), plus a `FrameGateResult` type mirroring `api.ts`'s existing `ApiResult`
discriminated-union style (`{ok: true} | {ok: false, code, message}`) rather than inventing a
different shape.

**Not the DOM `ImageData` class.** Constructing a real one needs a browser or jsdom/happy-dom,
which would force an unnecessary environment dependency onto what's meant to be a fully
device-independent story. Instead, `FramePixels` is a minimal structural type
(`{data: Uint8ClampedArray, width, height}`) — a real `ImageData` from C-05's eventual canvas
satisfies it with no adapter needed (TypeScript structural typing; extra properties like
`colorSpace` are harmless), and tests construct plain object literals with no DOM at all. Tests
need no `// @vitest-environment happy-dom` docblock as a result — plain Node is enough.

**Duplicate check: AND, not OR, deliberately.** `checkDuplicate` only flags a frame as a duplicate
when *both* the gyro delta and the image difference are below their thresholds, not either alone.
A single signal is a weaker/noisier proxy — gyro can jitter slightly with the phone essentially
still, and two visually-near-identical frames can still represent a real small translation worth
keeping. Requiring both to agree before discarding a capture avoids false-positives that would
silently waste a real, useful frame, which matters more for a one-shot physical capture than being
slightly less aggressive about trimming genuine duplicates. Covered directly by a test that would
fail under OR logic but passes under AND (`"passes when the image changed meaningfully, even if
the gyro looks identical (AND, not OR)"`).

**Gyro delta is per-axis max, not a combined Euclidean distance.** alpha/beta/gamma are different
physical rotation axes; summing or norming them into one number would need a real
rotation-geometry justification this story doesn't need. `Math.max` of the three per-axis
absolute deltas is a simple, defensible "did any single axis move enough" measure instead.

All four `DEFAULT_*` thresholds (`DEFAULT_BLUR_VARIANCE_THRESHOLD = 100`,
`DEFAULT_EXPOSURE_CLIP_FRACTION = 0.05`, `DEFAULT_DUPLICATE_GYRO_DELTA_DEG = 2`,
`DEFAULT_DUPLICATE_IMAGE_DIFF_THRESHOLD = 5`) are starting assumptions, not measured/calibrated
values — same honesty this project already applies to `recon/uncertainty.py`'s
`DEFAULT_SIGMA_DOWNGRADE_THRESHOLD_MM`. Tuning against real capture data is follow-up work this
story was never going to do; each is overridable, tested explicitly (one test per function
confirms the override is actually read, not just accepted and ignored).

No manual-check section filled in below — correctly so, per this story's own Tests section: all
three checks are pure functions with no hardware or device dependency, the one capture story in
this thread that doesn't need one.

## Why this exists

The verdict's Pass and Fail rules scale σ by a factor `k` (Pass needs "σ ≤ tolerance / k"
in the proposal's verdict table), and `k` "is a planning prior of 3; the M3 measurement
sets it". Nothing has yet checked that R-10's σ predicts real error at all.

## Acceptance criteria

- Per-vertex σ (R-10, on the R-07 to R-10 mesh) is plotted against per-vertex measured error
  on the calipered specimens, for the board reference.
- `k` is chosen from that curve and recorded in `docs/decisions.md` with the curve. σ_floor
  is G-04's, not this story's.
- If σ doesn't predict error, that is reported as the result rather than worked around.

## Tests

`tests/test_cad_size_check.py`: `load_observed_surface_vertex_indices` (indices alongside
positions, same R-09 fully-Observed-face rule as `load_observed_surface_points`) and
`per_vertex_height_reliability` (pairs a vertex's own sigma with its *signed* height error on a
synthetic prism GLB, confirms a NaN sigma — fewer than 2 observations — is dropped, not
propagated; a dedicated regression test passes a non-level board plane and asserts the error
shifts by exactly the expected amount — review found every other test used a level `(0,0,0)`
plane, which would pass whether or not `board_plane` was actually used).
`tests/test_g07_reliability_curve.py`: `bin_by_sigma` (quantile binning), `measure_k` (recovers a
known linear `error = k*sigma` relationship, reads a near-zero correlation as near-zero rather
than a hardcoded "reliable" threshold, handles every sigma being 0), `pool_pairs` (signed error
in, absolute pooled error out), `specimen_offsets_mm`/`specimen_summary`/`scatter_pairs` (the
offset-vs-scatter decomposition review asked for), `_read_board_plane` (reads `tsdf_fusion.json`
correctly), `measure_k_against_sigma_floor` (clamps sigma to `sigma_floor` first -- a vertex
whose own sigma is already above the floor gives the same ratio `measure_k` would, one below it
gives a *larger* ratio than raw sigma would, exactly the `max(sigma, sigma_floor)` behavior
I-07/I-09's own formulas need, confirmed on review to give a materially different, larger k once
actually plugged into those formulas than the scatter-only figure did). The curve and the choice
of `k` are the written record in D-077, not a plotted image — no plotting library exists in
this repo and no story's own written record anywhere here is one; see D-077.

## Notes and decisions

- First drafted as G-06 on the unmerged `chore/proposal-revisions-2026-09-05` branch, with
  the 6 h estimate kept here; renumbered.
- Per-vertex distance to a prism overlaps I-06 (deviation computation). Keep it scoped to
  prisms and say so, so I-06 doesn't inherit it by accident. **Resolved by construction, not just
  a note:** I-06 compares against *CAD* ground truth (a posed STL, signed raycast distance);
  G-07 compares against *caliper* ground truth (one measured scalar per specimen, matching G-04's
  own lineage) — different ground-truth sources, so `per_vertex_height_reliability` shares no
  code with `inspect/inspection/deviation.py`'s `compute_deviation`.
- Reuses G-04's reconstruction runs for G-02's raw capture data, but **not** G-04's own
  measurement pipeline: G-04's `cad_size_check.build_report` produces one scalar height error per
  specimen (the median over a density-peak-detected top face on the raw point cloud), never
  per-vertex. R-10's sigma is indexed by the R-07→R-10 *mesh*'s own vertices, so this story had to
  run that mesh pipeline fresh (it had never been run locally before this story — not even R-10's
  `uncertainty_run`, for any specimen) and write new per-vertex code
  (`cad_size_check.per_vertex_height_reliability`) rather than reuse `build_report`.
- **A real bug found and fixed, caught by the numbers coming out wrong (10x G-04's own floor),
  not by review:** the board plane must be the one R-07's own TSDF fusion already fit and
  re-anchored (`mesh/tsdf_fusion.json`'s `board_surface`), not re-fit from the served mesh's own
  vertices — that mesh is the segmented-out *part* only, with few or no real board-level points
  of its own to fit a plane from. See D-077 and the script's own module docstring for the full
  account.
- **Review round two (PR #367, @TabeenRaoof and @mbj1994) found two more real problems, both
  independently reproduced here before touching any code:** (1) the first version's `g02_02`
  figure came from a stale cached `metric_alignment.json` predating R-38, not an "unpatched code
  path" as first claimed — `ensure_pipeline` now regenerates the alignment and rebuilds the whole
  mesh pipeline fresh, every run, never trusting a cached file. (2) the pooled correlation mixed
  each specimen's own systematic offset with its vertex-level scatter, which is what made it come
  out negative — sigma cannot see a whole-part offset (that is sigma_floor's job, D-073), and
  removing each specimen's own offset before pooling reverses the sign to a real, if modest,
  positive relationship. A progress-log note from P-24 asks for both reviewers on G-07's method
  before measuring; this round got both.
- **The corrected result is a modest, real, positive relationship, not a negative one:** once
  each specimen's offset is removed, per-vertex sigma vs. scatter gives Pearson r = +0.24 (raw
  sigma) / +0.30 (sigma normalized by √residual_count, not itself proposed as `k`), with mean
  scatter rising across most sigma bins — far below the planning prior of 3, because sigma
  overstates real per-vertex scatter by roughly 4x in this data, not because sigma fails to
  predict it.
- **A third real problem, found on a second pass of review (@TabeenRaoof): the scatter-only k
  and the formulas I-07/I-09 actually use don't match.** The scatter relationship above answers
  this story's own research question, but I-07's Fail/Pass rows and I-09's Unverifiable row all
  apply `k` to *total* deviation (offset included) against `max(sigma, sigma_floor)`, never to
  scatter alone against raw sigma. Checked directly: a `k` of 0.25 in I-07's Fail condition is
  violated by 50% of this run's vertices, 100% on the two specimens with the largest offsets.
  **Two numbers, not one:** k ≈ 0.25 (scatter-only, this story's own research answer) and
  **k ≈ 0.70** (`consumable_k_estimate`, measured 0.688 — total error against
  `max(sigma, sigma_floor)`, the number I-07/I-09 actually cite). Both provisional; I-09 still
  has a residual gap even at 0.70 (`0.70 × 0.86 = 0.60mm`, below `s-04`'s own 0.73mm offset) —
  flagged in `I-09.md`, not resolved here. Full numbers, the offset/scatter table, and every
  caveat are in D-077.
- **Also found on the same review pass:** the script used to overwrite
  `fixtures/data/recon_runs/<id>/metric_alignment.json` and `rmtree` its `mesh/` in place —
  risking silently deleting another story's own cached R-07 outputs on a machine that keeps
  them there. Fixed: every regenerated output now goes to this story's own
  `fixtures/data/g07_reliability/<specimen_id>/`; `RECON_RUN_ROOT` is only ever read, never
  written to.
- σ_floor is G-04's (0.86 mm, D-073), not re-derived here, per this story's own acceptance
  criteria.

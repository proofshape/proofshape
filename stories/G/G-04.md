## Why this exists

The critical path runs through this story. M3 reads "σ_floor is a measured number. Every
demo tolerance is set from it" (sprint plan S3). The verdict logic can't set tolerances
without it (I-07, I-09), and R-16 needs a measured figure to judge R-04's known-size
comparison against.

## Acceptance criteria

- The method is written below before anything is computed: per-feature error is
  reconstruction minus caliper (G-03, G-06), not minus CAD; scale error is separated from
  shape error by the similarity fit; each edge's bias is reported apart from the spread
  (R-22's Finding 2); mean and 95th-percentile error for the board reference (proposal
  §12); how σ_floor follows from them; and which figure R-16 is to judge against.
- The chain runs on every G-08 capture: R-01 and R-02, then R-04 with R-23's board anchor,
  then `recon/cad_size_check.py` extended to take caliper truth and G-06's measured board
  pitch. The confidence filter used is named (D-045).
- The result is recorded as a decision in `docs/decisions.md`, with its conditions: landscape
  phone stills, the board reference, R-01's raw point cloud rather than the R-07/R-08 mesh.
  It says it doesn't yet hold for app capture or for the sheet and card references (G-10):
  σ_floor is defined per reference (glossary), and this is the board reference's.
- If σ_floor comes out above 3 mm, that is reported as the result and the proposal's M3
  fallback applies ("demo tolerances move up and the Unverifiable path becomes the
  story"), rather than the method being tuned until the number looks better.

### 2026-11-16: the method, written before computing anything (criterion 1)

**Per-feature error is reconstruction minus caliper, not CAD.** `recon/cad_size_check.py`'s
`measure_prism` already measures each footprint edge's length and the part's height from the
reconstructed point cloud, independent of CAD. New functions `match_caliper_edge_truth`/
`caliper_edge_errors` substitute G-03's caliper `mean_mm` for the CAD length as the truth each
measured edge is compared against, matched by CAD edge **length**, not by a specific edge's
identity — because a caliper reading can represent every edge of one length class at once (e.g.
G-03's rectangles: "this is the length of the two long sides"). Height is compared the same way,
directly, since there is only one height per specimen.

**Scale error is separated from shape error by the similarity fit.** R-04/R-23's rigid similarity
transform carries the reconstruction's overall scale; `measure_prism`'s own 2-D rigid fit
(`_fit_rigid_2d`) deliberately does *not* re-fit scale on top of it, so a part's own residual
per-edge bias is shape error specific to that part, not scale error already captured by the
board-ruler check (`measure_board_scale`) and by `*_ratio_over_board_scale` in the existing
report. G-06's board is anisotropic (+0.10% across vs +0.46% down from D-034's nominal 20 mm
squares — one scale factor cannot represent this), so a new, separately-scoped function
(`apply_board_pitch_correction`, inside `cad_size_check.py` only, never touching the shared
`recon/metric_alignment.py`) corrects the board-frame cloud's x/y for G-06's real measured pitch
before any edge or height is measured, so that known anisotropy isn't measured into the floor as
if it were part-specific shape error.

**Bias apart from spread (R-22 Finding 2).** Each edge's `caliper_error_mm` (bias:
measured − truth) is reported alongside the existing `perpendicular_spread_mm` (spread: p90−p10
of the edge's own inlier points), never merged into one number.

**Which specimens' edges are usable — originally thought, then corrected on review (see the
results below):** my first pass here reasoned that `g02_01` (square), `g02_04` (near-regular
pentagon) and `g02_05` (near-regular hexagon) needed excluding because their caliper readings
are ambiguous (several different physical-side readings for one CAD length class, with no
record of which numbered/lettered side is which reconstructed edge — a real G-08 gap, and
`match_caliper_edge_truth`'s `conflict_atol_mm` logic still correctly detects it). **That
reasoning was incomplete: review on PR #348 showed every specimen's edges are unusable right
now**, for a more fundamental reason than orientation — see the results section.

**Mean and 95th-percentile error, and how σ_floor follows (Proposal §12).** `mean_error_mm` is
the signed mean (systematic bias) of every included feature's `caliper_error_mm`; `sigma_floor_mm`
is its 95th percentile (nearest-rank) of absolute error — the proposal states both figures and
says σ_floor "feeds the pre-check" from them; this story fixes exactly how. **Which features get
pooled changed on review — see the results below.**

**What R-16 judges against:** the resulting `sigma_floor_mm` figure, for the board reference
only (confirmed below against the M3 fallback before being recorded) — **and, as it turned out,
only for out-of-plane (height) comparisons; see the corrected results below for why in-plane
ones judge as insufficient-evidence instead.**

### 2026-11-16: the real run, first pass — σ_floor = 7.52 mm (superseded below, same day)

Ran `scripts/measure_g04_board_error.py` for real against all six G-02 specimens (device `mps`,
on the M2 Max). Full evidence: `fixtures/data/g04_board_error/g04-board-error-evidence.json`
(owner-local, gitignored, cited by path — X-02's own precedent).

Found `g02_02`'s board-anchored alignment (R-23) didn't converge — board scale 0.8311 against
0.9947–0.9984 everywhere else, confirmed independently of the caliper comparison before touching
its numbers — and excluded it. Pooled the remaining 12 edge+height features into mean −1.11 mm,
σ_floor (p95 of absolute error) = 7.52 mm, and recorded it as **D-073**, opened as PR #348.

### 2026-11-16: corrected on review (@TabeenRaoof, PR #348) — σ_floor = 0.86 mm, from heights only

The review re-ran the identical chain on the identical photos and got **different edge numbers**
— board scale agreed to 4 decimals, individual edges did not. It traced this to two real,
pre-existing bugs this story's extension newly leans on, neither invented by the review:

1. **`measure_prism`'s edge length reads a perfect, noiseless prism about 4% short of its true
   corner-to-corner length**, by construction (its 2nd–98th-percentile point extent isn't the
   same convention a caliper uses). Confirmed by densely sampling each G-02 CAD's own walls with
   no noise and no reconstruction at all, then running `measure_prism` on that alone.
2. **`_fit_rigid_2d`'s exhaustive discrete pose search lands in a visibly wrong pose** for the
   square (`g02_01`) and the triangle (`g02_03`), confirmed against the point cloud directly, and
   isn't stable run to run on identical input — a tiny reconstruction difference can flip which
   discrete candidate wins, landing a *qualitatively* different pose, not a numerically close one.

Both make every specimen's edge numbers untrustworthy right now, not only the symmetric/near-
regular ones I'd originally flagged for a narrower reason (caliper-reading ambiguity, which is
real but not the dominant problem). Fixing either — corner-to-corner edge measurement via fitted-
wall-line intersection, and a pose search that can't land wrong on these shapes — is real,
open-ended algorithm work, filed as **R-37**, not attempted here. Per the review's own suggested
path: report what can actually be trusted, and record the gap plainly, rather than ship a number
built on a known fitting artifact.

**Height has no such dependency** (computed from the top-face point-density peak, before
`_fit_rigid_2d` ever runs) and is the only feature trusted now. Re-ran the aggregation (no VGGT
re-run needed — same cached reconstructions) pooling only the 5 included specimens' heights:
mean **+0.03 mm**, **σ_floor_mm (p95, nearest-rank) = 0.86 mm** — equal to the max here, since
with n = 5 that's what nearest-rank p95 *is*, stated plainly rather than implied to be finer-
grained than 5 points support. **This is provisional and likely optimistic** (no edges, small
n), not a clean pass — recorded as the corrected **D-073**, which also names `g02_02`'s precise
root cause (one frame, `IMG_4665`, 124.8 mm median corner residual against single digits
everywhere else; R-23's solve has no per-frame rejection and `metric_alignment.main` prints
`PASS` regardless) and files its follow-up as **R-38**.

**0.86 mm covers out-of-plane (height) features on the board reference only — stated precisely
because R-16 and I-07 read this literally, not just loosely.** In-plane features (edge lengths,
wall positions) have **no measured floor yet**, pending R-37: R-16 judges in-plane comparisons
as insufficient-evidence, not against 0.86 mm; I-07's `max(σ, σ_floor)` doesn't apply 0.86 to
in-plane deviation either. "Does not trigger M3's fallback" holds for height tolerances only.

**Per this story's own instruction, restated accurately this time:** 0.86 mm, from heights only,
does not trigger the M3 fallback on the evidence that can actually be trusted today — but the
edge gap is real, open, filed as R-37 (edge measurement) and R-38 (R-23's per-frame robustness),
not quietly dropped.

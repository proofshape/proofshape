## Why this exists

The critical path runs through this story. M3 reads "σ_floor is a measured number. Every
demo tolerance is set from it" (sprint plan S3). The verdict logic can't set tolerances
without it (I-07, I-09), and R-16 needs a measured figure to judge R-04's known-size
comparison against.

## Acceptance criteria

- The method is written below before anything is computed: per-feature error is
  reconstruction minus caliper (G-03, G-06), not minus CAD; scale error is separated from
  shape error by the similarity fit; each edge's bias is reported apart from the spread
  (R-22's Finding 2); mean and 95th-percentile error for the board reference (proposal
  §12); how σ_floor follows from them; and which figure R-16 is to judge against.
- The chain runs on every G-08 capture: R-01 and R-02, then R-04 with R-23's board anchor,
  then `recon/cad_size_check.py` extended to take caliper truth and G-06's measured board
  pitch. The confidence filter used is named (D-045).
- The result is recorded as a decision in `docs/decisions.md`, with its conditions: landscape
  phone stills, the board reference, R-01's raw point cloud rather than the R-07/R-08 mesh.
  It says it doesn't yet hold for app capture or for the sheet and card references (G-10):
  σ_floor is defined per reference (glossary), and this is the board reference's.
- If σ_floor comes out above 3 mm, that is reported as the result and the proposal's M3
  fallback applies ("demo tolerances move up and the Unverifiable path becomes the
  story"), rather than the method being tuned until the number looks better.

### 2026-11-16: the method, written before computing anything (criterion 1)

**Per-feature error is reconstruction minus caliper, not CAD.** `recon/cad_size_check.py`'s
`measure_prism` already measures each footprint edge's length and the part's height from the
reconstructed point cloud, independent of CAD. New functions `match_caliper_edge_truth`/
`caliper_edge_errors` substitute G-03's caliper `mean_mm` for the CAD length as the truth each
measured edge is compared against, matched by CAD edge **length**, not by a specific edge's
identity — because a caliper reading can represent every edge of one length class at once (e.g.
G-03's rectangles: "this is the length of the two long sides"). Height is compared the same way,
directly, since there is only one height per specimen.

**Scale error is separated from shape error by the similarity fit.** R-04/R-23's rigid similarity
transform carries the reconstruction's overall scale; `measure_prism`'s own 2-D rigid fit
(`_fit_rigid_2d`) deliberately does *not* re-fit scale on top of it, so a part's own residual
per-edge bias is shape error specific to that part, not scale error already captured by the
board-ruler check (`measure_board_scale`) and by `*_ratio_over_board_scale` in the existing
report. G-06's board is anisotropic (+0.10% across vs +0.46% down from D-034's nominal 20 mm
squares — one scale factor cannot represent this), so a new, separately-scoped function
(`apply_board_pitch_correction`, inside `cad_size_check.py` only, never touching the shared
`recon/metric_alignment.py`) corrects the board-frame cloud's x/y for G-06's real measured pitch
before any edge or height is measured, so that known anisotropy isn't measured into the floor as
if it were part-specific shape error.

**Bias apart from spread (R-22 Finding 2).** Each edge's `caliper_error_mm` (bias:
measured − truth) is reported alongside the existing `perpendicular_spread_mm` (spread: p90−p10
of the edge's own inlier points), never merged into one number.

**Which specimens' edges are usable, and why — found while grounding this, not assumed:**
caliper truth can only be assigned to a prism edge when every caliper feature matching that
edge's CAD length agrees (within 0.05 mm). `g02_01` (square), `g02_04` (near-regular pentagon)
and `g02_05` (near-regular hexagon) each have several *different* readings for edges the CAD
treats as one length class (e.g. `g02_01`'s two sides read 19.9 mm and 19.81 mm), with no record
of which numbered/lettered physical side is which reconstructed edge — G-08 never recorded that
mapping, and `measure_prism`'s fit is itself undetermined for a symmetric/near-regular footprint
(it can land any of several ways). Those three specimens' **edges** are excluded from the
aggregate for this reason, not guessed; their **height** feature has no such ambiguity and stays
in. `g02_02`, `g02_03` (the flagged triangle anomaly — included, not excluded, per this story's
own "report it, don't tune it away" instruction) and `g02_06` were expected to contribute full
edge-level data; **`g02_02` turned out, once run for real, to need its own exclusion for a
different and more fundamental reason — see the results below.**

**Mean and 95th-percentile error, and how σ_floor follows (Proposal §12).** Every included edge
and height `caliper_error_mm`, pooled across all six specimens, gives one error distribution.
`mean_error_mm` is its signed mean (the systematic bias). **σ_floor_mm is defined, as this
story's own concrete choice, as the 95th percentile of `|caliper_error_mm|`** across that pooled
distribution — the proposal states both figures and says σ_floor "feeds the pre-check" from
them; this story fixes exactly how.

**What R-16 judges against:** the resulting `sigma_floor_mm` figure, for the board reference
only (confirmed below against the M3 fallback before being recorded).

### 2026-11-16: the real run — σ_floor = 7.52 mm, above the 3 mm line (criteria 2-4)

Ran `scripts/measure_g04_board_error.py` for real against all six G-02 specimens (device `mps`,
on the M2 Max — slower than the estimate expected for `g02_04`/`g02_05`/`g02_06`, apparently
memory pressure across one long-lived process running VGGT six times in a row, not investigated
further here since the numbers themselves came out fine). Full evidence:
`fixtures/data/g04_board_error/g04-board-error-evidence.json` (owner-local, gitignored, cited by
path — X-02's own precedent).

**A real, unplanned finding before trusting any number:** `g02_02`'s board-anchored alignment
(R-23) did not converge for its capture — board scale 0.8311 (every other specimen: 0.9947 to
0.9984, matching R-23's own documented 0.9971–0.9994 real-data range) with an RMS residual of
21.3 mm against 2–4 mm everywhere else. Checked independently of the caliper comparison (via the
board-ruler diagnostic alone) before deciding anything — this is the alignment failing for one
capture, not a finding about the part, so `g02_02` is excluded entirely (edges and height) from
the aggregate, with the reason recorded in the evidence file per specimen, not silently dropped.
Its own raw/legacy camera-centre scale (0.951) is in the normal *legacy* range, so the fault is
specific to R-23's board-anchored solve for this one capture — flagged, not investigated further;
no story currently owns it.

**Result, pooled over the 12 remaining features (one height each from `g02_01`/`g02_04`/`g02_05`,
three edges + height from `g02_03`, four edges + height from `g02_06`):** mean error **−1.11 mm**,
**σ_floor_mm (95th percentile of absolute error) = 7.52 mm** — set by `g02_03`'s own edge_index 0
(−7.52 mm). Recorded as **D-073** in `docs/decisions.md`, with the full per-specimen table, the
pitch-correction scoping note, and the g02_02/g02_03 findings.

**Per this story's own instruction:** 7.52 mm is reported as the result, not tuned down. The
proposal's M3 fallback applies — demo tolerances move up, the Unverifiable path becomes the
working path for the board reference, until something narrows `g02_03`'s own inconsistency
(−7.5/+9.7/−3.0 mm across its three edges, far larger than the ~1 mm caliper-only anomaly G-03
already flagged — whether this is print-specific, an acute-angle reconstruction artifact, or
real is not determined here).

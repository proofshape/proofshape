## Why this exists

C-01, C-02 and C-03 each built their own isolated page section on purpose, so none would block
on touching another's already-shipped code: `#app` (the upload-page stub), `#camera-app` (a
one-shot preview), `#gyro-app` (a standalone reading display). That isolation was right for
proving each contract/permission independently, but it isn't the real app — right now there is
no single flow where creating a session and granting both permissions feed into one piece of
state. `capture/index.html`'s own comment already says what's missing: C-04 is what "wires the
live reading through." Nothing past this point (C-05's continuous capture, C-06's gate) has
anywhere real to plug into without it.

## Acceptance criteria

- One screen creates a session (reusing `api.ts`'s `createSession`), then requests camera and
  gyro permission together (reusing `camera.ts`/`gyro.ts`'s existing logic), replacing
  `index.html`'s three separate `#app`/`#camera-app`/`#gyro-app` demo sections with one real flow.
- App-level state — the current session id, and whether camera/gyro permission is granted — lives
  in one place that C-05 onward reads and writes, not duplicated per-module globals the way the
  three isolated demos currently are.
- If either permission is denied, the shell surfaces the existing C-02/C-03 error messaging and
  does not silently let the user continue to a broken next step.

## Tests

Composition and state-transition logic (which function gets called when, what state results, how
a denial propagates) is fully unit-testable with the same happy-dom `getUserMedia`/
`DeviceOrientationEvent` mocking already established in `camera.test.ts`/`gyro.test.ts` — this
story doesn't add a new hardware dependency, it wires together two permissions already proven
individually on a real device in C-02/C-03.

What *is* new on a real device: requesting both permissions back-to-back in one flow, which
neither C-02 nor C-03 tested in combination. Manual check (device, iOS/Safari version, steps,
result) for that combined sequence specifically — not re-verifying either permission alone.

## Notes and decisions

Written while working. What you tried, what surprised you, what you chose and why. If a decision
here will govern later work, also add it to `docs/decisions.md` with a number.

2026-10-08: Implemented as `capture/src/shell.ts` (`mountAppShell`), plus one new exported
function each on `camera.ts` (`requestCameraPermission`) and `gyro.ts` (`requestGyroPermission`)
— reusing their existing logic (`isGetUserMediaSupported`/`REAR_CAMERA_CONSTRAINTS`/
`describeCameraError`, `isOrientationPermissionRequestNeeded`/`describeOrientationError`) rather
than re-implementing it in `shell.ts`, which is what the acceptance criteria's "reusing
camera.ts's/gyro.ts's existing logic" actually asks for. `mountCameraCheck`/`mountGyroCheck`/
`page.ts` and their own tests are untouched — only `index.html`/`main.ts` now mount the new shell
instead of the three old demos.

**A real technical constraint the acceptance criteria doesn't spell out:** iOS requires
`getUserMedia`/`requestPermission()` to be called synchronously inside the click handler, with no
prior `await` — but the criteria describes "creates a session, *then* requests permission," and
session creation is an awaited network call. Literally awaiting it first would insert a microtask
gap before the gesture-requiring calls. Resolved by starting all three — `createSession`, the
camera request, the gyro request — synchronously in the same handler before awaiting any of them,
then awaiting each in turn to update the UI as it resolves. Verified, not just reasoned about: a
regression test calls `button.click()` with no `await` in the test and asserts both permission
mocks were already invoked, the same technique `gyro.test.ts` already uses for its own version of
this property.

**Stops the camera stream immediately after confirming it opened**, rather than holding it open.
This story only needs to prove/record that permission was granted; C-05 ("Live camera") is
explicitly the story responsible for keeping a stream running, and holding one open here with
nothing consuming it would be the same "camera stays on" bug C-05's own story calls out, just
arriving one story early. Re-requesting in C-05 costs nothing extra — once granted, the browser
doesn't re-prompt.

**A `deviceorientation` reading with any `null` component is dropped, not coerced to `0`.** The
DOM event reports `number | null` per axis; `Gyro` requires `number`. Writing a fabricated `0`
into shared app state would misreport a real orientation as "no tilt," which nothing downstream
could tell apart from a genuine zero reading.

**`AppState` is a plain object created fresh per `mountAppShell` call, not a module-level
singleton.** `gyro.ts`'s own `listening` flag was deliberately moved from module-level to
closure-scoped during C-03, specifically because a module-level mutable flag leaked across
repeated mounts in tests — `AppState` avoids that same class of bug by construction. `main.ts`
calls `mountAppShell` without capturing the returned state (nothing consumes it until C-05
exists, and binding an unused `const` would fail `noUnusedLocals` for no benefit); the function
still returns it, for tests now and for whenever C-05 is wired in.

**A real environment bug caught while writing the tests, not assumed:** `requestCameraPermission`
calls `stream.getTracks()` to stop the stream, but happy-dom's own `MediaStream` class doesn't
implement `getTracks()` — `new MediaStream()` (the pattern `camera.test.ts` already uses
successfully, since `mountCameraCheck` never calls `getTracks()`) threw
`stream.getTracks is not a function` the first time this story's tests actually exercised that
path. Fixed by giving the test a plain object with a working `getTracks()` instead of relying on
happy-dom's incomplete real class — the same class of "happy-dom has real but incomplete DOM
behaviour" gap this project has run into before (PR #72's `getUserMedia`/`MediaStream`, C-03's
`DeviceOrientationEvent` constructor).

**A second, separate infrastructure bug, also caught by the tests rather than assumed:**
`shell.test.ts` needed the same fixed-port `happy-dom` + real contract-stub pattern
`page.test.ts` already established (same-origin fetches). Running both together produced a real
`EADDRINUSE` on the shared port — Vitest runs test files in parallel by default, and two files
both trying to bind the one fixed port at the same time collide rather than queue. Fixed with
`fileParallelism: false` in `vite.config.ts`, and its comment updated (it previously said, now
incorrectly, that only `page.test.ts` used `happy-dom` at all — camera/gyro/dom's own test files
already did too, just never needed to fetch anything, so the collision was latent until this
story's test file became the second one that does). A related, narrower race also surfaced: this
story's own synchronous-call regression test fires a real (if deliberately unawaited by the test)
`createSession` fetch as a side effect, which could still be in flight when `afterEach` tore the
stub server down — fixed by having that test wait for the session status to populate before
finishing, even though the test itself doesn't care about the session result.

Not filed as a `docs/decisions.md` entry — these are test-infrastructure/implementation choices
local to this story, not project-wide rules future stories need to look up.

## Why this exists

`recon/provenance.py` already bakes vertex colours into the GLB — white for Observed, grey for
Unobserved, by that module's own documented convention — but nothing on the client says what
those colours mean, and white against light grey is hard to tell apart once the model is lit.
The proposal's "observed/unobserved map" is supposed to read as a map, not as raw, unexplained
geometry.

## Acceptance criteria

- The viewer remaps the GLB's baked vertex colours to a visually distinct display palette (not
  the near-white/grey values as received) and a legend in the UI names which colour means what.
- The remap's source colours are a TypeScript constant kept equal to `recon/provenance.py`'s
  `OBSERVED_COLOR` / `UNOBSERVED_COLOR` — a test fails if a future change to those Python values
  isn't mirrored here, rather than the client guessing independently what the server sends.
- A third, visually distinct slot for `inferred` is reserved in the palette and legend now, even
  though nothing produces it yet (generative shape completion, §6.6, is Tier 2 and not built) —
  so this story does not have to be revisited when it lands.

## Tests

A pure function mapping a given vertex-colour buffer to the display palette: Observed's exact
source RGB maps to its display colour, Unobserved's does too, and anything else — including a
future `inferred` value — falls into a named "unknown" case rather than being silently
misrendered. The drift-guard test against `recon/provenance.py`'s committed constants, same
pattern as R-15's `PROOFSHAPE_PUBLIC_BASE_URL` guard. No manual-check exception beyond what C-11
already covers — on-screen legibility is a one-line addition to that existing device check, not a
new device dependency.

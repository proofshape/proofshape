## Acceptance criteria

- One Dockerfile builds the service.
- One command deploys it through the Lightning deployment/public-endpoint path and it answers over HTTPS/TLS (D-036).
- A second member follows the runbook successfully without help.

## Notes and decisions

2026-09-17: D-036 replaces the RunPod-specific deployment assumption with Lightning. This does
not relax the story: the deployed service still has to be reachable securely over HTTPS/TLS and
a second member still has to reproduce the runbook.

2026-10-05: Implementation (PR 1 of 2). Planned with the team's answers on three open forks,
recorded as D-042: the image is published on every merge but started by hand; the endpoint is
token-gated; the service runs on demand. The runbook is the `R-15` section of `recon/README.md`.

What was built:
- **`Dockerfile`**: base `pytorch/pytorch:2.8.0-cuda12.8-cudnn9-runtime`, pinned by digest. That is
  the same torch 2.8.0+cu128 the Studio was validated on, and torch is never reinstalled.
- **`scripts/container_entrypoint.sh`**: fetches the weights at start-up, then runs one uvicorn
  worker.
- **`.dockerignore`**.
- **`.github/workflows/recon-image.yml`**: build, then smoke-test the container. On PRs it stops
  there; on `main` it also publishes to GHCR.
- **`.github/workflows/deploy-recon.yml`**: manual, `main` only. It calls
  **`scripts/deploy_recon.py`**.
- **`scripts/smoke_r14.py`** gained a `--base-url` mode. One shared `drive_session` now serves both
  the in-process R-14 check and the deployed one.

Things exploration and building turned up that weren't in the story:
- **One replica, one worker is required for correctness.** R-14's `SessionStore` keeps sessions on
  one container's local disk behind an in-process lock. A second replica would answer
  `session_not_found`. The deploy script hard-codes `--replicas 1`, and a test pins it.
- **A real HTTPS bug, caught before any deploy.** `getReconstruction`'s `glb_url` comes from
  `request.url_for`, an absolute URL built from the scheme uvicorn sees. TLS ends at Lightning's
  proxy, and by default uvicorn only trusts `X-Forwarded-Proto` from 127.0.0.1. So phones would
  have been handed an `http://` model link from an `https://` service. I checked both ways in the
  built container: with `--forwarded-allow-ips '*'`, a request carrying `X-Forwarded-Proto: https`
  got an `https://` `glb_url`. Without the flag, the same request got `http://`. The entrypoint now
  sets it, and the remote smoke fails if `glb_url`'s scheme differs from the base URL's.
- **The VGGT package depends on the non-headless `opencv-python`.** That clashes with our pinned
  `opencv-python-headless`; both provide `cv2`, and the non-headless one needs `libGL`. The image
  removes it and reinstalls the pinned headless build. Checked in the built image: only
  `opencv-python-headless 4.11.0.86` is present.
- **No new route for health checks.** `test_public_operation_ids_match_the_frozen_contract`
  requires exactly the five frozen operations. Readiness polls Lightning's own replica status, and
  CI waits on FastAPI's built-in `/openapi.json`.
- **The Lightning CLI was checked rather than guessed.** Lightning's docs site wouldn't render
  outside a browser, so every flag `deploy_recon.py` uses (`--token-auth`, `--replicas`,
  `--max-runtime`, `update`, `delete --yes`, `inspect`) was confirmed against `lightning deployment
  … --help` from the pinned `lightning-sdk==2026.10.1`. So were its auth variables
  (`LIGHTNING_USER_ID` + `LIGHTNING_API_KEY`) and the `inspect` JSON fields
  (`status.urls`, `status.ready_replicas`).

Verified locally (Apple Silicon, image built for `linux/amd64` under emulation, 4.49 GB):
- **Inside the image:** Python 3.11.13, torch 2.8.0+cu128, numpy 1.26.4, and `vggt`, `cv2` and
  `recon.service` all import. It runs as a non-root user.
- **Through the real entrypoint, with prefetch off:** `POST /v1/sessions` → 201.
- **Remote smoke against that container:** all 30 real `s-04` frames uploaded, then reconstruction
  failed with the explicit "PyTorch cannot see a GPU" message, as expected with no GPU.
- **Digest and label extraction in `deploy-recon.yml`:** checked against both a multi-arch and a
  single-arch public image.
- **Mutation checks:** each guarded behaviour was broken in turn and a test failed every time. The
  mutations were: a second worker, removing proxy trust, changing the port, dropping `.env` from
  `.dockerignore`, unpinning the base, two replicas, removing the main-only guard from start or
  stop, printing the token, accepting `http://`, dropping the `glb_url` check, and not polling. The
  main-guard mutation first survived, because the test failed for an unrelated reason (a missing
  variable). I fixed the test and the mutation is now caught.

**Still open, and why this PR doesn't close the story.** `workflow_dispatch` workflows can only
run once they're on `main`, and D-013 forbids deploying from anything else. So criteria 2 and 3
can only be shown after this merges. That is the same split R-13 used. After merge:
1. An admin does the runbook's one-time setup. The Lightning key comes from whoever owns the
   teamspace (@mbj1994 set it up in F-05).
2. Start the deployment and fill in the manual check below.
3. A second member follows the runbook unaided.
4. The close-out PR sets `Done` per D-038.

2026-10-06: @dalwalyk's review of PR 1 caught a real bug: `inspect_deployment` returned `None`
(meaning "deployment doesn't exist") for *any* non-zero exit from `lightning deployment inspect`,
not only a genuine absence. `stop()` used that to decide whether to call `delete`, so a transient
inspect failure (auth hiccup, network blip, rate limit) would have made `stop()` print "nothing to
stop" and return success while the GPU kept running and billing. Reproduced live, not just
reasoned about: running the real CLI against an unconfigured credential set exits 1 with "No
Lightning credentials are available" — the exact same exit code a genuine not-found produces.
Fixed by matching `inspect_deployment`'s stderr against the specific message
`resolve_deployment` in `lightning_sdk`'s CLI raises for an unknown name ("was not found");
anything else now raises `DeployError` instead of being read as absence. Two new tests cover it,
including the exact bug scenario (a broken inspect during `stop()`); both fail without the fix
and the mutation (reverting to the old blanket `if returncode != 0: return None`) was confirmed to
break only those two tests.

Also fixed, from the same review (non-blocking, but cheap): `recon-image.yml`'s smoke-test step
had an unguarded `curl` in its status capture. Under Actions' default `set -eo pipefail`, a
connection failure there (e.g. the container crashing before it answers) would have tripped
`errexit` before reaching the `docker logs` diagnostic right below it. Added `|| status=curl-failed`
so the failure path always runs.

2026-10-06/07: First real deploy. Two things this story's own notes above correctly predicted as
unobserved both turned out to matter:

- **GHCR package visibility is gated by an org-level policy, not just the package's own
  settings.** The package page's "Change visibility → Public" option was disabled with "Setting
  is disabled by organization administrators" — the actual control is a separate org setting
  (`https://github.com/organizations/<org>/settings/packages`, "Package creation" visibility
  checkboxes), not anything on the package itself. Not in this story's runbook originally; added
  to `recon/README.md`'s one-time setup now that it's been hit once.
- **The deployed endpoint was unreachable for roughly a day after `R-15 DEPLOY: READY`** — TCP
  connected, but every TLS handshake was reset instantly (`curl: (35) Recv failure: Connection
  reset by peer`, confirmed with `openssl s_client` too, so not a client-side quirk). Lightning's
  dashboard showed the replica itself healthy and fully started (`Uvicorn running on
  http://0.0.0.0:8000` in its own logs) the whole time — the problem was entirely at the public
  ingress, not the container. Root cause: the org's Lightning credits (5.00) were sitting
  entirely **unallocated** ("Credits across teamspaces: 0"), and public endpoint routing is
  apparently gated on the teamspace actually holding an allocation, even though the T4 itself ran
  and billed fine without one. Once the teammate who owns the Lightning account allocated credits
  to the `default-project` teamspace, the endpoint started answering within minutes, no redeploy
  needed. Worth real money context: at Lightning's ~$0.19/T4-hour (unverified against Lightning's
  own pricing page, which wouldn't render outside a browser), this entire task costs under $1 in
  actual compute — the $5 already in the org easily covers it. This blocker was never about
  insufficient credits, only unallocated ones.
- **`glb_url` came back as `https://localhost:8000/...`.** The proxy-header fix earlier in this
  story (`--forwarded-allow-ips`) was necessary but not sufficient: it fixes the *scheme*
  (confirmed correct, `https://`), but Lightning's edge does not forward the real public hostname
  to the container at all — the raw `Host` the app sees is literally `localhost`, confirmed by
  inspecting a real completed session's `getReconstruction` response. Exactly the risk this
  story's own notes flagged before ever deploying ("the remote smoke's GLB download would fail
  visibly" — it did). Fixed in `recon/service.py`'s new `public_model_url()`, checked
  most-specific-first: an explicit `PROOFSHAPE_PUBLIC_BASE_URL` operator override, then
  `X-Forwarded-Host` (in case a proxy sends one), falling back to today's `request.url_for`
  unchanged for every existing local/CI/in-process caller.
  Before this fix, with the pipeline already proven working: all 30 real `s-04` frames uploaded,
  VGGT reconstruction completed on the real T4 (43.9 s reconstruction stage) — only the final GLB
  download step failed, confirming the GPU pipeline itself was never the problem.

  **@mbj1994's review (PR #94) correctly caught that this wasn't actually proven to work in
  production** — the unit tests proved the helper's own precedence, but nothing wired
  `PROOFSHAPE_PUBLIC_BASE_URL` into the real deployment, and `X-Forwarded-Host` being sent by
  Lightning's proxy was never actually confirmed, only hoped for. Since the deploy workflow only
  runs on `main` by design (D-013/D-014), that couldn't be proven from the PR branch either way
  before merging. Fixed properly rather than merging on a hope: `scripts/deploy_recon.py`'s
  `start()` now makes a second `lightning deployment update` call, setting
  `PROOFSHAPE_PUBLIC_BASE_URL` to the real URL once `wait_until_ready` has returned it, then waits
  for that restart too. This makes correctness deterministic regardless of what Lightning's proxy
  does or doesn't forward. A drift-guard test keeps the two files' matching env-var-name string
  from silently diverging, since `deploy_recon.py` can't import `recon.service` directly (the
  deploy job's environment only installs `lightning-sdk`, not the full `requirements.txt`
  FastAPI/pydantic stack).

  Verified by unit test and mutation: reverting the service-side fix fails exactly the 3 new
  tests built to catch it; reverting the deploy-script wiring fails exactly the 3 tests guarding
  that; breaking the drift-guard string fails exactly that one test. Full suite 303 passed, 1
  skipped. Not yet re-verified against the real redeployed service — that's the next step before
  this story can record a real manual-check result.
- `--max-runtime`'s actual behavior still not observed (the deployment hasn't run anywhere near
  4 hours continuously yet).

## Tests

Automated (CPU, in the existing pytest CI job):
- **`tests/test_deploy_recon.py`**: main-only for both start and stop, with no CLI call at all off
  `main`; digest-pinned images only; one T4 replica on port 8000 with token auth; the token never
  printed; HTTPS-only ready URL; readiness timeout reports the last status; create versus update;
  stop is a no-op when nothing is running.
- **`tests/test_smoke_r14.py`**: the shared flow runs against the real `create_app` with a fake
  pipeline; a failed reconstruction is an error, not a pass; polling, and its timeout; the bearer
  token is sent; the proxy-downgrade check; HTTPS-or-localhost only; remote mode refuses to run
  without the token.
- **`tests/test_container.py`**: structural invariants. Base pinned by digest; no torch reinstall;
  no `COPY .`; secrets and captures excluded from the build context; one worker on the deployed
  port, with proxy trust; the prefetched model is the one the runner loads; deploy workflow manual
  and `main`-only with no literal credentials; publish only from `main`, after the smoke.
- **`.github/workflows/recon-image.yml`**: builds the real image and gets a 201 from inside the
  running container on every PR that can change it.

## Acceptance criteria

- A second member follows the runbook successfully without help.

## Notes and decisions

2026-09-17: D-036 replaces the RunPod-specific deployment assumption with Lightning. This does
not relax the story: the deployed service still has to be reachable securely over HTTPS/TLS and
a second member still has to reproduce the runbook.

2026-10-05: Implementation (PR 1 of 2). Planned with the team's answers on three open forks,
recorded as D-042: the image is published on every merge but started by hand; the endpoint is
token-gated; the service runs on demand. The runbook is the `R-15` section of `recon/README.md`.

What was built:
- **`Dockerfile`**: base `pytorch/pytorch:2.8.0-cuda12.8-cudnn9-runtime`, pinned by digest. That is
  the same torch 2.8.0+cu128 the Studio was validated on, and torch is never reinstalled.
- **`scripts/container_entrypoint.sh`**: fetches the weights at start-up, then runs one uvicorn
  worker.
- **`.dockerignore`**.
- **`.github/workflows/recon-image.yml`**: build, then smoke-test the container. On PRs it stops
  there; on `main` it also publishes to GHCR.
- **`.github/workflows/deploy-recon.yml`**: manual, `main` only. It calls
  **`scripts/deploy_recon.py`**.
- **`scripts/smoke_r14.py`** gained a `--base-url` mode. One shared `drive_session` now serves both
  the in-process R-14 check and the deployed one.

Things exploration and building turned up that weren't in the story:
- **One replica, one worker is required for correctness.** R-14's `SessionStore` keeps sessions on
  one container's local disk behind an in-process lock. A second replica would answer
  `session_not_found`. The deploy script hard-codes `--replicas 1`, and a test pins it.
- **A real HTTPS bug, caught before any deploy.** `getReconstruction`'s `glb_url` comes from
  `request.url_for`, an absolute URL built from the scheme uvicorn sees. TLS ends at Lightning's
  proxy, and by default uvicorn only trusts `X-Forwarded-Proto` from 127.0.0.1. So phones would
  have been handed an `http://` model link from an `https://` service. I checked both ways in the
  built container: with `--forwarded-allow-ips '*'`, a request carrying `X-Forwarded-Proto: https`
  got an `https://` `glb_url`. Without the flag, the same request got `http://`. The entrypoint now
  sets it, and the remote smoke fails if `glb_url`'s scheme differs from the base URL's.
- **The VGGT package depends on the non-headless `opencv-python`.** That clashes with our pinned
  `opencv-python-headless`; both provide `cv2`, and the non-headless one needs `libGL`. The image
  removes it and reinstalls the pinned headless build. Checked in the built image: only
  `opencv-python-headless 4.11.0.86` is present.
- **No new route for health checks.** `test_public_operation_ids_match_the_frozen_contract`
  requires exactly the five frozen operations. Readiness polls Lightning's own replica status, and
  CI waits on FastAPI's built-in `/openapi.json`.
- **The Lightning CLI was checked rather than guessed.** Lightning's docs site wouldn't render
  outside a browser, so every flag `deploy_recon.py` uses (`--token-auth`, `--replicas`,
  `--max-runtime`, `update`, `delete --yes`, `inspect`) was confirmed against `lightning deployment
  … --help` from the pinned `lightning-sdk==2026.10.1`. So were its auth variables
  (`LIGHTNING_USER_ID` + `LIGHTNING_API_KEY`) and the `inspect` JSON fields
  (`status.urls`, `status.ready_replicas`).

Verified locally (Apple Silicon, image built for `linux/amd64` under emulation, 4.49 GB):
- **Inside the image:** Python 3.11.13, torch 2.8.0+cu128, numpy 1.26.4, and `vggt`, `cv2` and
  `recon.service` all import. It runs as a non-root user.
- **Through the real entrypoint, with prefetch off:** `POST /v1/sessions` → 201.
- **Remote smoke against that container:** all 30 real `s-04` frames uploaded, then reconstruction
  failed with the explicit "PyTorch cannot see a GPU" message, as expected with no GPU.
- **Digest and label extraction in `deploy-recon.yml`:** checked against both a multi-arch and a
  single-arch public image.
- **Mutation checks:** each guarded behaviour was broken in turn and a test failed every time. The
  mutations were: a second worker, removing proxy trust, changing the port, dropping `.env` from
  `.dockerignore`, unpinning the base, two replicas, removing the main-only guard from start or
  stop, printing the token, accepting `http://`, dropping the `glb_url` check, and not polling. The
  main-guard mutation first survived, because the test failed for an unrelated reason (a missing
  variable). I fixed the test and the mutation is now caught.

**Still open, and why this PR doesn't close the story.** `workflow_dispatch` workflows can only
run once they're on `main`, and D-013 forbids deploying from anything else. So criteria 2 and 3
can only be shown after this merges. That is the same split R-13 used. After merge:
1. An admin does the runbook's one-time setup. The Lightning key comes from whoever owns the
   teamspace (@mbj1994 set it up in F-05).
2. Start the deployment and fill in the manual check below.
3. A second member follows the runbook unaided.
4. The close-out PR sets `Done` per D-038.

Not yet observed, to note on the first real deploy:
- How long a cold start takes, since it pulls the image and downloads the weights.
- Whether Lightning's proxy keeps the original `Host` header. If it doesn't, `glb_url` would have
  the right scheme but an internal host, and the remote smoke's GLB download would fail visibly.
- How `--max-runtime` actually behaves on a deployment.

## Tests

Automated (CPU, in the existing pytest CI job):
- **`tests/test_deploy_recon.py`**: main-only for both start and stop, with no CLI call at all off
  `main`; digest-pinned images only; one T4 replica on port 8000 with token auth; the token never
  printed; HTTPS-only ready URL; readiness timeout reports the last status; create versus update;
  stop is a no-op when nothing is running.
- **`tests/test_smoke_r14.py`**: the shared flow runs against the real `create_app` with a fake
  pipeline; a failed reconstruction is an error, not a pass; polling, and its timeout; the bearer
  token is sent; the proxy-downgrade check; HTTPS-or-localhost only; remote mode refuses to run
  without the token.
- **`tests/test_container.py`**: structural invariants. Base pinned by digest; no torch reinstall;
  no `COPY .`; secrets and captures excluded from the build context; one worker on the deployed
  port, with proxy trust; the prefetched model is the one the runner loads; deploy workflow manual
  and `main`-only with no literal credentials; publish only from `main`, after the smoke.
- **`.github/workflows/recon-image.yml`**: builds the real image and gets a 201 from inside the
  running container on every PR that can change it.

## Why this exists

R-07's acceptance criteria included "produces a mesh for every golden object." R-07 was
implemented and fully unit-tested against synthetic data on a machine with no GPU/torch and no
local `fixtures/data/recon_runs`, so that could not be checked against real photographs in the
same session. Same shape of gap as R-06 (split to R-17): the TSDF fusion logic itself — the
board-frame camera-pose derivation, the voxel projection/truncation math, marching cubes, the
Poisson fallback — is done and covered by synthetic tests; what's missing is someone with GPU
access actually running it on the five real golden objects and looking at what comes out.

## Acceptance criteria

- For each of the five golden objects, `recon/tsdf_fusion.py`'s `fuse_run` (or its CLI,
  `python -m recon.tsdf_fusion`) is run against that object's real R-01 + R-04 output, using
  R-06's `segment_part` masking (already wired into `fuse_run`).
- Each resulting `mesh.ply` is opened in a viewer and visually confirmed: a recognizable,
  roughly-closed mesh of the part, not a scattered/degenerate result.
- Per-object result (pass, or what was wrong) is recorded in this story's notes. A failure on a
  specific object is not automatically a defect in the fusion logic — voxel size, truncation
  distance, or R-06's height/footprint parameters may need adjusting for that object's geometry
  or that capture's frame count, all of which are already configurable on `fuse_run`.
- If the default marching-cubes path produces a poor result on a given object (e.g. too few
  frames for the TSDF to close), try the `--method poisson` fallback (needs Open3D installed
  locally — see `recon/tsdf_fusion.py`'s module docstring) and record which path worked.

## Tests

Same manual-check exception as R-17: "visually confirmed" is inherently a human judgment on real
photographs of real objects, not something an automated test asserts. `recon/tsdf_fusion.py`'s
own logic (the board-frame extrinsic derivation, TSDF sign/truncation/averaging, marching cubes'
coordinate mapping, the mesh PLY I/O) is already fully covered by synthetic-data unit tests
written alongside it in R-07 (`tests/test_tsdf_fusion.py`, plus the cross-check test in
`tests/test_metric_alignment.py`) — this story is only the real-data look-and-check those tests
cannot stand in for.

## Notes and decisions

2026-10-06: Ran `fuse_run` on all five golden objects on the shared Lightning pod. R-01/R-02/R-04
outputs already existed for all five from earlier work (mbj1994's R-19 chain run), so no fresh
VGGT reconstruction was needed — `fuse_run` ran directly against that existing data, which also
meant the GPU-unavailability on this particular pod session (`--device cuda was requested but
PyTorch cannot see a GPU`) never actually blocked this story, since `fuse_run` itself needs no
GPU, only R-01's already-persisted depth/poses.

**Per-object result, default (marching cubes):**
- s-01 (padlock, lighting A): not independently re-checked with default method — went straight to
  Poisson after confirming Poisson passed cleanly (see below); reasonable given s-02, the same
  physical object, shows the identical default-method banding artifact described below.
- s-02 (padlock, lighting B, same physical object as s-01): default output has a strong banding/
  corrugation artifact — fine parallel ridges across most of the surface, large holes, no
  recognizable padlock shape. Not a pass.
- s-03 (rounded rigid object): default output shows one genuinely recognizable smooth curved/dome
  surface patch, but surrounded by a chaotic halo of disconnected shard fragments. Not a pass.
- s-04 (yellow triangular prism): same banding/corrugation artifact as s-01/s-02, large hole, no
  recognizable prism shape. Not a pass.
- s-05 (rectangular prism): not independently captured as a separate screenshot; grouped with the
  general default-method banding pattern seen on every other object tried.

**Per-object result, `--method poisson` fallback** (after installing Open3D and, on this pod,
`apt-get install libusb-1.0-0` — Open3D's compiled bindings need libusb and the base container
didn't have it; a missing-OS-library problem, not a Python or project-code problem):
- s-01: **Pass.** Smooth, continuous, no banding. 471,816 vertices / 949,783 faces (face/vertex
  ratio ≈2.01, consistent with a closed surface). No PoissonRecon warning.
- s-02: **Pass.** Same clean, smooth result. 674,894 vertices / 1,345,019 faces (ratio ≈1.99). No
  warning.
- s-03: **Not a pass.** Porous, cratered, fragmented — no recognizable rounded-object structure
  from any angle checked. 1,026,022 vertices / 2,077,358 faces. PoissonRecon itself emitted
  `[WARNING] ... bad average roots: 6` during isosurface extraction — a genuine numerical signal
  from the library, not just a bad viewing angle.
- s-04: **Not a pass.** Messy blob with some flat angular facets visible (plausibly prism edges)
  but dominated by noise, a stray disconnected blade shape, and a separate floating blob.
  403,731 vertices / 818,976 faces (ratio ≈2.03). No PoissonRecon warning this time — the warning
  is not a reliable predictor of visual quality on its own.
- s-05: **Not a pass.** Messy, with one smooth curved tube/arc shape, a disconnected crescent
  piece, and a grainy noise patch — not recognizable as the rectangular prism. 518,705 vertices /
  1,039,940 faces. `[WARNING] ... bad average roots: 2`.

**Pattern worth recording, not just the per-object list:** the two objects that passed cleanly
(s-01, s-02) are the *same physical object* — just two lighting conditions of one padlock — while
all three objects that failed are three different physical objects (rounded object, triangular
prism, rectangular prism). That is not scattered bad luck; it points at `segment_part`'s default
height/footprint parameters suiting the padlock's particular size and not the other three
objects' geometry, which is exactly the class of cause the acceptance criteria above already
names as not automatically a fusion-logic defect. Deliberately stopped here rather than tuning
`--height-threshold-mm`/`--footprint-mm` per failing object: this story is a 1 h look-and-check,
and chasing a parameter fix for three objects is real investigative work in its own right, better
done deliberately than squeezed in here. Recording the finding precisely (which objects, which
methods, the exact warning text, the shared-object pattern) so whoever picks it up next doesn't
have to re-derive it.

Not filed as a separate follow-up story, unlike R-06/R-07/R-10's GPU-access splits — this one
doesn't need GPU access someone lacked, it needs someone to actually do the parameter-tuning work,
which is a real task a future story can scope properly rather than something blocked on access.

## Why this exists

R-07's acceptance criteria included "produces a mesh for every golden object." R-07 was
implemented and fully unit-tested against synthetic data on a machine with no GPU/torch and no
local `fixtures/data/recon_runs`, so that could not be checked against real photographs in the
same session. Same shape of gap as R-06 (split to R-17): the TSDF fusion logic itself — the
board-frame camera-pose derivation, the voxel projection/truncation math, marching cubes, the
Poisson fallback — is done and covered by synthetic tests; what's missing is someone with GPU
access actually running it on the five real golden objects and looking at what comes out.

## Acceptance criteria

- For each of the five golden objects, `recon/tsdf_fusion.py`'s `fuse_run` (or its CLI,
  `python -m recon.tsdf_fusion`) is run against that object's real R-01 + R-04 output, using
  R-06's `segment_part` masking (already wired into `fuse_run`).
- Each resulting `mesh.ply` is opened in a viewer and visually confirmed: a recognizable,
  roughly-closed mesh of the part, not a scattered/degenerate result.
- Per-object result (pass, or what was wrong) is recorded in this story's notes. A failure on a
  specific object is not automatically a defect in the fusion logic — voxel size, truncation
  distance, or R-06's height/footprint parameters may need adjusting for that object's geometry
  or that capture's frame count, all of which are already configurable on `fuse_run`.
- If the default marching-cubes path produces a poor result on a given object (e.g. too few
  frames for the TSDF to close), try the `--method poisson` fallback (needs Open3D installed
  locally — see `recon/tsdf_fusion.py`'s module docstring) and record which path worked.

## Tests

Same manual-check exception as R-17: "visually confirmed" is inherently a human judgment on real
photographs of real objects, not something an automated test asserts. `recon/tsdf_fusion.py`'s
own logic (the board-frame extrinsic derivation, TSDF sign/truncation/averaging, marching cubes'
coordinate mapping, the mesh PLY I/O) is already fully covered by synthetic-data unit tests
written alongside it in R-07 (`tests/test_tsdf_fusion.py`, plus the cross-check test in
`tests/test_metric_alignment.py`) — this story is only the real-data look-and-check those tests
cannot stand in for.

## Acceptance criteria

- Every vertex projected into every frame; view count and triangulation angle computed.
- Labelled Observed (two or more frames with adequate baseline) or Unobserved.
- Labels travel with the exported mesh.

## Notes and decisions

_Written while working. What you tried, what surprised you, what you chose and why._
_If a decision here governs later work, add it to `docs/decisions.md` with a number._

2026-10-01: Implemented in `recon/provenance.py` (`compute_observations`, `triangulation_angle_deg`,
`label_vertices`, `label_faces`, `provenance_run`, plus a CLI) — the mechanism behind the hard
rule ("unobserved geometry can never pass or fail a part"). Two things needed resolving against
other docs before writing any labelling logic:

- **Occlusion check.** A naive "projects inside the image + in front of the camera" view count
  would overcount: the back face of any non-convex part would be miscounted as seen by a frame
  that's actually looking through the object at its front. A frame only counts as observing a
  vertex if the vertex also projects within a configurable tolerance of that frame's *measured*
  depth at the landed pixel — the same occlusion logic R-07's `fuse_tsdf` already uses, reused via
  a shared helper (`metric_alignment.project_points_to_camera`, extracted from `fuse_tsdf`'s
  previously-inlined projection math) rather than re-derived. This is exactly the kind of
  duplication flagged repeatedly in review of PR #61 (COLMAP backend) — avoided here proactively.
- **"Observed" definition, proposal vs. glossary.** `submissions/2026-09-05-proposal.md`'s
  original definition of Observed also required "σ below the tier's floor," but σ (per-vertex
  uncertainty) is R-10's job, which depends on R-09, not the reverse. `docs/glossary.md`'s current
  definition and this story's own acceptance criteria deliberately only mention view count +
  triangulation angle. Per `CLAUDE.md`'s "the repository wins" rule, this story's own acceptance
  criteria (and the current glossary) are authoritative over the older proposal doc — R-09
  computes exactly what its criteria say; the σ-floor refinement is R-10's to add.

**Color convention, not invented:** `contracts/openapi.yaml` already specifies that provenance
labels travel as vertex colors inside the exported GLB (not separate JSON fields), and the
proposal says Unobserved vertices are "drawn gray" — so grey for Unobserved was already settled.
White for Observed is this story's own choice ("no color asserted yet" — the real deviation-
heatmap coloring is I-06, much later, which doesn't exist yet).

Face labels use a conservative convention this story chose (not contract-mandated): a face is
Observed only if all three vertices are. `provenance_run` accepts either R-07's raw `mesh.ply` or
R-08's cleaned `mesh_clean.glb` as input, since R-09 depends only on R-07 in the backlog graph —
R-08 is a sibling, not a prerequisite. In practice, labelling *after* R-08's decimation is
probably what R-14 (the endpoint) will want, since `fast_simplification` doesn't carry per-vertex
attributes through simplification — but that's R-14's wiring decision, not forced here. The raw
per-observation table (vertex/frame/z_cam/measured_depth) is persisted to `observations.npz`
specifically for R-10 to reuse without recomputing projections.

No measured numbers exist for "adequate triangulation baseline" or the occlusion tolerance;
`DEFAULT_MIN_TRIANGULATION_ANGLE_DEG` (2.0°, a standard SfM rule of thumb) and
`DEFAULT_DEPTH_CONSISTENCY_TOLERANCE_MM` (5.0) are documented, configurable assumptions, same as
every prior story's defaults (R-06's height threshold, R-07's voxel size, R-08's triangle count).

Nothing in this story's criteria needs real captured photos, so it closed end-to-end with
synthetic-mesh tests in one session — no follow-up story, same reasoning as R-08.

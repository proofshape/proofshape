## Why this exists

Nothing has ever exercised `capture/` against the frozen contract (`contracts/openapi.yaml`,
F-03) — every session-lifecycle field capture will ever send is still just prose in a spec file.
This is the smallest possible proof that the wire format actually works end to end, before
anyone builds the real app shell (C-04) around an assumption about it that turns out wrong. It
is deliberately *not* the app shell: no live camera, no gyro, no UI polish — those are C-02, C-03
and C-04 onward. A plain page with a file picker is enough to prove the contract.

## Acceptance criteria

- A page in `capture/` collects an order code, calls `POST /v1/sessions` (`createSession`), and
  displays the returned `session_id` — or the `400` error if the order code is rejected.
- The same page lets the user pick a JPEG file and a gyro reading (three plain number inputs are
  fine — a real reading is C-03's job), calls `POST /v1/sessions/{session_id}/frames`
  (`uploadFrame`) with them, and shows whether the frame was accepted (`202`) or rejected (`422`,
  with the reason).
- Calling `POST /v1/sessions/{session_id}/finish` (`finishSession`) after at least one accepted
  frame is possible from the page, and its result (`202` or `409`) is shown.

## Tests

R-14 (the real reconstruction endpoint) is still `Blocked`, so this story needs something to
actually call. Stand up a small local stub covering just these three routes — `contracts/README.md`
already describes a fuller "mock service" as later, separate S1 work; this is not that, just
enough for this story's own tests, shaped by `contracts/examples/*.json` so its canned responses
match the frozen contract exactly (a `201` with a `session_id`, a `202`/`422` frame result, a
`202`/`409` finish result).

Unit-test the request-building and response-handling logic against that stub: a valid order code
gets a session id displayed; an unknown one shows the `400` message; an accepted frame shows
`202`, a rejected one shows its `message`; `finish` before any accepted frame shows the `409`
case. None of this needs a real device, a camera, or HTTPS — it's file-input and fetch calls, so
it can run in CI like any other test in this repo.

## Notes and decisions

This story's own "Tests" section above says `contracts/README.md` "already describes a fuller
'mock service' as later, separate S1 work." That description actually lives in
`docs/sprint-plan.md` §4 ("The mock service (S1). ~40 lines answering every call in the frozen
contract with a canned GLB and a canned verdict"), not in `contracts/README.md`, which doesn't
mention a mock service at all. Leaving the citation above as written (correcting it would edit
acceptance-criteria text after the fact) — noting the right source here instead, since the
distinction it draws (this story's three-route stub is not that S1 mock service) is still
correct.

Tooling and design choices, recorded as D-040 (capture's npm project: `capture/`-local, Vite +
vanilla TypeScript + Vitest, no UI framework yet, Node 24) and D-041 (`gyro` travels as a
JSON-encoded `multipart/form-data` part — OpenAPI's default for an object property with no
`encoding:` override). Full reasoning for both is in `docs/decisions.md`.

Two things that weren't obvious going in:
- Vite statically rewrites the literal pattern `new URL('relative/path', import.meta.url)` into
  an asset import, subject to its dev-server `server.fs.allow` boundary — which denied reading
  `contracts/examples/*.json` from inside `capture/`'s stub, since `contracts/` sits outside the
  vite root. Fixed by building the path with `node:path`/`node:url` instead, which is a plain
  Node file read and never goes through Vite's asset pipeline.
- happy-dom enforces the same-origin policy like a real browser, so `src/page.test.ts` (the only
  file that needs a DOM) fetching an ephemeral-port stub from a different default window origin
  was silently blocked as cross-origin. Fixed by giving that one test file a fixed stub port that
  matches a fixed `environmentOptions.happyDOM.url` in `vite.config.ts`, and switching the rest
  of the suite (no DOM needed) to the plain `node` environment via `test.environment: "node"` —
  it had been defaulting the whole suite to `happy-dom`, which also meant the pure-HTTP tests in
  `api.test.ts` and `stub/contract-stub.test.ts` were needlessly subject to the same restriction.
  A fixed number of `setTimeout(0)` ticks also wasn't enough to await a real socket round trip
  (unlike the in-process stub calls elsewhere); `src/page.test.ts` polls with `vi.waitFor`
  instead.

Verified by mutation: temporarily sent `gyro` as `{x, y, z}` instead of `{alpha, beta, gamma}` —
both `src/api.test.ts` and `src/page.test.ts` failed loudly (the stub's own contract-shape check
fired a 500, which `api.ts` surfaces as a thrown error), then reverted.

2026-09-28: MASt3R feasibility checked on the shared Lightning Tesla T4 before integration.
The pinned upstream checkout is `f5209afc300cec36239a7ac992263f36847bbba0`. A real two-frame
s-04 model smoke test passed in 1.96 s inference time with 3.12 GiB peak allocated GPU memory,
producing 384×512 3D/confidence outputs. A four-frame s-04 sparse-global-alignment smoke test
also passed: 13.72 s alignment time, 3.26 GiB peak allocated GPU memory, four camera-to-world
poses, four 3×3 intrinsics matrices, finite dense depth for all 196,608 processed pixels per
frame, and confidence maps at 384×512. These are smoke-test measurements, not the required
full-capture R-11 wall-clock result.

Implementation uses `recon/mast3r_runner.py` plus `recon/reconstruction_runner.py`.
`PROOFSHAPE_RECON_BACKEND=mast3r` (or `--backend mast3r`) selects MASt3R while VGGT remains
the default. Both paths target the R-01 four-file contract. The adapter inverts MASt3R
camera-to-world poses to camera-from-world extrinsics and deliberately ignores EXIF rotation to
match R-01/R-02 stored-pixel geometry. It does not treat the checkpoint's "metric" name as proof
of metric inspection scale; R-04 remains responsible for board-frame alignment.



2026-09-28: Full 30-frame s-04 acceptance run passed through
`recon.reconstruction_runner` with `backend=mast3r`. The run wrote the R-01-compatible four-file
contract and reported 5,898,240 points with a measured total wall-clock of **249.89 s** on the
shared Lightning GPU. This is a single measured run, not an average.

The downstream compatibility check also passed without modifying R-04:
`python -m recon.metric_alignment fixtures/data/recon_runs/s-04-mast3r
fixtures/data/board_poses/s-04 --out .../metric_alignment.json` paired 29 frames and reported
**12.167 mm RMS camera-centre alignment residual**. That residual is an alignment
self-consistency diagnostic only; it is not object accuracy and it does not establish an
inspection tolerance.

# R-02 · Board detection and per-frame camera pose

**Area:** recon · **Tier:** 1 · **Estimate:** 5 h
**Depends on:** F-06, F-07
**State:** Claimed
**Owner:** @TabeenRaoof

---

## Acceptance criteria

- Detects the ChArUco board in each frame and returns a camera pose in the board frame.
- Reports which frames failed detection and why.
- Verified on a frame where the board is partly hidden by the part.

## Notes and decisions

_Written while working. What you tried, what surprised you, what you chose and why._
_If a decision here governs later work, add it to `docs/decisions.md` with a number._

2026-09-25: Implemented in `recon/board_pose.py` (CLI: `python -m recon.board_pose <capture>`),
tests in `tests/test_board_pose.py`. No GPU or PyTorch needed, so it runs on any laptop (and in CI, once CI runs pytest).

**What it writes** (`fixtures/data/board_poses/<sample>/`, git-ignored): `board_poses.npz`, with
camera-from-board extrinsics in millimetres using R-01's `x_cam = R @ x_world + t` convention
(NaN for frames without a pose, never an identity pose that looks measured), per-frame K, corner
counts, reprojection RMS, and every detected ChArUco corner (so R-03 can calibrate without
re-detecting); and `board_poses.json`, with each frame's status, failure reason and message. The
board frame is OpenCV's: origin at the board's outer corner, x along the 8-square side, z pointing
into the table, so cameras have negative z centres. R-04 should know that before it chooses an
"up" direction.

**Failure reasons** (criterion 2): `board_not_detected` (no markers at all) and
`board_partially_occluded` (markers found, but fewer than 6 corners, or all visible corners on one
line, which leaves the pose undetermined) are both contract `ErrorDetail` codes.
`image_unreadable`, `intrinsics_unavailable` and `pose_solve_failed` are R-02-internal; R-14
decides how to surface them. The minimum of 6 corners is a chosen guard, not a measured threshold.

**Four things that surprised me, in order of how much they would have hurt:**

1. **D-034's OpenCV flag was backwards.** With `setLegacyPattern(False)`, as D-034's amendment
   specified, every real frame found markers but zero corners: s-01 posed 0/26. The committed
   `fixtures/charuco_board.pdf` gives 35/35 corners with `True` and 0/35 with `False`. The calib.io
   print choice stands; only the mapping to OpenCV was wrong. Corrected under D-034 (agreed with
   @TabeenRaoof), with the evidence, and `test_code_board_detects_the_committed_print_file`
   now checks the code's board against the PDF itself, including a 20 mm pitch measured from the
   PDF's point units. The synthetic tests couldn't have caught this: they render and detect with
   the same `make_board()`, so they agree with each other even when both are wrong.
2. **EXIF orientation differs within a single capture.** s-02 mixes Orientation 1 and 6 frames
   (all stored as 5712×4284 landscape). VGGT's loader ignores the tag, while `cv2.imread` applies it
   by default, so a naive R-02 would have handed R-04 cameras rotated 90° about the optical axis
   relative to R-01's on those frames. R-02 reads stored sensor pixels
   (`IMREAD_IGNORE_ORIENTATION`) to match R-01 and records the tag per frame. **R-01/R-04 owners:**
   if R-01 ever switches to `exif_transpose`, R-02 must switch too, and vice versa.
3. **Intrinsics before R-03.** A pose needs K, and calibrating K is R-03 (which depends on this
   story). Agreed approach: K from the EXIF 35 mm-equivalent focal (26 mm on these iPhone 16
   frames), converted on the *diagonal* as the standard defines it; the 36 mm-width shortcut is
   about 4% short on a 4:3 sensor. Principal point at the centre, no distortion. Every frame
   records `intrinsics_source`; `estimate_board_poses(..., intrinsic_override=K)` is the hook
   for R-03. There is no silent fallback focal: a frame without EXIF focal gets
   `intrinsics_unavailable` (its corners are still saved for R-03).
4. **IPPE, OpenCV's planar pose solver, refused some valid corner layouts.** On a partial
   (unverified) s-03 download, 3 of 22 frames saw only board column 0 plus one neighbouring
   corner, an "L" that isn't collinear, so the pose is determined, but IPPE returned "no
   solution". Switched to SQPnP (globally optimal, no starting guess) plus LM refinement. On
   every frame where both solved, the refined poses were identical (s-02 re-run: same 29 frames
   posed, translations within 1e-6 mm), and SQPnP solved all 3 L-frames at about 1 px RMS. IPPE
   accepts a noise-free projection of the same pose, so the regression test
   (`test_pose_solved_from_real_l_shaped_corners`) uses the 6 real detected corner positions
   from `s-03/IMG_3946`, and it fails if IPPE is put back.

claim, and R-03 should lower it.

All five were run with the SQPnP code as committed, on the team's local staging copy
(`../proofshape-fixtures-staging/`, next to the repo), after checking that every sample there
matches `golden_capture_manifest.json` exactly: frame count and `content_sha256`, the same check
`download_golden_capture.sh` does. `python -m recon.board_pose` takes any folder, so no copying
was needed. s-01 was also run earlier with the IPPE solver, on a verified Drive download; the
two runs posed the same 26 frames and agree to within 1e-7 mm. s-03's low corner counts are
expected: the rounded part covers most of the board from above.

Getting the data from Drive hit its download limit on the second full fetch ("…or have had many
accesses"), partly because an orphaned earlier download was still running alongside the new
one. Because `download_golden_capture.sh` deletes each sample folder before fetching it, the
failed re-fetch also deleted a verified local copy. Worth a small F-06 follow-up: download into a
temporary folder and swap it in only after verification.

Every golden frame has the part standing on the board, so every posed frame above is a
partly-hidden-board case. Checked by eye as well as by RMS: on `s-01/IMG_3939` (grazing view,
only 12/35 corners detected) and `s-02/IMG_4040` (Orientation 6, 25/35), projecting all 35 board
corners and the board outline with the solved pose lands on the printed pattern, including the
corners hidden under the padlock; the same holds for `s-03/IMG_3945` (6 corners, the "L" layout
from point 4). All 4 failures were checked by eye and are genuine:
- `s-02/IMG_4056` is heavily blurred (2 markers readable). It's reported as
  `board_partially_occluded` because R-02 sees "too few corners" and can't tell blur from
  occlusion. Rejecting blurred frames up front is the capture frame gate's job (C-06, contract
  code `frame_rejected_blur`).
- `s-03/IMG_3968` (no markers: `board_not_detected`), `s-03/IMG_3969` (3 corners) and
  `s-04/IMG_4097` (2 corners) are near-table-level grazing views, where the board is squashed
  to a thin strip. These are the frames the capture guidance should steer people away from.

**Loose ends for other stories:** `find_capture_frames` duplicates R-01's function of the same
name (R-01 isn't merged, so there was nothing to import); consolidate once both are on `main`.
The Python CI workflow runs only ruff, not pytest, so these tests run under the pre-PR checklist,
not in CI. That's a gap for whoever next touches F-04.

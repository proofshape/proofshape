## Why this exists

No order is stored anywhere. R-14: "buyer/order storage is not in the written backlog yet, so
R-14 does not invent it". That has three consequences:
- **There is no buyer side to write to.** The buyer page (C-16) has nowhere to save an order.
- **No session can have a CAD.** So `getVerdict` always answers 404 `no_cad_uploaded`.
- **The order code checks nothing.** The deployed `app = create_app()` passes no
  `known_order_codes`, so any non-empty code starts a paid GPU run (O-005's third question).

## Acceptance criteria

- **Create and read an order.**
  - `POST /v1/orders` (`createOrder`) takes a multipart body:
    - an optional CAD file (`.stl`, `.obj` or `.glb`);
    - the spec, as a JSON part (D-041's pattern), stored as an opaque object and marked
      `x-proofshape-extends-at` (D-032);
    - an optional placement note and an optional buyer reference.
  - It returns 201 with an `Order`: `order_code`, `created_at`, `has_cad`, the CAD's units and
    bounding box in mm, the spec and the note.
  - The CAD is checked with `inspection.cad.load_mesh` and kept byte for byte, never converted. A
    file it rejects gets a new 422 `cad_unreadable`.
  - `GET /v1/orders/{order_code}` (`getOrder`) returns the order, or 404 `order_code_unknown`.
- **Stored as files.** A folder and a JSON file per order (proposal §5), under
  `PROOFSHAPE_ORDERS_DIR`, default `proofshape-data/orders`, written atomically as
  `SessionStore` writes. It can't share `PROOFSHAPE_DATA_DIR`, which is the sessions folder
  itself.
  - Codes are generated by the server, hard to guess and easy to type: for example `PO-` and eight
    Crockford base32 characters. The buyer's own PO number goes in the buyer reference. The mock
    keeps `PO-48213-A`.
- **Sessions check the code.**
  - `createSession` answers 400 `order_code_unknown` unless the code is in the store. A test can
    still pass `known_order_codes`, which then overrides the store.
  - `getVerdict` looks up the session's order. With no CAD on the order it answers 404
    `no_cad_uploaded`, as now. With a CAD on file it answers a new 404 `verdict_not_available`
    until I-07 exists. It never invents a verdict.
- **The contract, under D-031.**
  - A minor version bump on top of A-11's 1.1, under the rule for additive changes that D-056
    proposes in #217.
  - An example for every new operation and error code, which `tests/test_contract.py` requires.
  - Manual §4 and §9 updated in the same pull request.

## Notes and decisions

- **Why it depends on A-11.** A-11's contract v1.1 (#217, with D-056) merges at the Nov 13
  boundary, and this change builds on it. Contract changes need both other members' approval and
  merge only at a sprint boundary (D-031). Four days aren't enough to build this, get both
  approvals and merge on Nov 13, so **Dec 2 is the realistic boundary**. Everything that waits on this (C-16 and C-17)
  then lands between Dec 2 and M7's code freeze on Dec 4. The Nov 13 call has to decide whether
  that is acceptable.
- **O-005.** This closes "any code starts a GPU run" only if `createOrder` is guarded too, since
  anyone holding the token in the public bundle could otherwise create an order.
  - Recommended guard: a buyer key held only on the server (for example `PROOFSHAPE_BUYER_KEY`,
    sent as a header and typed into the buyer page, never built into it). `createOrder` is
    refused when the key is unset.
  - Record the chosen guard as a decision when this is built.
- **Units.** STL and OBJ carry no units, so millimetres are a convention, and GLB is
  `assumed_mm` (I-02, I-11). Returning the bounding box makes a CAD drawn in metres visibly 1000×
  wrong on the buyer page.
- **Persistence.** On Lightning the container's disk is lost when it stops (D-042), so orders go
  with it. That is a known limit, recorded here. Shared storage would be its own story.
- **Out of scope:**
  - buyer accounts, a portal and approval routing (proposal §4);
  - single-use codes. That is session integrity (Tier 3, 3rd on the cut list), and a Rescan needs
    a second session on the same order anyway;
  - the verdict (I-07) and the tolerance internals (D-032);
  - listing an order's sessions.
- **A decision when built:** record the store layout and the code format with a number.
- **Freeze and cut list.** S5 work ("buyer setup … CAD upload"), filed 2026-11-09, four days
  before M5's feature freeze. It is Tier 2, it closes a Tier 1 cost exposure, and it isn't on the
  cut list.
- **Overlap.** A-11 (#217) and R-31 (#274) both edit `recon/service.py`. Rebase on both.
- **Fold check** (2026-11-09). No story in flight owns this.
  - R-14 left the work explicitly unwritten.
  - No branch has an order store or an `/orders` route.
  - The manual §4 says "There is no buyer side and no order storage."

  So it's a new story.
- **Estimate basis:** R-14 (the endpoint) took 4 h and R-29 (contract-shaped errors) 2 h, both
  actuals. This reuses both patterns and adds a contract round.

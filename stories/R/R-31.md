## Why this exists

Every reconstruction on the M2 Max hangs forever (#261). It raises no error, never times out, uses
0% CPU, and leaves the session `pending`.

The cause is two OpenMP runtimes in one process: Open3D and torch each ship their own
`libomp.dylib`. Since `4237642` (R-27's PR #250, 2026-11-05), `recon/provenance.py` imports Open3D
at module level, and `run_reconstruction_pipeline` imports it before VGGT. With Open3D loaded
first, torch's first multithreaded operation deadlocks. Loading torch first doesn't help: importing
Open3D then segfaults.

That blocks every local run, `scripts/smoke_r14.py` included. It very likely blocks the phone path
on the Mac (D-049) too.

## Acceptance criteria

- **No setup step for the person running it.** On macOS, `scripts/smoke_r14.py` on golden s-04
  completes with no OpenMP or thread variables set by hand. So does a session through
  `uvicorn recon.service:app` on the Mac (the D-049 path). The approach is the implementer's choice
  (options in the notes), but it must not swap the hang for the torch-first segfault.
- **A recurrence fails in seconds, not hours.** A regression test runs the pipeline's real import
  sequence in a subprocess with a timeout: the modules `run_reconstruction_pipeline` imports, then
  a multithreaded torch operation, then a parallel Open3D operation.
- **The cost is measured, not assumed.** Record golden s-04's stage timings with the fix
  (`stage_timings_s`) in the notes. If the fix limits threads, the slower CPU stages show up there.
- **Linux is unchanged.** The R-15 image's container tests and smoke check still pass. Linux
  behaviour doesn't change unless that's measured and recorded.

## Tests

- The subprocess regression test from the second criterion. The conflict is in macOS's wheels, so
  the test runs on macOS. Wherever it skips, it must say why.
- The D-049 phone-path session is a written manual check. CI runs on Linux with no MPS, so it can't
  run the Mac service.

## Notes and decisions

- **Evidence.** #261 has the reproduction table, the commands, and the stack trace from the real
  pipeline: `vggt/layers/vision_transformer.py:110`, a `torch.zeros` for the position embedding,
  inside `VGGT.from_pretrained`.
- **Verified workaround:** `OMP_NUM_THREADS=1` (plus `HF_HUB_OFFLINE=1` when VGGT's weights are
  cached). With it, golden s-04 through `smoke_r14` passed on the M2 Max on 2026-11-07: 60 s for
  30 frames, and 36 s and 34 s for two 15-frame subsets.
- **Options**, from #261. None is decided here.
  - Set `OMP_NUM_THREADS=1` for the service on macOS. It has to be set before either library
    initialises OpenMP, so setting it inside a request handler is too late.
  - Import Open3D lazily. That alone isn't enough, because torch first and Open3D second segfaults.
  - Give both libraries one OpenMP runtime. This needs investigation.
- **Not here:** a pipeline-wide timeout, so that a hang anywhere fails the session instead of
  leaving it `pending`. #261 notes the gap. A failure code for it is a contract change (D-031).
  No story yet.
- **Fold check** (2026-11-07). No story in flight owns this.
  - A-12 (in review, #259) doesn't touch these imports.
  - R-30, being claimed in #258, changes `fuse_run`'s board handling, not the import order.
  - Searched `stories/` and `docs/decisions.md` for libomp, OpenMP, `OMP_NUM_THREADS`, deadlock
    and #261: nothing.

  It's a defect from an already-merged story, outside every open story's scope, so it's a new
  story.
- Found on 2026-11-07, while running a 30-versus-15-photo reconstruction test on s-04 as a
  follow-up to A-12. That work is recorded as P-29.

- **Implementation 2026-11-09 (@mbj1994, PR #274):** `recon.service` imports a self-applying
  `runtime_env` guard at module import, while `agent_tools` is loaded lazily inside `create_app`.
  That guarantees the guard runs before `agent_tools -> provenance -> Open3D`, so neither Open3D
  nor torch can initialise its OpenMP runtime first. `recon/__init__.py` stays import-free for
  A-12/LaS-Comp's isolated Python 3.10 environment. On macOS the guard forces
  `OMP_NUM_THREADS=1`; on Linux and other platforms it does nothing. It deliberately overrides an
  inherited macOS value such as 4 rather than using `setdefault`, because leaving a multi-threaded
  value would recreate #261.
- The regression test runs the real service/import sequence in a subprocess, then a torch tensor
  operation and Open3D normals/raycasting, with a 30 s timeout. It is macOS-only because the
  conflict is in those wheels; Linux CI records an explicit skip. Separate unit tests pin the
  macOS setting, the no-op Linux behavior, the self-applying runtime hook, and the service import
  order that places it before `agent_tools`.
- **Real-Mac verification (2026-11-09, @TabeenRaoof, M2 Max 32 GB, macOS 26.6.2):**
  tested this PR's head `46904f9` from a clean checkout with Python 3.11.14, torch 2.14.1 and
  Open3D 0.18.0. No `OMP_*`, `MKL_*`, `OPENBLAS_*`, `VECLIB_*` or `NUMEXPR_*` variable
  was set by hand; only `PROOFSHAPE_RECON_DEVICE=mps` and `HF_HUB_OFFLINE=1` were set.
  `pytest tests/test_macos_openmp.py -q` passed **5/5 in 3.2 s**. Removing the guard makes the
  test fail, and removing both the guard and the environment assertion reproduces the actual
  deadlock and trips the 30 s timeout. The torch-first order without the guard segfaults
  (exit -11), while the guarded order completes.
- **Golden s-04 smoke:** in-process `scripts/smoke_r14.py` completed in **64 s wall** with
  `status: complete`, `metric: true`, no warnings, a 908,200-byte GLB and
  `observed_fraction = 0.0899`.
- **D-049 service path:** `uvicorn recon.service:app` completed on port 8765 in **56 s wall**
  with no manually supplied OpenMP variable. It returned the same 908,200-byte GLB and the same
  observed fraction as the in-process run.
- **Measured stage timings (s):**

  | Stage | In-process | uvicorn |
  |---|---:|---:|
  | board_detection | 3.32 | 3.28 |
  | reconstruction | 52.79 | 44.63 |
  | metric_alignment | 0.06 | 0.12 |
  | fusion | 1.88 | 1.72 |
  | export | 0.21 | 0.25 |
  | provenance | 2.12 | 2.38 |
  | uncertainty | 0.03 | 0.03 |
  | completion | 0.25 | 0.28 |
  | **sum** | **60.7** | **52.7** |

- **Measured cost of `OMP_NUM_THREADS=1`:** no regression was measurable on this M2 Max.
  Fusion was actually faster single-threaded (1.26–1.35 s vs 3.85–5.14 s at the 12-core
  default); cleanup was 0.20 s vs 0.27–0.30 s; provenance 1.71–1.72 s vs 1.72–1.79 s;
  uncertainty stayed 0.03 s; VGGT preprocess stayed about 2.8–3.0 s and MPS inference about
  20.1–21.7 s. Fusion, cleaned GLB and provenance outputs were byte-identical under both settings.
- **Linux/entry-point check:** the full macOS suite passed 971 tests with 4 skips; Ruff lint and
  format checks and the story-state checker were clean. The guard is a no-op off macOS. Current
  processes that load only torch (`reconstruction_runner`) or only Open3D (fusion, provenance,
  inspection CLIs) do not need it; any future process that loads both must import
  `recon.runtime_env` before exercising either OpenMP runtime.

## Notes and decisions

_If a decision here governs later work, add it to `docs/decisions.md` with a number._

2026-09-29: Implemented in `recon/part_segmentation.py` (`segment_part`, `segment_run`, plus a
CLI). Two things needed pinning down before writing any filtering logic, since the acceptance
criteria's wording ("sheet footprint", "above the board plane") doesn't map onto a number without
reading other files first:

- **"Sheet footprint" is the printed ChArUco pattern's rectangle**, not the physical A4/Letter
  paper edge. `docs/glossary.md` defines "Reference sheet" as "the ChArUco board (tier 1)," and no
  code anywhere in the repo detects the actual paper outline — `docs/manual.md` §3.2 flags that as
  a manual, unbuilt check (one of the "three independent scale checks" that's still aspirational).
  The pattern rectangle is the only footprint the project has an exact, already-defined geometry
  for: `recon/board_pose.py`'s `BOARD_SQUARES_X`/`BOARD_SQUARES_Y`/`BOARD_SQUARE_MM` give
  160 x 120 mm, imported rather than re-declared so the two modules can't drift. A real physical
  sheet is wider than this (manual.md's own guidance says a part larger than the pattern but still
  "roughly sheet-sized" is fine) — this module will clip such a part's overhang. Flagging this
  now rather than leaving it implicit: getting an actual sheet-outline detector wired in is real
  future scope (probably alongside the outline-based scale check manual.md describes), not
  something this 4h story attempts.
- **"Above the board plane" means negative z.** `board_pose.py`'s own docstring: origin at the
  pattern's outer corner, z = 0 on the paper, z increasing *into* the table, so "a camera above
  the board therefore has a negative z camera centre." A point above the board (the top of a part
  sitting on it) therefore has negative z; height above the board is `-z`. Given this project's
  history with exactly this kind of sign/orientation mistake (D-034's legacy-pattern flag, the
  reverted per-frame orientation claim in R-04's notes), this is pinned by an explicit unit test
  (`test_segment_part_keeps_points_above_board_by_negative_z`) rather than left to a comment.

Also extracted `apply_similarity_transform` out of `metric_alignment.py`'s
`AlignmentResult.transform_points` (now a one-line call to it) — R-06 only has the written
`metric_alignment.json` (scale/rotation/translation_mm), not a rebuilt `AlignmentResult` with its
per-frame residuals, so it needed the bare formula. Existing `AlignmentResult` tests are
unaffected; behaviour is unchanged. Added `read_ply` to `vggt_runner.py`, symmetric to the
existing `write_ply` (no PLY reader existed anywhere in the repo before this).

**"Visually verified on every golden object" is split out to R-17.** This machine has no
GPU/torch installed and `fixtures/data/recon_runs` is empty locally — R-01 needs the shared
Lightning GPU Studio (or a local Metal run), neither reachable in this session. Everything this
story actually controls (the segmentation logic, its configurability, its I/O) is done and covered
by synthetic-data unit tests (`tests/test_part_segmentation.py`), including the height/footprint
sign conventions above; what's missing is someone with GPU access actually looking at a segmented
golden-object point cloud, which is real-data verification work this story was never going to be
able to do in this session, not an unfinished part of the segmentation logic itself. Rather than
leave this story open indefinitely on a criterion it can't control (or merge it dishonestly marked
Done against an unmet criterion), that verification is split out to **R-17** — the same move R-04
made for its known-size tolerance judgment (split to R-16) when it hit the same shape of problem:
a criterion this story's own code can't satisfy on its own, needing a resource (GPU Studio time)
this session didn't have.

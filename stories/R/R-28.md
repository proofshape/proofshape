## Why this exists

`rescale_vggt_intrinsic` converts VGGT's K to full-resolution pixels by scaling each axis by full
÷ processed size. That's only right for a plain resize. VGGT centre-crops portrait frames, so on
a 1080 × 1920 frame it returns fy about 1.78 times too large (#182). R-03's VGGT fallback and
R-22's focal-ratio diagnostic both use it. R-23 already records each frame's resize and crop as
`preprocess_geometry`, but this function doesn't read it. Nothing has caught it because the live
service doesn't call it and the golden set is landscape.

Separately, R-02's `board_poses.json` records `"legacy_pattern": false` for a board built with
the legacy pattern. That's the layout that finds no corners on the real print (#188).

## Acceptance criteria

- VGGT intrinsics are rescaled from each frame's recorded `preprocess_geometry`, scale and crop
  offset both. Without it, a portrait run is refused, as `metric_alignment.py` already refuses
  one. R-03's fallback and R-22's `focal_ratio_board_over_vggt` both go through the fixed path,
  and the per-axis advice in `vggt_runner.py`'s docstring is corrected.
- `board_poses.json`'s `legacy_pattern` comes from the same place `make_board` sets it.

## Tests

- a portrait frame (for example 1080 × 1920) gives fx = fy for a square-pixel camera, and the
  principal point lands where the crop puts it;
- a landscape frame is unchanged from today;
- a portrait run with no `preprocess_geometry` is refused;
- the written board metadata matches the board R-02 actually used.

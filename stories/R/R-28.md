## Why this exists

`rescale_vggt_intrinsic` converts VGGT's K to full-resolution pixels by scaling each axis by full
÷ processed size. That's only right for a plain resize. VGGT centre-crops portrait frames, so on
a 1080 × 1920 frame it returns fy about 1.78 times too large (#182). R-03's VGGT fallback and
R-22's focal-ratio diagnostic both use it. R-23 already records each frame's resize and crop as
`preprocess_geometry`, but this function doesn't read it. Nothing has caught it because the live
service doesn't call it and the golden set is landscape.

Separately, R-02's `board_poses.json` records `"legacy_pattern": false` for a board built with
the legacy pattern. That's the layout that finds no corners on the real print (#188).

## Acceptance criteria

- VGGT intrinsics are rescaled from each frame's recorded `preprocess_geometry`, scale and crop
  offset both. Without it, a portrait run is refused, as `metric_alignment.py` already refuses
  one. R-03's fallback and R-22's `focal_ratio_board_over_vggt` both go through the fixed path,
  and the per-axis advice in `vggt_runner.py`'s docstring is corrected.
- `board_poses.json`'s `legacy_pattern` comes from the same place `make_board` sets it.

## Tests

- a portrait frame (for example 1080 × 1920) gives fx = fy for a square-pixel camera, and the
  principal point lands where the crop puts it;
- a landscape frame is unchanged from today;
- a portrait run with no `preprocess_geometry` is refused;
- the written board metadata matches the board R-02 actually used.

2026-10-30: Implementation. `rescale_vggt_intrinsic` takes `(scale_x, scale_y, crop_left_px,
crop_top_px)` — the same fields `vggt_runner.describe_vggt_crop_preprocess` already records per
frame — instead of a plain `processed_size_hw`/`full_size_hw` ratio, and inverts that resize-then-
centre-crop map using the same half-pixel-correct convention
`metric_alignment.lift_board_corner_observations`'s own forward map already uses
(`(px + 0.5) * scale - 0.5`), so both directions of the same transform agree. A new
`resolve_vggt_frame_scale` resolves each frame's own scale/crop from `preprocess_geometry`,
falling back to a plain resize ratio only for a frame that is clearly uncropped landscape (the
same backward-compat boundary `lift_board_corner_observations` already draws) — anything else is
refused by name, not guessed. Wired into both real call sites: `camera_intrinsics.
load_vggt_fallback` (R-03) and `cad_size_check._measure_board_scale_after_transform` (R-22's
`focal_ratio_board_over_vggt`). `vggt_runner.py`'s module docstring corrected to point at the
fixed function and `preprocess_geometry`, not `processed_image_size_hw` directly.

One consequence worth naming: the half-pixel-correct convention shifts every rescaled principal
point by exactly 0.5px versus the old direct-ratio formula, even for a landscape frame with no
crop (focal length is unaffected). An existing test's pinned numbers were updated to the
mathematically precise values; this is immaterial next to the reprojection RMS this project
already reports in the 1–3px range, not a behaviour change worth its own decision number.

`board_pose.py` gets one named constant, `BOARD_LEGACY_PATTERN = True`: `make_board()` and the
written `board_poses.json` metadata both read it now, instead of `make_board()` calling
`setLegacyPattern(True)` directly while a separate hardcoded `False` literal a few hundred lines
away wrote the metadata — the two had already drifted apart once.

Mutation-tested all four changes by hand: the crop-aware cx/cy formula (fails exactly the portrait
recovery test and the landscape half-pixel-shift test), the backward-compat refusal condition
(fails exactly the two refusal tests), `cad_size_check.py`'s wiring (reverting to the bypassed
call fails exactly the new wiring test, caught via a `monkeypatch` on `resolve_vggt_frame_scale`
rather than a full synthetic crop scene — changing the synthetic bundle's own `preprocess_geometry`
scale would also have disturbed `lift_board_corner_observations`'s separate, already-correct
corner-pixel mapping, which this story doesn't touch), and `BOARD_LEGACY_PATTERN` (fails exactly
the new board_pose test). Full suite 649 passed (was 639), ruff and `ruff format --check` clean,
`check_story_states.py` consistent.

2026-10-30: Review of PR #223 caught a real gap: `resolve_vggt_frame_scale`'s recorded-geometry
path trusted a frame's `preprocess_geometry` entry without checking that its own recorded
`original_size_hw`/`processed_size_hw` actually matched the caller's `full_size_hw`/
`processed_size_hw` — both parameters were only used on the fallback branch. Reproduced: a
description recorded for a 1080×1920 frame, called with `full_size_hw=(3840, 2160)`, returned a
scale silently 2x off, the same class of bug #182 itself was. Fixed by copying the same two
checks `lift_board_corner_observations` already makes before trusting a recorded entry, raising
`CalibrationFailure` instead of `ValueError` to match this module's own style. New test
(`test_resolve_vggt_frame_scale_refuses_a_recorded_frame_for_a_different_image_size`),
mutation-tested by removing both checks, which fails exactly that test, nothing else. Full suite
now 650 (was 649).

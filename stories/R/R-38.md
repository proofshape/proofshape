## Why this exists

Found on review of G-04/PR #348 (@TabeenRaoof), not invented here: `g02_02`'s capture failed
R-23's board-anchored alignment (board scale 0.831 against 0.995–0.998 for every other G-04
specimen) because of one bad frame, not a systemic problem.

Traced to the frame level: `IMG_4665` has a median per-corner residual of 124.8 mm against
every other frame's single digits (the next-worst frame in the whole G-04 set is 11 mm).
`metric_alignment`'s unweighted least-squares solve (`solve_similarity`) has no per-frame
outlier rejection, so this one frame pulls the whole fit off. R-02 posed `IMG_4665` cleanly
(1.9 px reprojection, 19 markers) and VGGT's camera centre for it is in line with the others,
so the fault is specifically in VGGT's depth at that frame's corners — the kind of thing a
per-frame residual check could catch and drop. Worse: `metric_alignment.main` prints
`R-04 ALIGNMENT: PASS` at this 23.3 mm RMS, because there is no threshold at all
(`metric_alignment.py`'s `main`) — this is a real gap in the live chain, not just G-04's own
measurement script: a session this bad would be served today with no warning.

## Acceptance criteria

- `solve_similarity` (or its caller in `load_and_align`) rejects per-frame outliers before the
  final solve — for example, an iterative trim on each frame's own residual contribution — so
  one bad frame (`g02_02`'s `IMG_4665` is the real reproduction case) doesn't set the whole
  alignment's scale. Dropping it by hand already recovers RMS 1.86 mm / scale ≈0.99 on `g02_02`'s
  real data, confirming the fix direction; the committed solve should reach something close to
  that without being told which frame to drop.
- `metric_alignment.main` gains a real residual threshold and stops printing unconditional
  `PASS` — a session whose solved alignment residual exceeds it reports a real failure/warning,
  not a silent pass. The threshold is a measured decision (D-003), not a guess: sweep it against
  every G-04/golden-set real run available (the five that pass cleanly, plus `g02_02`'s known
  failure) and record the chosen value and why in `docs/decisions.md`.
- Whether that threshold should also mark the live session `Unverifiable` (expanding that
  verdict beyond its current intake-time-only use, per `docs/glossary.md`) or a separate new
  failure mode is a real design fork — decided explicitly, as its own recorded decision, not
  assumed silently either way.
- Once this lands, `g02_02` can be re-measured and potentially rejoin G-04's aggregate instead
  of being excluded — recorded as a follow-up to D-073, not required by this story itself.

## Tests

Code change with tests written alongside it: a synthetic per-frame-outlier case (reusing the
style of `tests/test_cad_size_check.py`'s synthetic board bundles) proving the fix rejects a
planted bad frame and recovers the clean solve, plus a test that `metric_alignment.main` reports
failure on a residual above the new threshold.

## Notes and decisions

- Origin: review on G-04/PR #348 (@TabeenRaoof), 2026-11-16. Full per-frame residual numbers in
  that PR's review comments and in D-073.
- This matters beyond G-04: R-36 (demo hosting) serves live sessions through this exact chain,
  and today a 23 mm-RMS alignment would reach a real demo session with no warning.

### 2026-11-16: fixed, measured, recorded as D-075

New `solve_similarity_rejecting_outlier_frames` (`recon/metric_alignment.py`): iteratively
solves, takes each present frame's median residual, MAD-trims across those per-frame medians
(the same style as `cad_size_check.fit_board_plane`'s robust fit), drops the single worst frame
if it clears `reject_sigma_k` MAD-widths above the group's median, repeats up to
`DEFAULT_MAX_FRAME_REJECT_ITERATIONS=4` times, never below `MIN_FRAMES_AFTER_REJECTION=2`
distinct frames. `align_board_geometry` calls it in place of a bare `solve_similarity`;
`BoardAlignmentResult` gains `rejected_frame_names`/`per_frame_residual_mm` (written into
`metric_alignment.json`). `metric_alignment.main` gains `--max-residual-mm` and a real
`FAIL`/exit-1 path.

**Real sweep, all 11 available captures, no VGGT re-run needed:** `g02_02`'s `IMG_4665` is
rejected, RMS drops from 23.353 mm to 1.863 mm (matches Tabeen's own manual estimate almost
exactly, worst/threshold ratio 8.38 — an unambiguous outlier). A second, genuine but **borderline**
finding the sweep itself surfaced: `s-01` (golden set, previously thought clean) also rejects a
frame, `IMG_3927.jpeg` (7.15 mm vs 2–4 mm for its other frames) — but at worst/threshold 1.04,
right at the line, not cleanly separated like g02_02 (every other clean capture sits at
0.42–0.68). Tabeen's independent re-run got 1.02, close enough to agree, but small enough
run-to-run noise could plausibly flip it either way on a future run. Stated as borderline, not
oversold as confirmed-clean-margin. Every clean-after-fix result falls in 1.6–3.9 mm;
`DEFAULT_MAX_RESIDUAL_MM = 8.0 mm` set with real margin above that. Full table in D-075.

**Rejected frames are now skipped at fusion too, not only at alignment (review on PR #358,
@TabeenRaoof — caught after the first version of this fix only touched alignment):**
`rejected_frame_names` was written to `metric_alignment.json` but nothing downstream read it, so
`IMG_4665`'s own bad depth still reached `tsdf_fusion.fuse_run` and crashed fusion once the
alignment itself was correct, with an error that didn't name the real cause — safer, but not the
recovery this story described. `fuse_run` now drops any rejected frame's depth before it reaches
the volume. Confirmed this lets g02_02 actually recover end to end (Tabeen's scratch test,
deleting `IMG_4665` from a copy of its npz files): fusion runs on the remaining 29 frames, board
scale 0.9989, height error −0.17 mm against caliper truth — inside D-073's 0.86 mm σ_floor.

**The live service never checked the residual either (review on PR #358, @mbj1994):**
`recon/service.py::run_reconstruction_pipeline` called `load_and_align` directly and went
straight to fusion, never through `metric_alignment.main`, so `--max-residual-mm` only existed
on the CLI. A live session over the threshold now raises the pipeline's existing
`metric_alignment_failed` right after alignment, before fusion starts — with a test proving
`fuse_run` is never called once the gate fires.

**Design fork, decided explicitly:** the residual failure is `metric_alignment.main`'s own new
`FAIL`, not wired into the `Unverifiable` verdict — no verdict-computation code exists anywhere
in the repo today to extend by analogy (`GET /v1/sessions/{id}/verdict` unconditionally 404s),
so that would be inventing new machinery, not a code hookup. `declared_at`'s unused
`"post_reconstruction"` value is flagged in D-075 for whoever builds real verdict logic next.

**Known limit, recorded not hidden:** this is a single-shot threshold on the initial
(uncorrected) solve. A severe enough single-frame corruption (confirmed separately: a
synthetic ~2x-true-depth corruption collapses the fitted scale toward zero) can distort that
initial solve badly enough that the corrupted frame's own residual no longer stands out. The
real g02_02 failure (scale pulled to 0.83, not collapsed) is well within what this handles; a
more severe future failure is not guaranteed to be caught by this design. The MAD threshold also
has no absolute floor (noted in D-075).

**Not done here, explicitly out of scope per this story's own acceptance criteria:** G-04's
aggregate is not re-run; `g02_02` could now rejoin it (with real evidence it would land within
tolerance), left as a follow-up. `s-01`'s newly-rejected frame changes its `metric_alignment.json`
going forward; other stories' historical numbers computed from the old alignment are not
retroactively audited.

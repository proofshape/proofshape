## Why this exists

VGGT scores every pixel's depth with a confidence. R-01 keeps all of them: `--min-confidence`
defaults to 0.0, because, in `recon/vggt_runner.py`'s own words, "no threshold has been measured
yet." R-07's fusion doesn't read the confidence at all. R-17 measured the result on all five golden
objects:
- 11.5–29.3% of the segmented points are stray points, not the part.
- About three-quarters of pixels sit at VGGT's confidence floor.
- As a diagnostic, dropping points below 1.5 cut stray points to 1.1–2.3% with the part's measured
  size unchanged.

R-18's fused meshes for s-03/s-04/s-05 failed with both fusion methods. Fusing those same
low-confidence pixels is the leading suspect, but nobody has tested it.

## Acceptance criteria

- R-01's default confidence threshold is chosen from measurement on the golden set, not guessed.
  For a range of thresholds, report the stray-point fraction and how much of the part survives;
  s-04 and s-05 can be checked against their CAD. Record the chosen value and its evidence in
  `docs/decisions.md`, and change the CLI default.
- R-07's TSDF fusion uses VGGT's per-pixel confidence, so a pixel left out of the cloud is left out
  of the fused surface too. Whether it masks or weights is the owner's call; record it.
- R-18's check (`fuse_run`, default and `--method poisson`) is rerun on all five golden objects. The
  per-object results are recorded beside R-18's, so the before and after can be compared.

## Tests

Synthetic depth maps where a low-confidence spurious region must not appear in the fused TSDF.
Check the same test fails with confidence ignored, so it is known to catch the problem. The chosen
threshold must reach `run.json` from the CLI. The golden-set rerun is a manual check, the same
exception R-17 and R-18 use: judging a real fused mesh is a human look.

## Notes and decisions

2026-10-09 (when written up, from R-17's findings):
- **Don't overshoot.** At confidence ≥ 5, s-05 kept 27,484 of 129,140 segmented points, and its
  walls became too sparse to measure. The useful range in R-17's diagnostic was well below that.
- **R-21 interacts with the mesh rerun.** `fuse_run` applies R-06's `segment_part`, so the part's
  base is cut off in the fused mesh too. Fusing an open-bottomed shell may itself hurt R-18's
  Poisson results. R-21 landing first would make this story's rerun more telling, but it isn't a
  hard dependency.

2026-10-11 (implementation):

**Shared predicate.** `recon.vggt_runner.confidence_keep_mask(confidence, min_confidence)` is the
one function that decides "is this pixel trusted" -- `select_point_cloud` (R-01's cloud) and
`recon.tsdf_fusion.fuse_run` (R-07's fusion) both call it on the same `depth_conf` array, so a
pixel dropped from `points.ply` is dropped from the fused surface too, by construction, not by two
independently-reimplemented checks that could drift apart.

**Mask, not weight** (the acceptance criteria left this to the owner). Fusion drops a pixel
exactly when R-01 drops it from the cloud: same predicate, same threshold. Weighting would add an
unmeasured knob, and VGGT/MASt3R/COLMAP's confidence scales aren't comparable, so a weighting
function would need its own measurement this story doesn't have time for.

**The threshold: measured with `recon/confidence_sweep.py`** (replacing R-17's one-off script),
swept on all five real golden-set runs locally (Metal, no Studio access needed since this only
reads already-persisted `depth.npz`/`poses.npz`/`metric_alignment.json`). Cross-checked against
R-17 first: the no-threshold baseline stray fractions (19.2/18.7/11.4/29.3/17.7% for
s-01..s-05) reproduce R-17's reported 19.3/19.0/11.5/29.3/17.7% almost exactly, and R-17's own
1.5 diagnostic reproduces its reported 1.1-2.3% band.

The result was not the one expected going in: almost all of the achievable stray-fraction
reduction is captured the instant the threshold clears VGGT's *exact* confidence floor of 1.0 (the
median pixel sits exactly there on every object); pushing the threshold any higher, including to
R-17's own 1.5 diagnostic, buys negligible further cleanup while steadily costing real part
coverage. A fine-grained sweep right above the floor (1.00001, 1.0001, 1.001, 1.01, 1.05, 1.1)
confirmed the knee sits at the floor itself, not partway up the scale -- see **D-045** for the
full reasoning and the baseline/chosen/R-17-diagnostic comparison table. **Chosen:
`DEFAULT_MIN_CONFIDENCE = 1.0001`.**

Full sweep (stray fraction / part voxel coverage against the threshold-0 baseline), all five
objects, `confidence_sweep.json` written beside each run (git-ignored, under
`fixtures/data/recon_runs/<s>/`):

**A real caveat on s-01/s-02's coverage numbers:** their threshold-0 baseline cluster's x/y extent
is exactly 160x120mm -- the full board pattern, not the padlock. R-17 already found s-01/s-02's
baseline includes a spurious raised board-grid layer spanning the whole board, so for these two
objects specifically, "coverage vs. baseline" is partly measuring recovery of that spurious layer,
not just the part. R-17's own independent CAD check (on s-04/s-05, which don't have this
contamination) is why 1.5's "part's measured size unchanged" claim was trusted over my own
coverage metric when the two were in tension.

**Dispatcher (`recon/reconstruction_runner.py`).** `run_on_capture`'s `min_confidence` default
changed from `0.0` to `None`, meaning "defer to the selected backend's own default" rather than
forcing one number on all three: VGGT gets the new measured D-045 default; MASt3R and COLMAP stay
at `0.0` (MASt3R's confidence is a different, unmeasured scale; COLMAP's is a binary validity mask
that already refuses any nonzero threshold). This is what lets `recon/service.py`'s pipeline (which
calls the dispatcher with no `min_confidence` at all) pick up the new default without touching it.

**`fuse_run` reads its threshold from the run's own `run.json`** by default
(`min_confidence_source: "run.json"`), not a fixed number, so the fused surface always matches
whatever `points.ply` was actually built with for that run -- a run whose `run.json` predates this
field (or is missing) is an explicit error, never a silent 0.0. An explicit `min_confidence`
overrides it, which is what the golden-set rerun below uses to test both before and after against
the *same* existing (pre-R-20) runs.

**Tested that the tests actually catch the regression**, not just inspected the diff: temporarily
removed the confidence `&` from `fuse_run`'s `keep_mask` locally, reran
`tests/test_tsdf_fusion.py -k confidence`, confirmed the marching-cubes wiring test and the
Poisson-path test both failed (two iterations -- the first attempt's "spurious" test pixel turned
out to land outside the default footprint, so segmentation alone excluded it and the bug went
undetected; moved it to an in-footprint location so confidence is the only thing that can tell the
two points apart), then reverted and confirmed all tests pass again on the real code.

**Golden-set rerun (R-18's acceptance criterion, manual check).** Ran `fuse_run` on all five
golden objects, both methods, at `--min-confidence 0.0` (reproducing R-18's original, unfiltered
input exactly, since it reads the same pre-existing `fixtures/data/recon_runs/<s>/` as R-18/R-17
used) and `--min-confidence 1.0001` (the chosen default), using R-07's own default voxel size (2mm)
and R-06's default footprint/height. Rendered with matplotlib (equal aspect, `-z` as height --
R-17's lesson) since no mesh viewer is installed on this machine.

*Marching cubes, visual review by @TabeenRaoof:* **not a pass on any of the five**, matching R-18.
The unfiltered (t=0) meshes are a dense, noisy tangle with no recognizable part on any object,
consistent with R-18's "banding/corrugation... no recognizable shape." At the chosen threshold,
every object is visibly and measurably less noisy (28-48% fewer vertices; fewer scattered
fragments; s-04 in particular shows real flat planar facets that plausibly correspond to the
prism's faces) -- but none closes into a recognizable, roughly-closed part mesh. This matches
R-17's own prediction when it filed this story: R-20 addresses one of three causes it found (stray
low-confidence points), while the base cut landing above the real board (R-21) and the part
reconstructing smaller than its CAD (R-22) are separate, still-uncorrected factors likely keeping
these meshes from closing.

| Object | R-18 (default method) | Local t=0 (reproduction) | Local t=chosen (1.0001) |
|---|---|---|---|
| s-01 | Not independently checked (see notes) | Noisy tangle, no recognizable shape | Visibly less noise (70,010→50,161 v, -28%); still no recognizable shape |
| s-02 | Banding/corrugation, large holes, not a pass | Noisy tangle, no recognizable shape | Less noise (56,113→40,557 v, -28%); still not a pass |
| s-03 | One recognizable patch in a chaotic shard halo | Noisy tangle, no recognizable shape | Less noise (44,617→25,674 v, -42%); still not a pass |
| s-04 | Banding/corrugation, large hole, not a pass | Noisy tangle, no recognizable shape | Markedly less noise (63,744→33,352 v, -48%); real flat facets visible but still fragmented, not closed |
| s-05 | Not independently captured | Noisy tangle, no recognizable shape | Less noise (46,363→26,445 v, -43%); still not a pass |

*Poisson: could not be completed on this machine.* Installing Open3D (0.20.0, then 0.18.0 to rule
out a version regression) and running `extract_mesh_poisson` -- even called directly on R-06's
already-segmented `segmented_points.ply`, with no R-20 code in the path at all -- crashes with a
native, non-Python-catchable abort inside Open3D's bundled PoissonRecon (`Failed to close loop`,
`libc++abi: terminating`) on every one of the five objects, including s-01/s-02, the two R-18
reported passing cleanly. Reproducing it at `--min-confidence 0.0` (numerically identical input to
pre-R-20 fusion) and via a direct `extract_mesh_poisson` call confirms this is a pre-existing
Open3D/macOS-ARM64 platform issue, not something this story's confidence change caused -- R-18's
successful Poisson runs were on a different platform (the Lightning Studio) with an unpinned,
unrecorded Open3D version. **The Poisson half of this story's rerun is genuinely incomplete**;
someone with Studio/Linux access (or a working macOS Open3D build) needs to finish it. Not filed as
its own story here, the same call R-18 made for its own parameter-tuning gap -- flagging it
precisely so whoever has that access next doesn't have to rediscover it.

**Provenance gap, deliberately not fixed here.** `recon.provenance.compute_observations` also
reads `depth.npz` and counts a frame as "observing" a vertex using the same per-pixel depth
samples -- including low-confidence ones R-20 now excludes from the cloud and the fused surface.
A vertex built only from trusted pixels could still be labelled Observed with help from a
distrusted one. This doesn't regress anything (the gap already existed before R-20), but it
touches the hard rule (AGENTS.md: unobserved geometry must never assert a pass/fail), so it isn't
a "note and move on" -- **filed as R-23**, since changing it moves `observed_fraction` and R-10's
sigma distribution, which deserves its own review rather than riding in on this story's diff.

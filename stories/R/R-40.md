## Why this exists

Every live session goes through `mesh_cleanup.cleanup_run` (`recon/service.py:521`), then
provenance. Two known defects there can end a session that reconstructed correctly, and both are
on the demo host's path (D-072).

- **#263, an endless loop.** `write_glb_with_size_limit`'s re-decimation loop
  (`recon/mesh_cleanup.py:325-337`) never checks whether a round reduced the mesh. If
  `decimate_mesh` stalls above `min_triangle_count` while the GLB is still over the size limit,
  it repeats forever. #263's reproduction loops more than 25,000 times in 5 s. Nothing in the
  pipeline has a timeout, so the session would stay `pending`. It hasn't been seen on a real
  mesh.
- **#300, decimation breaks manifoldness.** `cleanup_run` drops non-manifold faces first (R-30),
  then decimates to 50,000 faces (`DEFAULT_TARGET_TRIANGLE_COUNT`), and nothing checks again. On
  R-32's MASt3R s-05 meshes (63,347 and 64,965 faces), decimation created 26 and 36 non-manifold
  edges. Provenance then refused them (`recon/provenance.py:135`). In the live service that
  failure now reaches `run_session`'s catch-all, so the supplier gets `internal_error`. VGGT's
  golden meshes are 31–41k faces, so they never decimate. A larger part, or more frames, would.

## Acceptance criteria

- **#263:** a round that doesn't reduce the face count raises the existing "cannot be decimated
  further" `ValueError`, whatever `min_triangle_count` is.
- **#300:** after decimation, and after every re-decimation in `write_glb_with_size_limit`, no
  edge is shared by more than two faces. Dropping non-manifold faces again, or any equivalent
  that guarantees it, is fine. The cleanup's output is "manifold", and that's tested.
- **R-32's two failing runs complete.** MASt3R s-05 "all" and "half0", from their saved artifacts
  (outside git, CPU only), go through cleanup and provenance on the fix. Their face and
  non-manifold-edge counts are recorded.
- **#247 re-checked.** One golden object's Poisson mesh goes through the new cleanup into
  provenance. If it passes, #247 is closed with that evidence. If not, it stays open with the new
  count.

### 2026-11-18: review found two more issues (PR #381, @mbj1994)

- **Blocker 1, the #263 regression test didn't actually protect CI.** The original test ran
  `write_glb_with_size_limit` on a `ThreadPoolExecutor` worker and timed out `future.result()`
  at 5 s — but a Python thread can't be killed, and `concurrent.futures` joins its worker
  threads at interpreter exit regardless of any `.result(timeout=...)` on the caller's side. If
  the fix ever regressed to the old infinite loop, this test would print a timeout failure and
  then the whole pytest process would hang forever anyway, joining that thread. Fixed by running
  it in a real `multiprocessing.Process` instead: `.join(timeout=5.0)`, and if still alive,
  `.terminate()` + `.join()` to actually kill and reap it before failing the test. Verified by
  hand: temporarily reverted the #263 fix, confirmed the test now fails cleanly at ~5.5 s instead
  of hanging, then restored the fix and confirmed it passes again. (The subprocess target has to
  be a module-level function and apply the `decimate_mesh` patch *inside the child* —
  `pytest`'s `monkeypatch` fixture only touches the parent process's module object, which a
  spawned child never inherits.)
- **Non-blocking note, addressed anyway.** `non_manifold_faces_dropped_after_decimation` only
  reported `cleanup_run`'s own post-decimation drop, silently missing any drops from
  `write_glb_with_size_limit`'s re-decimation rounds. `write_glb_with_size_limit` now returns
  that round-by-round sum as a 5th tuple element (all three callers in this repo updated:
  `cleanup_run` and two direct test calls), and `write_cleanup_report` carries it as its own
  field, `non_manifold_faces_dropped_during_size_redecimation`, kept separate from the other two
  non-manifold-drop fields rather than summed together — each field now names exactly which
  stage caused it.
- **Blocker 2, R-32's two MASt3R runs, still open.** mbj1994's review is right that the story
  can't just say this acceptance criterion is undone without either the real numbers or an
  explicit waiver. I don't have those artifacts and can't get them from this machine. Asked
  the owner (@dalwalyk) whether they have access or want this escalated to R-32's owners
  (@mbj1994, @TabeenRaoof) for an explicit decision.
- Re-ran everything after both fixes: `tests/test_mesh_cleanup.py` 32/32, full suite 1365
  passed, `ruff check`/`ruff format --check` clean, `check_story_states.py` clean.

### 2026-11-18: R-32's real runs found a third, distinct defect (PR #381, @TabeenRaoof)

@TabeenRaoof had R-32's saved Colab artifacts locally and ran the acceptance check this story
couldn't run on this machine. Result: **half0 now completes** (0 non-manifold edges, provenance
succeeds, 1.46% Observed — consistent with R-32's own weak-MASt3R-on-s-05 finding, not a new
concern). **"all" still fails, but on a different error**: not `non-manifold edge ... belongs
to N faces` any more (`drop_non_manifold_faces` already fixed that — 0 non-manifold edges on
this head), but `mesh winding is topologically contradictory`. Decimation can fold a few faces
into a winding no single per-face flip can resolve — manifold (every edge has ≤2 owners) but
not orientable. Same root cause as #300 (decimation breaks a property the input had), a
different property than `drop_non_manifold_faces` checks.

**Fix**: two new functions in `recon/mesh_cleanup.py`, `_find_orientation_conflict` (the same
flood fill as `provenance._orient_faces_with_groups`, reimplemented rather than imported —
`provenance.py` already imports from `mesh_cleanup.py`, so the reverse import would be
circular — returning the first conflicting face pair instead of raising) and
`drop_faces_until_orientable` (drops both faces on each conflict, re-checks manifoldness, and
retries; always terminates since each round strictly reduces the face count). Called right
after `drop_non_manifold_faces` at both existing call sites (`cleanup_run`'s own decimation, and
every round of `write_glb_with_size_limit`'s re-decimation loop). Two new report fields,
`non_orientable_faces_dropped_after_decimation` and
`non_orientable_faces_dropped_during_size_redecimation`, kept apart from the non-manifold-drop
fields the same way those are kept apart from each other.

**Tested**: a minimal non-orientable manifold (5 faces on a 5-vertex ring, `(i, i+1, i+2 mod
5)` — every edge has exactly 2 owners, but no combination of per-face flips makes the winding
consistent; confirmed by hand against `_find_orientation_conflict` before writing the fix) —
unit tests for both new functions, plus end-to-end tests at both call sites (a fake
`decimate_mesh` that decimates for real, then grafts the ring onto 5 new, otherwise-disconnected
vertices, the same isolation pattern the existing non-manifold-injection tests use). 38/38 in
`tests/test_mesh_cleanup.py` (6 more than before), full suite 1371 passed, `ruff
check`/`format --check` clean, `check_story_states.py` clean. Re-ran the real #247 Poisson check
on golden `s-04` after this change: identical result to before (47,415 faces, 0 non-orientable
drops — that mesh just didn't hit this particular defect), provenance still accepts it.

## Why this exists

Every live session goes through `mesh_cleanup.cleanup_run` (`recon/service.py:521`), then
provenance. Two known defects there can end a session that reconstructed correctly, and both are
on the demo host's path (D-072).

- **#263, an endless loop.** `write_glb_with_size_limit`'s re-decimation loop
  (`recon/mesh_cleanup.py:325-337`) never checks whether a round reduced the mesh. If
  `decimate_mesh` stalls above `min_triangle_count` while the GLB is still over the size limit,
  it repeats forever. #263's reproduction loops more than 25,000 times in 5 s. Nothing in the
  pipeline has a timeout, so the session would stay `pending`. It hasn't been seen on a real
  mesh.
- **#300, decimation breaks manifoldness.** `cleanup_run` drops non-manifold faces first (R-30),
  then decimates to 50,000 faces (`DEFAULT_TARGET_TRIANGLE_COUNT`), and nothing checks again. On
  R-32's MASt3R s-05 meshes (63,347 and 64,965 faces), decimation created 26 and 36 non-manifold
  edges. Provenance then refused them (`recon/provenance.py:135`). In the live service that
  failure now reaches `run_session`'s catch-all, so the supplier gets `internal_error`. VGGT's
  golden meshes are 31–41k faces, so they never decimate. A larger part, or more frames, would.

## Acceptance criteria

- **#263:** a round that doesn't reduce the face count raises the existing "cannot be decimated
  further" `ValueError`, whatever `min_triangle_count` is.
- **#300:** after decimation, and after every re-decimation in `write_glb_with_size_limit`, no
  edge is shared by more than two faces. Dropping non-manifold faces again, or any equivalent
  that guarantees it, is fine. The cleanup's output is "manifold", and that's tested.
- **R-32's two failing runs complete.** MASt3R s-05 "all" and "half0", from their saved artifacts
  (outside git, CPU only), go through cleanup and provenance on the fix. Their face and
  non-manifold-edge counts are recorded.
- **#247 re-checked.** One golden object's Poisson mesh goes through the new cleanup into
  provenance. If it passes, #247 is closed with that evidence. If not, it stays open with the new
  count.

## Tests

Written with the fix:
- #263's stalled-`decimate_mesh` reproduction, asserting a `ValueError` under a timeout so a
  regression fails instead of hanging CI;
- a mesh that decimation actually makes non-manifold (derived from R-32's s-05 meshes or built
  synthetically), asserting the cleanup output has no edge with more than two faces;

## Implementation notes

### 2026-11-18: fix and real-data check (@dalwalyk)

- **#263 fix.** `write_glb_with_size_limit`'s loop now records the face count before each
  `decimate_mesh` call and raises the existing "cannot be decimated further" `ValueError`
  whenever a round doesn't actually reduce it, regardless of `min_triangle_count` — matching the
  acceptance criterion's "whatever `min_triangle_count` is." Tested with a monkeypatched
  `decimate_mesh` that never reduces, run on a background thread with a 5 s
  `concurrent.futures` timeout, so a regression fails the test fast instead of hanging CI.
- **#300 fix, both call sites.** `drop_non_manifold_faces` is now called again right after
  decimation: once in `cleanup_run` (after its own `decimate_mesh` call), and once per round
  inside `write_glb_with_size_limit`'s loop. `write_cleanup_report` gained a new field,
  `non_manifold_faces_dropped_after_decimation`, kept separate from the existing
  `non_manifold_faces_dropped` (R-30's pre-component-filter count) since the two have different
  causes. Both call sites have a dedicated synthetic regression test (built the way the story's
  own Tests section allows): a fake `decimate_mesh` that decimates for real, then injects one
  extra face reusing an existing shared edge, pushing that edge from 2 owners to 3. Each test
  asserts the final output has no edge with more than 2 owners.
- **#247 re-checked for real, not just a repro.** Ran the real pipeline locally (CPU only, no
  GPU needed for Poisson) on the golden `s-04` capture using the cached data in
  `fixtures/data/recon_runs/s-04`: `tsdf_fusion.fuse_run(method="poisson")` →
  `mesh_cleanup.cleanup_run` (fixed) → `provenance.provenance_run`.
  - Raw Poisson mesh: 201,203 vertices, 403,622 faces, **1,215 non-manifold edges, max 4
    owners** — matches #247's own reported range (1,164–4,578 edges) exactly.
  - After the fixed `cleanup_run`: `non_manifold_faces_dropped` (pre-component-filter) 3,760;
    `non_manifold_faces_dropped_after_decimation` (the new check) 2,585; final mesh 47,415 faces,
    **0 non-manifold edges**.
  - `provenance.provenance_run` on that cleaned GLB **succeeded** (no `ValueError`).
  - **#247 is closed by this evidence.**
- **R-32's two failing runs were not re-run.** The acceptance criterion asks for MASt3R s-05
  "all" and "half0" from their saved artifacts (outside git, produced on a Colab T4,
  `R-32-mast3r-colmap-executed-2026-11-11.ipynb`). Those artifacts are not on this machine —
  confirmed with a filesystem-wide search, same gap as the `sess_*` phone-capture data noted on
  PR #378. Whoever has that notebook/output needs to run the fixed `cleanup_run` on those two
  meshes and record the before/after face and non-manifold-edge counts here.
- Full `tests/test_mesh_cleanup.py` suite: 32/32 pass (6 new). Full repo suite: 1365 passed
  (up from 1363; same pre-existing unrelated `test_fixture_ignore_rules.py` caveat already
  documented elsewhere when real fixture data is symlinked into a scratch worktree — not
  triggered in a normal checkout). `ruff check`/`ruff format --check` clean.
  `check_story_states.py` clean.

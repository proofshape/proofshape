## Notes and decisions

_Written while working. What you tried, what surprised you, what you chose and why._
_If a decision here governs later work, add it to `docs/decisions.md` with a number._

2026-09-29: Implemented in `recon/tsdf_fusion.py` (`build_voxel_grid`, `fuse_tsdf`,
`extract_mesh_marching_cubes`, `extract_mesh_poisson`, `fuse_run`, plus a CLI). The one genuinely
hard piece, worked out before writing any fusion code: TSDF fusion is voxel-projection based — for
every voxel, project it into every frame's camera and compare against that frame's measured depth
— which needs each frame's camera pose *in the board frame*, not just points in the board frame
(all R-04 produces). Derived and added
`recon.metric_alignment.apply_similarity_transform_to_extrinsic`:

- R-01's extrinsic is `x_cam = R_o @ x_world + t_o` (arbitrary units); R-04's transform is
  `x_board_mm = scale * (rotation @ x_world) + translation`. Substituting one into the other and
  multiplying through by `scale` (so camera-space coordinates come out in the same millimetres as
  `x_board_mm`, not R-01's arbitrary units) gives `R_board = R_o @ rotation.T` (a proper rotation —
  two orthonormal matrices compose cleanly) and `t_board = scale * t_o - R_board @ translation`.
  Depth used with the derived extrinsic must be pre-scaled by `scale` (intrinsics stay unchanged —
  a pixel-to-ray direction is scale-invariant).
- Given this project's history with exactly this class of silent bug (D-034, R-04's reverted
  orientation claim, R-06's z-sign), this derivation isn't just commented — it has a direct test
  and a cross-check test (`tests/test_metric_alignment.py`) that composes it with
  `unproject_depth_to_world` and confirms it lands on exactly the same points
  `apply_similarity_transform` gives directly, not just "looks reasonable."

TSDF fusion (`fuse_tsdf`) projects every voxel into every frame (vectorized across voxels per
frame), truncates the signed distance, and accumulates a running weighted average; voxels far
behind a measured surface from a given frame get no update at all from it (occlusion is unknown,
not "very occupied"), while voxels far in front are clipped to `+truncation_mm` (still a solid
"definitely empty" signal). Masking reuses `recon.part_segmentation.segment_part` directly on each
frame's board-frame unprojected points, so board/table/hand pixels never contribute — no
segmentation logic is re-derived. `extract_mesh_marching_cubes` masks out never-observed voxels
from skimage's `marching_cubes` (its `mask` parameter) so unobserved space can never fabricate a
surface, mirroring the hard rule's "unobserved geometry never asserts anything" at the meshing
level; it also treats skimage's "No surface found" (too few/sparse observations to close a
surface) as a legitimate empty-mesh outcome, not a crash.

**Dependency decision:** `scikit-image` (marching cubes) is added to `requirements.txt`/CI — it's
CPU-only, lightweight, and needed by every run. Open3D (the Poisson fallback only) is imported
lazily inside `extract_mesh_poisson`, the same pattern R-01 uses for torch/VGGT, and is
deliberately **not** in `requirements.txt`/CI — a much heavier, GUI-adjacent dependency for a
fallback path not exercised by default. Its test is gated with `pytest.importorskip("open3d")`.

**"Produces a mesh for every golden object" is split out to R-18.** Same gap as R-06→R-17: this
machine has no GPU/torch and no local `fixtures/data/recon_runs`, so real R-01/R-04 output for the
five golden objects isn't reachable in this session. Everything this story actually controls (the
board-frame extrinsic derivation, the TSDF fusion math, marching cubes, the Poisson fallback, the
mesh I/O) is done and covered by synthetic-data unit tests (`tests/test_tsdf_fusion.py`).

## Why this exists

C-02 proved the permission prompt and a single preview frame — enough to answer "does
`getUserMedia` work here," nothing more. Real capture needs the stream to keep running under the
user's control, grab a still frame on demand paired with the gyro reading at that instant, and
release the camera when the session ends. Every later story — C-06's gate, the actual upload
flow — operates on frames this story is what produces.

## Acceptance criteria

- From C-04's shell, the camera stream stays running (not stopped after one preview like C-02)
  until the session ends, and a "capture frame" action grabs the current video frame as image
  data without restarting the stream on every capture.
- Each captured still is paired with the gyro reading at the moment it was grabbed (reusing C-03's
  live orientation values), never a stale or default reading.
- Ending the session actually stops the `MediaStream`'s tracks — C-02 never had to handle this,
  since it never ran longer than one frame; a continuous stream left running is a real
  camera-stays-on bug, not a hypothetical one.

## Tests

Frame-grab logic (canvas draw plus gyro pairing) is pure and testable against a fake video
element and fake gyro state. Stream start/stop and track release use the same `getUserMedia`
mocking pattern C-02 already established — assert `.stop()` is called on every track.

Manual check (device, iOS/Safari version, steps, result): whether a real phone's video element
keeps delivering usable frames over a longer live session (minutes, not one snapshot) — duration
and real-hardware stability aren't something a mock stream can stand in for, the same reasoning
C-02/C-03 used for their own device checks.

## Notes and decisions

2026-10-14: Implemented in `capture/src/camera.ts` (stream/capture/teardown logic) and
`capture/src/shell.ts` (wiring into the one real app flow).

**`requestCameraPermission`'s contract changed in place, rather than adding a parallel
function.** It now hands back the granted `MediaStream` instead of stopping its tracks
immediately — the stop-loop (and the comment explaining why it existed, one story early) is
gone. No new function needed: the old C-02 demo page (`mountCameraCheck`) does its own direct
`getUserMedia` call and never called `requestCameraPermission` at all, so this was the only call
site and changing it in place was safe.

**Captured frames are stored as `state.lastCapturedFrame`, overwritten on each capture — not an
array.** C-09 ("Capture loop," not yet built) is what will actually consume/accumulate frames
into the gate-then-upload flow; building accumulation, dedup, or a queue here would be inventing
a later story's job ahead of time. A single overwritten field is the minimal thing that honestly
satisfies this story's own acceptance criteria (a capture action that grabs a still paired with
the live gyro reading), with nothing yet claiming to own what happens to it after.

**Gyro-pairing nullability lives in the caller, not the pure capture function.** `captureFrame`
takes a concrete `Gyro`, not `Gyro | null` — "never a stale or default reading" is enforced by
`shell.ts`'s click handler refusing to call it at all when `state.latestGyro` is still `null`
(no orientation event has fired yet), rather than threading optionality into the pure function
and inventing a default there.

**`capturePixelsFromVideo` throws on a zero-dimension video** (`videoWidth`/`videoHeight` both
0, i.e. not yet playing) rather than silently handing back an empty/garbage frame. Draws into an
offscreen canvas and reads back real `ImageData`, which satisfies `FramePixels` structurally with
no adapter needed — exactly what `frame_gate.ts`'s own forward-looking comment (C-06) expected.

**Teardown is tied to a confirmed-successful finish, not to the click itself.** `stopCameraStream`
is only called after `finishSession` resolves `ok: true` — not on the not-ok branch, not in the
catch block — since the session genuinely hasn't ended in either of those, and stopping the
camera on a finish attempt that didn't actually finish would be a worse bug than the one this
story exists to fix.

**Testing the canvas path needed a stub, not a real one.** happy-dom's `HTMLCanvasElement` has no
real 2D rendering, so `capturePixelsFromVideo`'s tests (and `shell.test.ts`'s capture-button
integration test) stub `HTMLCanvasElement.prototype.getContext` with a fake context
(`drawImage` spy, `getImageData` returning known data) and override a real `<video>`'s
`videoWidth`/`videoHeight` via `Object.defineProperty` (both read-only 0 in happy-dom). This is
what the story's own "fake video element" framing meant in practice.

**`shell.test.ts`'s camera-grant status message changed from "Camera permission granted." to
"Camera started."** — two pre-existing tests updated accordingly. The stream is now kept alive
and attached to a real preview, so "started" is the more accurate claim; also had to make
`stubGrantedCamera`'s fake stream a real `new MediaStream()` (with `getTracks` overridden)
rather than a plain object, since happy-dom's `srcObject` setter validates the value is a real
`MediaStream` instance — the old plain-object stub only had to satisfy `getTracks()`, never
`srcObject`, since the stream was previously discarded immediately.

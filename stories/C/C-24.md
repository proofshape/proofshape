## Why this exists

R-36's home pre-check (2026-11-16) found two ways an interruption breaks a supplier's session on
the demo path (D-072). Both were filed from it.

- **#351, the outage message.** With uvicorn stopped, the phone showed "Could not upload frame —
  uploadFrame: response body was not valid JSON (status 500):" (session `sess_2e59418b1077`). On
  the D-049 path, Vite's proxy answers an unreachable backend with a 500 and an empty body.
  `readJsonBody` (`capture/src/api.ts:20-26`) throws on it, and `describeNetworkError`
  (`capture/src/messages.ts:39-44`) passes every non-`TypeError` message through unchanged, which
  `messages.test.ts:114` pins. The session itself was fine: after the service restarted, it
  continued in the same session and finished, both times R-36 tried it (91 s and 138 s outages).
  The supplier just had no way to know that.
- **#352, a reload loses the session.** The supplier switched to Messages mid-capture
  (`sess_9cd4d8e064eb`, 6 frames). Returning to Safari reloaded the page, and the app came back
  with no session. `AppState` (`capture/src/shell.ts:40-57`) keeps the session id only in
  memory, and the accepted gyro readings that coverage is rebuilt from are in memory too. The
  server-side session stays `capturing` for good.

At the defense or the expo, either one ends a live demo that the service could have finished.

## Acceptance criteria

- **#351:** a 5xx reply whose body isn't JSON is shown as an actionable message, not the raw
  `readJsonBody` text. Something like "The service isn't reachable right now. Wait a moment and
  capture again; your earlier frames are kept." This applies to every call that reads a body
  (upload, finish, the reconstruction poll and the agent message), not only upload. A 5xx with a
  JSON error body, and every frozen error code, display as they do today. The test at
  `messages.test.ts:114` is changed on purpose, with the reason stated, not deleted.
- **#352:** the session id, the accepted-frame count and the accepted gyro readings are kept in
  `sessionStorage` (or the URL; see Notes). On load, a stored session that hasn't finished is
  offered as "Continue session", and continuing sends the next frame to that same session.
  Starting a new session or finishing one clears the stored state. Declining starts a fresh
  session.
- **No contract change (D-031).** Continuing uses only existing endpoints. The server numbers
  frames from its own count (`SessionStore.add_frame`), so a frame the server accepted whose 202
  never reached the phone still lands at the right index. The client's stored count is for
  display only, and the next 202's `frame_index` corrects it.
- **Checked on the iPhone, and the manual updated.** R-36's two cases are repeated on the Mac
  demo path (D-072): switch to another app mid-session, come back, continue and finish; and stop
  uvicorn mid-session, see the new message, restart it, continue and finish. `docs/manual.md`
  §9 ("When something goes wrong") says what the supplier does in each case.

## Tests

Written alongside the code:
- `api.test.ts` and `messages.test.ts`: a 500 with an empty body, a 502 with an HTML body, and a
  500 with a JSON `ErrorDetail` body. Only the first two give the new message.
- `shell.test.ts`: state persisted after an accepted frame; offered and restored on mount; cleared
  on finish and on a new session; a corrupt or partial stored value is ignored with a fresh
  session, never a crash.

**Manual check, and why:** iOS discarding and reloading a backgrounded Safari tab, and Vite's proxy
answering for a stopped backend, only happen on the real device and dev server. The fourth
criterion is that check.

## Notes and decisions

- **`sessionStorage` or the URL.** `sessionStorage` survives a reload in the same tab, which is
  what iOS does on return. A `?session=` parameter (as `report.html` already uses) would also
  survive the supplier opening a new tab, but it puts the session id in history and in shared
  links. The owner picks one and records why.
- **Out of scope:** what happens to an abandoned `capturing` session on the server (#352's second
  point). It needs an expiry rule, which belongs to the service. That's for a later story, if the
  team wants one.
- **Out of scope:** the duplicate-frame check's baseline (the last accepted frame's pixels) isn't
  restored after a reload. The first frame after continuing is checked for blur and exposure, but
  not for duplication. That's acceptable; say so in the manual check's notes.

## Implementation notes

### 2026-11-17: decisions and build (@TabeenRaoof)

**Decided with the owner before coding:**
- **`sessionStorage`, not a `?session=` parameter.** It survives the same-tab reload iOS does,
  and keeps the session id out of the address bar, history and copied links. A brand-new tab
  starts fresh, and the manual says to keep to one tab.
- **Beyond the written criteria: "Show result" after Finish.** The criteria cleared the saved
  session when Finish succeeded. A reload during the 30–50 s of reconstruction would then lose the
  result screen, which is the same demo risk this story exists for. So the session stays saved,
  in a `finished` phase, until a terminal result (complete or failed) has been shown. A reload in
  that window offers **Show result**, which resumes polling without asking for the camera. A
  timeout or a fetch error keeps the saved copy, since Retry still needs it.

**#351, the outage message** (`capture/src/api.ts`, `messages.ts`):
- `readJsonBody` throws a typed `ServiceUnreachableError` for a 5xx whose body isn't JSON.
  `recon.service` answers every error with a JSON `ErrorDetail`, so such a body comes from a proxy
  in front of it: Vite's empty 500 on the D-049 path, or a hosting proxy's HTML 502/503/504.
- `describeNetworkError` turns it into "The service isn't reachable right now — wait a moment and
  try again." The buyer page gets this wording too.
- Upload failures go through `describeUploadError`, which adds "Frames already accepted are
  kept." for this case and for C-18's dropped connection, and for nothing else.
- A non-JSON 2xx/4xx is still a broken contract, with its own detailed message. A 5xx *with* a
  JSON body came from the service and isn't called unreachable.
- `messages.test.ts`'s old pass-through test was kept on purpose, now with a 2xx example, with a
  comment saying why its scope narrowed.

**#352, the session that survives a reload** (`capture/src/session-persistence.ts`, `shell.ts`):
- **What's saved:** the session id, the order code, a phase (`capturing` or `finished`), the
  accepted-frame count from the server's `frame_index`, and every accepted gyro reading. It's
  written at Start and after every server-accepted frame, never for a rejected one.
- **Parsing:** every field is checked explicitly. A corrupt or partial record is discarded and
  removed, never half-used: a wrong session id would send frames to someone else's session.
  Every storage call is wrapped, because Safari can throw on storage access, and losing resume
  must never stop a capture.
- **On mount,** a saved record shows a panel: **Continue session** (`capturing`) or **Show
  result** (`finished`), plus **Start new**.
- **Continue is a tap,** because iOS only shows the camera and motion prompts from a user
  gesture. Start's handler became `beginCapture`, shared by both. Continue skips `createSession`,
  restores the session id, and replays the saved readings through the overlay, which rebuilds
  coverage exactly because it anchors on the first one.
- **Start always means new:** it drops a saved session.
- **A dead session:** if an upload after continuing gets `session_not_found` or
  `session_already_finished`, the saved copy is dropped and Start is enabled again, with "This
  session can't take more frames — start a new session." Both arrive as 422s from the service
  and the stub.
- **Not saved:** the duplicate gate's anchor (the last frame's pixels). The first frame after
  continuing is checked for blur and exposure only.

**Tests:**
- `session-persistence.test.ts`: 18 tests (round-trip, 11 corrupt shapes, throwing storage, no
  storage).
- `api.test.ts`: 4 tests (Vite's empty 500 on every session call, a proxy's HTML 502, a non-JSON
  2xx still a contract error, a JSON 500 not "unreachable").
- `messages.test.ts`: 8 new or changed tests.
- `shell.test.ts`: 11 tests (save at Start and per frame, a rejected frame not saved, a reload
  offering Continue, Continue reusing the session with no `createSession` and coverage rebuilt,

- Capture suite: 323 passed at build (2026-11-17), and 324 once `main` was merged in. The extra

  passes.
- **Mutation checks:**
  - the 5xx rule moved to ≥ 600: 2 api tests failed;
  - the save after an accepted frame removed: 3 shell tests failed;
  - the coverage replay removed: 1 failed.

  Each was confirmed applied, then restored, and the restored file was checked byte-identical

### 2026-11-18: review fix (@dalwalyk, PR #375)

- **Capture needs a live session.** After a dead session was dropped, `state.sessionId` was
  null while the camera and gyro stayed live, and `updateCaptureAvailability` didn't check the
  session (`updateFinishAvailability` does). Capture stayed clickable and answered "Start a
  session first." It now requires `state.sessionId !== null`, and is re-checked as soon as a
  session is created or continued. The click handler's guard stays as the backstop.
- **The test now covers it.** The dead-session test asserts Capture is disabled while the
  camera and gyro are still live. With the new condition removed, that test fails; restored, the
  file is byte-identical and it passes.
- **The test count** above was corrected: 323 was the figure at build, and it's 324 after the
  merge from `main`.

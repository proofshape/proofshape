## Why this exists

R-36's home pre-check (2026-11-16) found two ways an interruption breaks a supplier's session on
the demo path (D-072). Both were filed from it.

- **#351, the outage message.** With uvicorn stopped, the phone showed "Could not upload frame —
  uploadFrame: response body was not valid JSON (status 500):" (session `sess_2e59418b1077`). On
  the D-049 path, Vite's proxy answers an unreachable backend with a 500 and an empty body.
  `readJsonBody` (`capture/src/api.ts:20-26`) throws on it, and `describeNetworkError`
  (`capture/src/messages.ts:39-44`) passes every non-`TypeError` message through unchanged, which
  `messages.test.ts:114` pins. The session itself was fine: after the service restarted, it
  continued in the same session and finished, both times R-36 tried it (91 s and 138 s outages).
  The supplier just had no way to know that.
- **#352, a reload loses the session.** The supplier switched to Messages mid-capture
  (`sess_9cd4d8e064eb`, 6 frames). Returning to Safari reloaded the page, and the app came back
  with no session. `AppState` (`capture/src/shell.ts:40-57`) keeps the session id only in
  memory, and the accepted gyro readings that coverage is rebuilt from are in memory too. The
  server-side session stays `capturing` for good.

At the defense or the expo, either one ends a live demo that the service could have finished.

## Acceptance criteria

- **#351:** a 5xx reply whose body isn't JSON is shown as an actionable message, not the raw
  `readJsonBody` text. Something like "The service isn't reachable right now. Wait a moment and
  capture again; your earlier frames are kept." This applies to every call that reads a body
  (upload, finish, the reconstruction poll and the agent message), not only upload. A 5xx with a
  JSON error body, and every frozen error code, display as they do today. The test at
  `messages.test.ts:114` is changed on purpose, with the reason stated, not deleted.
- **#352:** the session id, the accepted-frame count and the accepted gyro readings are kept in
  `sessionStorage` (or the URL; see Notes). On load, a stored session that hasn't finished is
  offered as "Continue session", and continuing sends the next frame to that same session.
  Starting a new session or finishing one clears the stored state. Declining starts a fresh
  session.
- **No contract change (D-031).** Continuing uses only existing endpoints. The server numbers
  frames from its own count (`SessionStore.add_frame`), so a frame the server accepted whose 202
  never reached the phone still lands at the right index. The client's stored count is for
  display only, and the next 202's `frame_index` corrects it.
- **Checked on the iPhone, and the manual updated.** R-36's two cases are repeated on the Mac
  demo path (D-072): switch to another app mid-session, come back, continue and finish; and stop
  uvicorn mid-session, see the new message, restart it, continue and finish. `docs/manual.md`
  §9 ("When something goes wrong") says what the supplier does in each case.

## Tests

Written alongside the code:
- `api.test.ts` and `messages.test.ts`: a 500 with an empty body, a 502 with an HTML body, and a
  500 with a JSON `ErrorDetail` body. Only the first two give the new message.
- `shell.test.ts`: state persisted after an accepted frame; offered and restored on mount; cleared
  on finish and on a new session; a corrupt or partial stored value is ignored with a fresh
  session, never a crash.

**Manual check, and why:** iOS discarding and reloading a backgrounded Safari tab, and Vite's proxy
answering for a stopped backend, only happen on the real device and dev server. The fourth
criterion is that check.

## Notes and decisions

- **`sessionStorage` or the URL.** `sessionStorage` survives a reload in the same tab, which is
  what iOS does on return. A `?session=` parameter (as `report.html` already uses) would also
  survive the supplier opening a new tab, but it puts the session id in history and in shared
  links. The owner picks one and records why.
- **Out of scope:** what happens to an abandoned `capturing` session on the server (#352's second
  point). It needs an expiry rule, which belongs to the service. That's for a later story, if the
  team wants one.
- **Out of scope:** the duplicate-frame check's baseline (the last accepted frame's pixels) isn't
  restored after a reload. The first frame after continuing is checked for blur and exposure, but
  not for duplication. That's acceptable; say so in the manual check's notes.

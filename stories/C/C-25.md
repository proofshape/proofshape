## Why this exists

C-06 set the gate's thresholds as "starting assumptions, not measured/calibrated values"
(`capture/src/frame_gate.ts:21-24`, `DEFAULT_BLUR_VARIANCE_THRESHOLD = 100`). Tuning them was left
as follow-up work. R-36's home pre-check gave the first real case. Frame 20 of `sess_8fdecd4b3a02`
is visibly smeared: only 6 ChArUco corners were detectable, against 16–27 on that session's other
frames. It was accepted, uploaded and used in the reconstruction (#355).

## Acceptance criteria

- **Measured first.** `checkBlur`'s Laplacian variance is computed on frame 20 and on that
  session's other 22 frames, from the same pixels the shell passes it (`shell.ts:469`, the
  captured frame at the resolution the gate actually sees). The values are recorded in this
  story's notes.
- **If a threshold separates frame 20 from the sharp frames:** `DEFAULT_BLUR_VARIANCE_THRESHOLD`
  changes to it. The values from R-36's other phone sessions are checked so that it doesn't reject
  their sharp frames, and that check is recorded. No accuracy or rejection rate is claimed beyond
  those frames.
- **If none does:** that's recorded with the numbers, the threshold stays, and the notes name
  what would catch this frame instead (for example, a directional or edge-width measure). A
  measured "Laplacian variance can't see this" is an acceptable outcome. Guessing a new number is
  not.

## Tests

A test in `frame_gate.test.ts`, written with the change, builds a synthetic high-contrast
checkerboard and applies a directional motion-blur kernel. It pins what the gate does with it: it
rejects the frame if the threshold changed, or it documents the miss if not. Real frames can't be
fixtures (AGENTS.md: no photographs in git). The measurement in the first criterion is the
real-data check, and it's recorded in the story.

the blur gate is not a screen-photo detector.

**Initial JPEG-only result:** the stored R-36 JPEGs showed a separating interval, but they were
not sufficient by themselves because the live gate runs on pre-JPEG canvas pixels. PR #400 therefore
added a debug-only path to record the exact pre-JPEG `measureBlurVariance()` value for accepted
frames and compare it with the stored JPEG of the same frame.

**Offline encoder context, not a substitute for the device run:** @TabeenRaoof also measured 236
paired pre/post-JPEG samples derived from the 59 golden s-04/s-05 stills at 480 × 640, with
horizontal blur widths 1/5/9/15 px. Pillow/libjpeg quality 0.92 raised Laplacian variance in every
pair by **+0.3% to +4.7%** (the 100–350 threshold region was +0.3% to +4.2%). That suggests the
R-36 JPEG gap is likely to survive compression, but Safari/Apple's canvas encoder can differ, so
only the paired `?blur-debug=1` phone run can confirm equivalence for the live path.

The stored JPEG was higher on every paired frame by **+0.88% to +2.11%** (median about +1.2%);
the largest absolute shift was **+11.82**, and the frame ordering was unchanged. Applying that
measured 1–2% direction/magnitude to the old R-36 stored values puts the two blur candidates
159.3 / 168.1 at roughly **156–158 / 165–167** at the gate, while the lowest sharp stored frame
246.2 corresponds to roughly **241–244**. The separating gap therefore survives at the live
pre-JPEG gate.

**Threshold decision:** set `DEFAULT_BLUR_VARIANCE_THRESHOLD = 200`. It is inside the measured
blur/sharp gap, rejects the two low R-36 candidates, and remains below every 16–27-corner R-36
frame. In the paired device run all 16 accepted pre-JPEG frames were at least 237.56, so 100 and
200 classify those 16 identically. Claims are limited to these measured sessions; this is not a
general rejection-rate estimate.

**Paired-run limitation:** one deliberately shaken attempt in the new run measured 62.98 and was
rejected locally, so by design it never uploaded and has no stored-JPEG partner. No accepted frame
in that new session landed in the 100–250 interval. The equivalence conclusion therefore comes
from the 16 accepted pairs plus the old R-36 JPEG values, not from re-capturing the exact old
frame 20.


**Debug-run coverage limitation:** `proofshape.c25BlurDebug.v1` records only frames that clear the
local gate and are then accepted by the server. A frame rejected locally for blur (<200), exposure,
or duplicate never uploads and therefore never appears in the paired table. A short pairing table
must not be interpreted as evidence that no more-severely blurred attempts occurred.

In `?blur-debug=1` mode the shell also shows a dedicated debug status line. It reports the stored
measurement count after each accepted frame and turns into a visible warning if sessionStorage is
unavailable or a read/write fails. Capture remains non-blocking, but an operator must not use a run
for calibration if that warning says the paired evidence is incomplete.

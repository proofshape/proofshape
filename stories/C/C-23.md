## Why this exists

Split out of C-18 on claiming (@dalwalyk, 2026-11-12): C-18 originally covered both an iPhone and
an Android device check in one story, but Android access wasn't settled when C-18 was claimed
("who has an Android phone to run it on" was an open question on C-18 itself, never answered), and
running it is genuinely uncertain — "towards the end, or probably not," in the team's own words,
not a committed date. Splitting lets the iPhone half close on its own schedule instead of being
held open by a device nobody has lined up yet.

**This leaves the proposal's own §12 rule unmet in the meantime, named plainly rather than
dropped silently:** "a checklist per feature, run on one iOS and one Android phone at every
milestone. Tier 1 must pass on both." Android has never been checked on this project (manual §2,
"Android is untested"). Whether that gap is closed by this story running later, or accepted as a
known shortfall against the proposal, is the team's call, not decided here or by splitting C-18.

## Acceptance criteria

- **A full session on an Android phone in Chrome, recorded.** Open with `?order=`, grant
  permissions, follow the guided orbit, finish, wait for the result, view the model and download
  the GLB — the same flow C-18 ran on the iPhone.
  - Run against the real service, on the Mac path (D-049) or on the hosted build if C-21 has
    landed.
  - Recorded in C-13's block format: device, OS version, browser version, steps, result, and PASS
    or FAIL.
- **Android-specific behaviour, checked against what C-18's draft already flagged as new ground:**
  - `DeviceOrientationEvent.requestPermission` doesn't exist on Android, so C-03's
    feature-detection path is the one actually exercised here for the first time.
  - `alpha` may be relative rather than compass-based; confirm C-20's heading maths tolerates it,
    or file a fix.
  - Chrome's self-signed-certificate handling on the dev server (C-21's hosted HTTPS, once it
    lands, removes this friction — not available yet, C-21 is still `Claimed`).
- **Fixes are time-boxed.** At most 1 h of fixes in this story, each with a unit test (D-029).
  Anything beyond that is filed as an issue linked from here, not fixed silently. Keyboard access
  and error-message coverage are app-wide audits C-18 already ran; this story doesn't repeat them
  unless the Android run surfaces something those audits missed.

## Tests

The device run is a written manual check, same reasoning as C-18: real permission prompts, real
sensors and a real mobile browser can't be driven from CI on this project's budget (AGENTS.md).
Each fix carries its own unit test.

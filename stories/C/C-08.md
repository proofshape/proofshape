## Why this exists

Interactive guidance and the later defect-aware guidance (proposal §8.1) both need to answer one
question: given the mesh so far, which camera position would see the most surface that hasn't
been properly observed? Proposal §6.2 defines the method: candidate views on a hemisphere, each
scored by how many under-observed vertices it would see, using Open3D raycasting on the CPU. D-022
puts this in the capture lane. Nothing computes it today.

## Acceptance criteria

- Generates candidate camera positions on a hemisphere centred on the board origin, each looking
  at the part: radius 25–40 cm and at most 60° from vertical, per proposal §6.2. The radius range,
  angle limit and sampling density are named, overridable constants.
- Scores each candidate by the number of under-observed vertices it would see unoccluded, using
  raycasting against the mesh, and returns the candidates ranked best first. "Under-observed"
  means R-09's `Unobserved` label after R-10's sigma downgrade (`recon/provenance.py`,
  `recon/uncertainty.py`'s `downgrade_high_sigma_vertices`). Reuse those definitions; don't
  redefine them.
- The core is a pure function over a board-frame mesh plus per-vertex labels. A thin CLI over a
  run directory, like the other `recon/` modules, is optional.

## Tests

Synthetic meshes, no GPU and no capture needed:

- A box with one face labelled unobserved: the top candidate must face that face.
- An occluder placed in front of that face: that view's score must drop.
- A fully observed mesh: every score is zero.

Open3D is deliberately **not** in `requirements.txt` (`recon/tsdf_fusion.py` imports it lazily
for that reason). The owner decides between two options:

- Add `open3d` so these tests run in CI.
- Raycast with something already installed.

Record the choice here. Tests that skip in CI and never run don't count toward the definition of
done.

**Chosen (2026-10-15): add `open3d`**, pinned `open3d==0.18.0` in `requirements.txt`. See the
notes below and D-047.

interactive mode. So for now C-07's arrow targets the batch fixed orbit, and this scorer has three
consumers: interactive mode (on the proposal's cut list), rescan guidance, and the later
disagreement-map and defect-aware guidance. Wiring it into C-07's arrow is a separate step that no
story owns yet.

2026-10-15 (planning, agreed before building): four design choices, all recorded in
`recon/next_view.py`'s module docstring as well.

**Raycaster: Open3D in `requirements.txt` (D-047).** That's the story's own fork, settled in favour
of CI coverage: every C-08 test runs in CI, and none of them skip. `RaycastingScene` was checked
on macOS ARM64 with numpy 1.26.4 before choosing it. R-20's macOS Open3D crash is inside Poisson,
not the raycaster. Adding Open3D had two knock-on effects on R-07. Its "Open3D not installed"
test would have started skipping in CI, so it now fakes the missing import with
`monkeypatch.setitem(sys.modules, "open3d", None)`. Its Poisson success-path test now runs in CI
for the first time. The stale "deliberately not in requirements.txt" wording in
`recon/tsdf_fusion.py` and `requirements.txt` was corrected.

**The hemisphere is centred on the part, not the literal board origin.** The criterion above says
"centred on the board origin", but `board_pose.py` puts that origin at the board's *outer
corner*, about 100 mm from the board's centre. Centred there, a "25 cm" candidate would be
anywhere from ~15 to ~35 cm from a part sitting mid-board. The default centre is the mesh's x/y
bounding-box centre at the part's base: the mesh's *largest* z, since board +z points into the
table, and not z = 0, because of R-21. The look-at point is the bounding-box centre. Both can be
overridden.

**The score is the criterion's count, with a head-on tie-break.** An in-memory prototype on the
box test had 8+ candidates tying at 81/81 visible. A flat face is fully visible from anywhere in
front of its plane, so a pure count can't say which view *faces* it. Ties are broken by the
larger Σ|cos(incidence)| over the visible under-observed vertices, then by candidate index. The
absolute value means mesh winding order, which nothing upstream guarantees, doesn't matter. A
test asserts that reversing every face's winding leaves the ranking unchanged.

**Thin CLI included.** `python -m recon.next_view <R-10 out dir>` reads `mesh_uncertainty.glb`,
decodes labels with R-09's `colors_to_labels`, and writes `next_view.json`.

2026-10-15 (while building):

**Only rays to under-observed vertices are cast, but the whole mesh occludes.** An Observed vertex
can't add to any score, so raycasting it would be wasted work. Observed surface still blocks the
view of what's behind it, so the scene holds every triangle. A vertex counts as visible if the
first hit is within `DEFAULT_SELF_HIT_TOLERANCE_MM` (0.5 mm, a quarter of R-07's voxel,
unmeasured) of the vertex itself, or if the ray misses entirely.

**The board is deliberately left out of the scene.** Every candidate is above the part's base,
every part vertex is on the same side of the board plane, and a half-space is convex. So the
line between them never crosses the board, and it can't occlude. This is also why
`max_angle_from_vertical_deg` is refused at 90°.

**Surprise while building: shared edge vertices.** Two tests first asserted that a view from straight
above, or from the far side, sees *none* of the unobserved +x face. Both failed with 5. The code
was right and the tests were wrong. The +x face's top row of vertices is also the top face's
edge, so it really is visible across the top. The tests now assert exactly those 5.

**Occluder result, measured on the synthetic box.** The best view without the wall (azimuth 0°,
60° from vertical) sees 25/25 under-observed vertices. With an Observed wall 15 mm in front of
the face it sees 0. The new best goes round the wall's edge, to azimuth 60°, and sees 25 again.

**Among otherwise-equal views, the head-on tie-break slightly favours the far radius.** At 400 mm
the rays are closer to parallel, so square-on-ness is more uniform across the face (+x box case:
14.76 at 400 mm vs 14.61 at 250 mm). It only orders views that already tie on count, so it's
recorded here rather than corrected.

**Speed, measured on this laptop (Apple Silicon, synthetic data only).** A 44,702-vertex sphere
with half its vertices under-observed scores all 147 default candidates in 0.33 s. That's a
synthetic measurement, not a figure for golden-object meshes.

**Deliberately not modelled:** the camera's field of view (a candidate counts every unoccluded
vertex), and grazing angles (a vertex seen nearly edge-on still counts). Both would need a
threshold nobody has measured.

**Not done here:** a run on a real golden object. There are no local R-09/R-10 outputs for
`s-01`…`s-05`, and regenerating them needs the GPU pipeline (R-01 → R-10), which is outside this
story's scope. Anyone with a `mesh_uncertainty.glb` from the Lightning Studio can run the CLI on
it directly.

2026-10-16 (PR #144 review by @dalwalyk: approved, with three non-blocking findings):

1. **"Batch the per-candidate `cast_rays` calls into one."** Measured before changing anything,
   and not adopted. Same rays, looped vs one batched call: 0.26 s vs 0.26 s at 44,702 vertices,
   and 1.02 s vs 1.07 s at 179,402 vertices (synthetic spheres, this laptop). The cost is the
   number of rays, which is identical either way. The loop adds only 147 call overheads, and
   batching would cost K× the memory at once.
2. **"`score_next_views` recomputes the centre/look-at even when both are passed."** Fixed: it
   only computes defaults when one is missing. A test makes the default helper fail if called
   when both are given.
3. **"Equal radii with `radius_steps >= 2` silently duplicate candidates."** Fixed: it's now
   refused, mirroring the existing `radius_steps=1` check, with a test.

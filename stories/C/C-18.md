## Why this exists

The proposal's acceptance rule is "a checklist per feature, run on one iOS and one Android phone at
every milestone. Tier 1 must pass on both" (§12). The capture app has only ever been checked on
iPhones in Safari, and C-13's check didn't record the iOS version. S6 has 11 capture hours for
exactly this: "test on one iPhone and one Android; UI bugs; keyboard access; error messages"
(sprint plan §6).

**Scoped to the iPhone half on claiming (@dalwalyk, 2026-11-12).** The Android half, originally
this same story's other acceptance-criteria bullet, is split out into C-23 rather than done or
skipped here — Android access wasn't settled ("who has an Android phone to run it on," below,
unresolved since this story was written up) and running it "towards the end, or probably not" is
a real possibility, not a committed date. **This leaves a named gap against the proposal's own
§12 rule ("Tier 1 must pass on both") until C-23 actually runs — not resolved by this story,
raised for the team in the PR that makes this split.** See C-23 for the Android half and its own
open items.

## Acceptance criteria

- **A full session on the iPhone, recorded.**
  - One iPhone in Safari runs a whole session: open with `?order=`, grant permissions, follow the
    guided orbit, finish, wait for the result, view the model and download the GLB.
  - Run against the real service, on the Mac path (D-049) or on the hosted build if C-21 has
    landed.
  - Recorded in C-13's block format: device, OS version, browser version, steps, result, and PASS
    or FAIL — explicitly including the iOS version C-13's own check omitted.
- **Keyboard access.** Every control on the pages `main` has works with Tab, Enter and Space, with
  focus visible. The viewer's orbit either gets a keyboard alternative or its limit is stated in
  the manual.
- **Error messages.** Every message the capture page can show is listed here: each error code it
  can receive, the frame gate's rejections, permission refusals and a lost network. Each one tells
  the supplier what to do (manual §9); any that doesn't is fixed or filed.
- **Fixes are time-boxed.** At most 1.5 h of fixes in this story, each with a unit test (D-029).
  Anything beyond that is filed as an issue linked from here, not fixed silently.

## Tests

The device run is a written manual check. Real permission prompts, real sensors and a real mobile
browser can't be driven from CI on this project's budget, which is the case AGENTS.md allows. An
optional unit test can check that every interactive element on the capture page is a native,
focusable control. Each fix carries its own unit test.

## Notes and decisions

- **Keyboard access audit (code review, not a new physical pass).** Every interactive control on
  the page `main` loads is a native, focusable element, confirmed one by one: the order-code
  `<input>`, Start, Capture frame, Finish session and Retry reconstruction (all
  `<button type="button">`), the report link (`<a>`, `href` set before it's shown), the model
  viewer's "Colour by" `<select>`, and Download GLB (`<a download>`). Nothing in `capture/`
  suppresses `outline` or `:focus` — Tab, Enter and (on the buttons) Space all work, with a
  visible focus ring, by default, no extra wiring needed. The one real gap: the 3D viewer's
  `OrbitControls` (`three`) has no keyboard binding configured (`listenToKeyEvents` never called,
  no `tabindex` on the canvas), so the model can't be orbited by keyboard today. Per this story's
  own criterion ("either gets a keyboard alternative or its limit is stated in the manual"), fixed
  by stating the limit: `docs/manual.md` §8.1 now says so plainly, rather than building keyboard
  3D navigation inside this story's time box.
- **Error-message audit, listed here as the criterion asks (not just pointed at §9).** Every
  message the capture page (`shell.ts`) can show:
  - Client-side frame-gate rejections (checked before anything uploads, `frame_gate.ts`):
    `frame_rejected_blur` ("Hold steadier; pause before each shot"), `frame_rejected_exposure`
    ("Diffuse the light; avoid direct glare"), `frame_rejected_duplicate` ("Move to the next
    orbit position") — manual §9's existing table.
  - Permission refusals (`camera.ts`, `gyro.ts`): "Camera permission denied. Enable camera access
    for this site in Settings and try again.", "No camera found on this device.", "The camera is
    already in use by another app.", "The rear camera isn't available with these settings.",
    "Gyro permission denied. Reload the page and tap Start to try again." Each already names the
    next step.
  - Service responses on start/upload/finish and reconstruction failures: the codes in manual §9
    (`order_code_unknown`, `too_few_frames`, `session_not_found`, `session_already_finished`,
    `vlm_veto`, `board_not_detected`, `board_partially_occluded`, `insufficient_baseline`,
    `metric_alignment_failed`, `no_cad_uploaded`), each with its own "what to do." This story's
    own real `metric_alignment_failed` case (above) matched §9's existing description exactly,
    confirming the catalog is accurate today, not just aspirational.
  - **A lost network — the one real gap, caught on review (@TabeenRaoof, #306).** Every network
    call in `shell.ts` (start, upload, finish, poll) caught a failure and showed the raw
    `Error.message` verbatim, which for a genuine network failure is the browser's own wording —
    "Load failed" on Safari, "Failed to fetch" on Chrome — naming no next step. **Fixed:**
    `capture/src/messages.ts` gained `describeNetworkError`, which recognises a `fetch` network
    failure specifically (`error instanceof TypeError`, distinct from the `Error`s `api.ts` itself
    throws for a malformed or contract-undefined response, whose messages are already specific)
    and returns "No connection to the service — check your network and try again." Used at all
    five of `shell.ts`'s network-call catch sites; the two catch sites that wrap purely local work
    (reading the camera preview, the local frame gate) are untouched, since a `TypeError` there
    would be a real local bug, not a lost connection. Three new unit tests in
    `messages.test.ts` (`describeNetworkError`'s three branches); `docs/manual.md` §9 gets a new
    row for it. About 0.5 h of the 1 h fix budget.
- **Two of the three sessions' failures are themselves a finding worth more than a note (caught on
  review, @TabeenRaoof, #306).** The close/steep-framing failure (above) is now a concrete line in
  `docs/manual.md` §3.4: "Don't shoot so close that only a few squares fill the frame," citing
  this exact session's 2-of-16 corner count as the reason.
- **Layout polish.** The midterm report promised it for this story ("layout polish is planned for
  the device-testing story (C-18)"). The first candidate is C-20's note that the arrow renders
  below the camera preview rather than on top of it.
- **Not covered:** Android (split to C-23); the buyer page and the report page (C-16, C-15). The
  whole system on both phones is X-04's (integration point I4, "Whole system on both phones;
  record the backup demo"), which now needs C-23 too, not just this story.
- **Freeze and cut list.** S6 hardening in the sprint plan, not new feature work, so M5's freeze
  doesn't stop it. It is Tier 1 acceptance and isn't on the cut list.
- **Fixes:** one code fix (`describeNetworkError`, above, with its own unit tests, D-029) and
  three documentation lines (manual §8.1's keyboard wording, §9's new network-error row, §3.4's
  close-framing guidance) — about 0.5 h of the up-to-1 h fix budget used.
- **Estimate basis:** about 1 h for the device check, 1 h of audits (keyboard access, error
  messages — both app-wide, not iPhone-specific, so C-23 doesn't redo them) and up to 1 h of
  fixes, down from the original two-phone 4 h estimate (1 h per device check, 1 h audits, 1.5 h
  fixes) now that only one device check is in this story.

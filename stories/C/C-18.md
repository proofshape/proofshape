## Why this exists

The proposal's acceptance rule is "a checklist per feature, run on one iOS and one Android phone at
every milestone. Tier 1 must pass on both" (§12). The capture app has only ever been checked on
iPhones in Safari. Android is untested (manual §2, "Planned, C-18"), and C-13's check didn't record
the iOS version. S6 has 11 capture hours for exactly this: "test on one iPhone and one Android; UI
bugs; keyboard access; error messages" (sprint plan §6).

## Acceptance criteria

- **A full session on each phone, recorded.**
  - One iPhone in Safari and one Android phone in Chrome each run a whole session: open with
    `?order=`, grant permissions, follow the guided orbit, finish, wait for the result, view the
    model and download the GLB.
  - Run against the real service, on the Mac path (D-049) or on the hosted build if C-21 has
    landed.
  - Each is recorded in C-13's block format: device, OS version, browser version, steps, result,
    and PASS or FAIL.
- **Keyboard access.** Every control on the pages `main` has works with Tab, Enter and Space, with
  focus visible. The viewer's orbit either gets a keyboard alternative or its limit is stated in
  the manual.
- **Error messages.** Every message the capture page can show is listed here: each error code it
  can receive, the frame gate's rejections, permission refusals and a lost network. Each one tells
  the supplier what to do (manual §9); any that doesn't is fixed or filed.
- **Fixes are time-boxed.** At most 1.5 h of fixes in this story, each with a unit test (D-029).
  Anything beyond that is filed as an issue linked from here, not fixed silently.

## Tests

The device runs are a written manual check. Real permission prompts, real sensors and real mobile
browsers can't be driven from CI on this project's budget, which is the case AGENTS.md allows. An
optional unit test can check that every interactive element on the capture page is a native,
focusable control. Each fix carries its own unit test.

## Notes and decisions

- **Android is new ground. Watch:**
  - `DeviceOrientationEvent.requestPermission` doesn't exist, so C-03's feature-detection path is
    the one taken;
  - `alpha` may be relative rather than compass-based, which C-20's heading maths should tolerate;
  - Chrome's handling of the dev server's self-signed certificate, which C-21's hosted HTTPS would
    remove.
- **Layout polish.** The midterm report promised it for this story ("layout polish is planned for
  the device-testing story (C-18)"). The first candidate is C-20's note that the arrow renders
  below the camera preview rather than on top of it.
- **Not covered:** the buyer page and the report page (C-16, C-15). The whole system on both phones
  is X-04's (integration point I4, "Whole system on both phones; record the backup demo").
- **Freeze and cut list.** S6 hardening in the sprint plan, not new feature work, so M5's freeze
  doesn't stop it. It is Tier 1 acceptance and isn't on the cut list.
- **Open question:** who has an Android phone to run it on. Settle it before claiming.
- **Fold check** (2026-11-09). No story in flight owns this. Every C story's device check so far
  was an iPhone; no story or branch has an Android run. So it's a new story.
- **Estimate basis:** about 1 h per device check, 1 h of audits and the 1.5 h of fixes. C-02 took
  2 h and C-20 4 h, each a device check plus its fixes.

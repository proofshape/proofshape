## Why this exists

D-048 deferred a permanent host for the capture app, "a permanent host like GitHub Pages, named in
the original proposal", "to its own future story". Nobody wrote it. Three things follow:
- **A phone reaches the app only through a laptop.** It needs a laptop's dev server, on the same
  network, with a self-signed certificate (D-049).
- **Nothing proves the app builds.** CI never runs `vite build`, so a broken production build
  would go unnoticed.
- **The backup demo has nowhere to run.** S6's recorded backup demo (I4) needs the app somewhere a
  phone can open it.

## Acceptance criteria

- **CI builds the app.** `.github/workflows/typescript-ci.yml` runs `npm run build` on every pull
  request, within the job's existing two-minute limit.
- **Deployed from `main`.**
  - A workflow publishes `capture/` to GitHub Pages on every push to `main` that changes it
    (D-014; sprint plan §8: "Deployment runs only from `main`, on push, through GitHub Actions").
  - It sets Vite's `base` to the Pages path and the service's address at build time.
  - The `?viewer-demo` modes exist only in development builds, because they rely on the dev
    stub. A hosted build says so instead of failing.
- **O-005 answered before a public page points at the paid service.** The hosted build is pointed
  at the Lightning deployment only after O-005's three questions are answered and recorded as a
  numbered decision:
  - whether `--token-auth` refuses the browser's CORS preflight, answered by a `curl -i -X
    OPTIONS` against a running deployment;
  - whether a token visible in a public bundle is acceptable;
  - how an unknown order code is stopped from starting a GPU run: R-34's order check if it has
    landed, otherwise the service's existing `known_order_codes`, read from a deploy-time
    setting (today `app = create_app()` passes none).
- **One real phone session.** One session from the hosted page against a started deployment,
  recorded in C-13's format, then the deployment stopped (D-042). D-049's Mac path stays
  documented as the fallback.

## Tests

- Unit tests for the capture link under a base path, and for the demo modes being dev-only.
- The workflow's first successful run, recorded with its run id.
- The real-phone session is a manual check. TLS, CORS against the real proxy and the token can't
  be stubbed, which is C-13's reasoning.

## Notes and decisions

- **A team decision comes first: which service the hosted page calls.**
  - Only the Lightning deployment is reachable from a public page. The Mac's service listens on
    127.0.0.1 and is reached only through the dev server on the local network (D-049).
  - So the hosted page works only while a deployment has been started by hand: one replica, a
    four-hour cap (D-042).
  - Still to check: whether the Lightning address stays the same across a stop and a start. If not,
    either rebuild per start or add a runtime override.
- **Setup:** an organisation admin sets Pages' source to "GitHub Actions". Record that in
  `capture/README.md`.
- **Side benefit:** Pages serves real HTTPS, so phones no longer need to accept a self-signed
  certificate, which also helps C-18.
- **Orders don't survive a stop.** R-34's orders live on the container's disk, so a demo creates
  its order and captures within one start.
- **Freeze and cut list.** Deployment, not a feature, but still new work after Nov 13, so the
  boundary call has to carry it explicitly (working agreement 4). It isn't on the cut list.
- **Fold check** (2026-11-09). No story in flight owns this.
  - R-15 deploys the service only.
  - C-13 named the hosting options and chose none permanently (D-048).
  - No branch has a Pages workflow.

  So it's a new story.
- **Estimate basis:** R-15 (the container and its deploy) took 5 h against 4. A static site has
  no image, so 4 h.

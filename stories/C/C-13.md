## Why this exists

`capture/` has only ever talked to the local stub. R-15 deployed a real, reachable, token-gated
service, but nothing in `capture/` has ever pointed at it, and the service has no CORS configured
for a browser origin different from itself. This is integration point I1 in the sprint plan's own
terms ("first real frames through the real service"), landing well after the Sept 25 date the
plan named for it. Closing that gap is this story's main criterion. D-042 deliberately left
"browser-facing access is decided by whichever story first connects capture to the deployed
service, not here" — this is that story.

## Acceptance criteria

- `capture/` can be configured, at build time, to call the deployed service's base URL instead of
  the stub, and a capture link can pre-fill a known order code so a supplier is not typing one in.
- The deployed service answers a cross-origin request from wherever `capture/` ends up served
  (CORS), and the bearer token D-042 requires is supplied by whatever that hosting choice turns
  out to be. Name the real options in this story's notes — serve the app from the recon
  container itself (same origin, no CORS needed); a separate static host with CORS and the order
  code as the access control; something else — and record which was chosen and why, rather than
  picking silently. *(2026-10-15, D-049: for C-13's own check the choice is the dev server's
  same-origin `/v1` proxy to the Mac, so no CORS or token is involved; D-048's CORS and token
  support stays in the code for a Lightning target.)*
- A full session — create, capture a few real frames, finish, poll, view — completes end to end
  from a real phone against the real `recon.service`, running natively on the M2 Max (D-010)
  with `PROOFSHAPE_RECON_DEVICE=mps` and reached through `npm run dev:device` with
  `PROOFSHAPE_RECON_PROXY` (D-049).
  *Superseded 2026-10-15 by D-049, kept for the record:* ~~against the real deployed service,
  using R-15's runbook (start → stop) so the paid GPU is not left running afterward.~~

## Notes and decisions

2026-10-15: Recorded as D-048. The real options named in this story's acceptance criteria:

- **Serve `capture/` from the recon container itself (same origin, no CORS).** Ruled out: traced
  that Lightning's `--token-auth` (R-15) gates *every* request at the proxy, including a plain
  page load (R-15's own manual check: no token → 401). A phone's top-level navigation can't
  attach an `Authorization` header before any JS runs, so the page itself would never load. It
  would also tie the free static frontend's reachability to the paid, on-demand GPU container's
  uptime.
- **A separate static host, with CORS and the order code as the access control — chosen.** For
  this story, "separate static host" is the existing `npm run dev:device` LAN-HTTPS pattern
  C-02/C-03/C-09 already used for phone manual checks, now pointed at the deployed base URL
  instead of the stub — not a new GitHub Pages pipeline (named in the original proposal as the
  long-term plan), which is new CI infrastructure beyond this story's 3h estimate and belongs in
  its own future story.
- **A server-side proxy that hides the token from the browser entirely.** Ruled out as new
  infrastructure beyond this story's scope, not a 3h change to `api.ts`/`service.py`.

`recon/service.py`'s `create_app` adds `CORSMiddleware` with a wildcard origin (deliberate, not
an oversight — CORS only restricts browser JS, and a non-browser caller ignores it entirely; see
D-048 for the full reasoning). `capture/src/config.ts` resolves `VITE_RECON_BASE_URL` /
`VITE_RECON_TOKEN` at build time; `api.ts` attaches the token as `Authorization: Bearer <token>`
on every outgoing request when present. The token is visible to anyone who opens dev tools on
the page — the order code, already checked server-side against `known_order_codes`, is the real
gate on whether a session does anything. `main.ts` also pre-fills the order code from a capture
link's `?order=` query param, the same pattern it already used for C-11's `?viewer-demo=1`.

**Still open: the real-phone manual check below.** That needs starting the paid Lightning
deployment (R-15's runbook), which bills a GPU for as long as it runs — a deliberate, explicit
step, done separately with the team's go-ahead rather than folded silently into this PR.
*(Superseded 2026-10-15 by D-049: the check now runs on the M2 Max, see the last entry.)*

2026-10-15: **First real-phone attempt found the same chicken-and-egg R-15 itself hit.** Started
the deployment from `main` at `1fb54de` (the claim-only commit, merged before this PR), pointed
`npm run dev:device` at it, and got `Could not start session — Load failed` on a real iPhone.
Confirmed by reading `1fb54de:recon/service.py` directly: no `CORSMiddleware`, because this
story's actual code change is still only on the unmerged branch. Per D-042, the service image is
published only on a push to `main` — so the CORS fix can't be *live* on any deployed instance
until this PR merges, and the manual check can't succeed against code it isn't testing. Stopped
that deployment immediately (run `38834386243`) rather than leave it billing against a check it
couldn't pass.

Following R-15's own precedent (`stories/R/R-15.md`, "Still open, and why this PR doesn't close
the story"): this PR merges on its automated verification (unit tests, clean checkout) with the
manual-check block below left unfilled, same as R-15's PR #83. A second, short close-out PR does
the real deploy → phone check → `State: Done` once a post-merge image exists to test against —
exactly the split D-038 exists to make explicit rather than silently skipped.
*(Superseded 2026-10-15 by D-049: with the service on the Mac, the phone check runs against this
branch's own code, so C-13 closes inside this PR and no close-out PR is needed.)*

2026-10-15: **Scope moved to the M2 Max; @TabeenRaoof joins as co-owner (D-049).** A second
Lightning start never got a ready replica (run `38838190937`: deployment created, no status
reported for 30 minutes), with the teamspace's credits in doubt. The team agreed to co-own C-13
and run its end-to-end check against `recon.service` on the M2 Max instead, dropping Lightning
from this story. Two changes made that possible:

- `recon/service.py` never passed a device to the backend, so it always asked for `cuda` and
  could not run on a Mac. `PROOFSHAPE_RECON_DEVICE` (`reconstruction_runner.resolve_device`, same
  pattern as `PROOFSHAPE_RECON_BACKEND`) now selects it; unset stays `cuda`, so the container is
  unchanged.
- The phone loads the page over HTTPS, so it can't call `http://<mac>:8000` (mixed content), and
  the contract stub's middleware answered every `/v1` route before any proxy could.
  `PROOFSHAPE_RECON_PROXY` (`capture/stub/dev-recon-target.ts`) now leaves the stub out and
  proxies `/v1` to the service, with `xfwd` so `glb_url` comes back on the dev server's own
  origin. Hosting options for this check, in the acceptance criteria's terms: the service over its
  own HTTPS (a second self-signed certificate to accept on the phone) or the same-origin proxy —
  chosen, because it needs no CORS, no token and no extra certificate.

Verified on the M2 Max before the phone check: `scripts/smoke_r14.py` drove golden object s-04
(30 frames) through the local service with `PROOFSHAPE_RECON_DEVICE=mps`, giving `complete`,
`metric: true` (ChArUco tier) and a 1,058,908-byte GLB in about 66 s end to end, 47.6 s of it
VGGT. That is one run on one object, not a latency measurement. Then the same session was read
through the HTTPS dev server with `PROOFSHAPE_RECON_PROXY`: `glb_url` came back as
`https://127.0.0.1:5174/v1/sessions/<id>/model.glb`, and the GLB downloaded through the proxy.

What this leaves for a later Lightning story is recorded as O-005, not fixed here: whether the
browser's preflight gets past `--token-auth`, and the order code, which the deployed app does not
actually check (`app = create_app()` sets no `known_order_codes`).

2026-10-15: **The first real-phone sessions found an integration gap, not a capture problem
(D-050).** Two sessions from an iPhone (19 and 17 frames, full 13/13 orbit coverage) both failed
with "insufficient_baseline: … found 0". The board was detected in every frame (16–18 markers,
18–21 corners each), but every frame was `intrinsics_unavailable`: the app's frames come from a
canvas, so they carry no EXIF focal length, and R-02 can't pose without one. The golden capture
never hit this because it is Camera-app photos. The phone also showed the wrong reason: the
service had no case for this failure, so it fell through to `insufficient_baseline`, whose advice
(move further between shots) didn't apply.

Fixed in this PR, as agreed with the team: the service now calibrates K from the board with R-03
when frames have no focal length, and runs R-02 again with it (D-050), and the failure message
names the real cause. Rerunning the pipeline on the first failed session's own 19 frames on the
M2 Max: calibration RMS 0.20 px, 18 of 19 frames posed, `metric: true`, observed fraction 0.17,
about 44 s end to end. One session, not an accuracy or latency measurement.

Open, not fixed here: the app captures at only 480×640, because `capture/src/camera.ts` asks
`getUserMedia` for no resolution. Reconstruction works at that size, but detail and metric
accuracy will be worse than at the camera's real resolution. That belongs to the capture lane as
its own change, not to this story.

2026-10-16: **Manual check passed on session 600, after the D-050 fix; the attempts before it are
the more useful finding.** Every session from the iPhone, from the service's own records (sessions
333 and 500 were abandoned before Finish and are left out):

| Order code | Frames | Outcome |
|---|---|---|
| 111, 112 | 19, 17 | Failed: no EXIF focal length (before D-050) |
| 222 | 15 | Failed in fusion: 0 board points near the fitted surface ("too little of the board is visible") |
| 223 | 15 | Complete, but a clear glass object: the board shows through the glass, and the glass itself was not reconstructed |
| 334 | 19 | Failed: board calibration found 2 usable views, needs 3 |
| 335 | 19 | Failed in fusion: fitted board tilt 19.65°, over `max_tilt_deg=2.0` |
| 300, 400 | 14, 14 | Failed in fusion: same as 222 (with 222, the three tries of the second object) |
| 600 | 19 | **Complete**, metric, observed fraction 0.16 |

So the end-to-end path works, which is what this story has to show, but after D-050 only 2 of 7
finished sessions produced a model from phone frames. Four of the five failures are in fusion's
board-surface fit (R-21) and one in R-03's calibration, and every one named its reason rather than
failing silently. Why phone frames fail there when the golden capture does not is not known yet:
the 480×640 resolution, the board-calibrated K, and how much of the board each object leaves
visible are all candidates. That needs its own recon-lane story and is not fixed here. The glass
result is the known weakness of image-based reconstruction on transparent objects, recorded as an
observation, not a bug.

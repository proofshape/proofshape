## Why this exists

Split out of the original A-07 on review (@TabeenRaoof, #302): the sprint plan's own S5 capture
bullet lists "the agent conversation view" as its own line item, in the capture lane's budget,
separate from A-05's next-view arrow and from the agent's own generative-AI budget. This is the
phone-side UI surface that shows what A-07's loop says to the supplier — interpreting a rejection
reason, adapting to a struggling user, explaining at session end what was captured — none of
which the agent's own server-side loop can display by itself.

## Acceptance criteria

- A phone-side view (new, or an extension of the existing capture shell — an open question for
  whoever claims this to settle, not decided here) that displays the agent's messages as A-07's
  loop produces them.
- Reads whatever contract field or route A-07's own D-031 request adds for surfacing agent
  messages to the phone (A-07's acceptance criteria name this requirement explicitly) — this
  story does not invent its own separate wire format.
  - **This story is built against a mock field in the stub, not the real one, and doesn't wait
    for it** — the same pattern C-14/C-15 already used (sprint plan §5, D4): no story owns a
    merged real field yet, since A-07's D-031 round hasn't happened (its next sprint boundary is
    Dec 2). Ready here means "the view can be built and tested now," not "the real wire exists" —
    caught on review (@TabeenRaoof, #318), since leaving this unstated would make C-22 Ready in
    the index but not in practice, the same gap A-05 had before #302 named it.
- Degrades sensibly when the agent has fallen back to A-08's deterministic policy (no agent
  message to show, or a fixed message indicating the fallback), since "the session always
  completes" even without the agent's own voice.

## Tests

Written alongside the view: a component/unit test rendering a representative set of agent
messages and the fallback state, following this project's existing capture-UI test conventions
(see C-07/C-09's own test files for the pattern).

## Notes and decisions

- Whether this is a new UI surface or an extension of the existing shell is not decided anywhere;
  this is a real design question for whoever claims it.
- Estimate is a rough planning figure, not backed out of a specific proposal line item the way
  A-07/A-13's are — the sprint plan's S5 capture bullet bundles several items under one 20 h
  total without a per-item breakdown.

### Built in PR #323

- Extended the existing capture shell rather than adding a separate page. The assistant panel is
  its own component and the shell only mounts it and feeds it A-07-shaped results.
- The mock mirrors A-07's `AgentLoopResult` phone-facing fields: `finished`,
  `fallback_reason: model_error | timeout | loop_detected | null`, and `message`. Client-side
  transport failure is kept separate from the agent's fallback reason.
- The panel stays hidden until the mock/route has returned HTTP 200 at least once. This keeps
  today's real service truthful: it has no agent-message route yet, so suppliers do not see a
  repeated fake fallback line after every accepted frame.
- Supplier-facing status text never exposes raw fallback codes. The code is retained only in a
  data attribute for debugging. Identical consecutive messages are deduplicated.
- Agent requests are optional, time-bounded, and never hold the Capture/Finish lock. Older
  overlapping replies are ignored so a slow response cannot overwrite newer guidance.
- Added focused component, route-timeout, and shell regression tests, including the exact
  non-blocking-request regression caught in review.

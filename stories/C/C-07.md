## Why this exists

The proposal's Tier 1 includes a "gyro-guided next-position arrow," and its capture loop has the
supplier follow on-screen guidance around the part. Nothing on the client tells anyone where to
stand next today, so whether the frames cover the part is down to luck. Under D-002 batch capture
is the guaranteed path, and batch guidance is a fixed orbit (proposal §6.2), which needs no
server round trip. That means the arrow can work now, without waiting for any reconstruction.

## Acceptance criteria

- A fixed batch orbit of 12–16 target views (per proposal §6.2: eight around the part at mid
  elevation, the rest higher, including straight down) is defined as data. The elevations and the
  angular tolerance for "this slot is covered" are named, overridable constants, not magic
  numbers (house style: `recon/uncertainty.py`'s `DEFAULT_SIGMA_DOWNGRADE_THRESHOLD_MM`).
- Pure functions: given the gyro readings of the accepted frames so far, mark which orbit slots
  are covered and pick the next uncovered one. Given the live reading and that target, return
  the arrow direction, or an "on target" result. Azimuth is anchored to the first accepted frame's
  `alpha`, because iOS reports `alpha` relative to an arbitrary zero. Elevation comes from `beta`.
  Rotation only: position is never integrated from the accelerometer (proposal §6.2).
- An overlay renders the arrow plus a covered/remaining count into a container element it is
  given, and updates on `deviceorientation`. It does not own or start the camera stream; that is
  C-05's job.

## Tests

The orbit, coverage and arrow logic are pure functions and fully unit-testable in plain Node with
`Gyro` literals (`capture/src/types.ts`), the same way C-06 tests its gate with no DOM. Cover at
least: slot coverage within and just outside the tolerance, next-slot choice, `alpha` wrapping
around 0/360, and anchoring to the first frame's heading. Overlay mounting and updates on a
synthetic `deviceorientation` event use the happy-dom pattern already in `gyro.test.ts`.

Manual check (device, iOS/Safari version, steps, result): walk an orbit around a part on a real
phone and confirm the arrow points the right way and the count advances. How real sensor readings
behave as the phone moves around a part can't be mocked. That's the same reasoning C-02 and C-03
used for their device checks.

## Notes and decisions

Written while working. What you tried, what surprised you, what you chose and why. If a decision
here will govern later work, also add it to `docs/decisions.md` with a number.

2026-10-08 (when written up): **Depends on C-03 only, not C-05, on purpose.** Following C-06's
precedent, the logic is pure and the overlay renders into any container, so this can be picked up
in parallel with C-04 instead of queuing behind C-04 → C-05. Putting the overlay on top of C-05's
live view is a separate wiring step. So is feeding it the gate's accepted frames (C-06). No story
owns that wiring yet.

**Why the target is the fixed orbit, not C-08's scorer.** D-002 says interactive reconstruction
gets built only if the M2 latency table shows it is nearly free. R-13's real T4 numbers (VGGT
80.21 s total on `s-04`) are far above the proposal's ~2 s-per-update bar for interactive mode.
That puts batch on the path that ships. If C-08's scorer is wired in later, it replaces the source
of the next target. The arrow and overlay stay as they are.

2026-10-10: Implemented as `capture/src/orbit.ts` (pure functions, no DOM, same shape as C-06's
`frame_gate.ts`) and `capture/src/overlay.ts` (the DOM-mounting piece). `gyro.ts` is untouched —
by the time this overlay mounts, gyro permission has already been granted elsewhere, so the
overlay just attaches its own `deviceorientation` listener, reusing `mountGyroCheck`'s mechanism
without reimplementing it.

**The one real-device-dependent assumption, isolated on purpose.** `beta` (W3C: 0° flat/screen-up,
~90° held upright) has to map to this story's "elevation" (0° = level with the part, 90° =
straight down). The natural reading — upright, camera pointing roughly horizontally at the part,
is the normal mid-elevation pose at beta≈90; tilting the phone down to shoot from above moves beta
toward 0 — gives `elevationDeg = 90 - beta`, isolated in one function (`elevationFromBeta`)
specifically so it's a one-line fix if the real-device check below shows it's backwards. This is
the single highest-risk guess in this story, flagged explicitly rather than buried.

**"Next uncovered" is the lowest orbit-array index not yet covered, not nearest-to-current.**
`computeCoverage` is only ever given the accepted-frame history, not a live/current position to
measure distance from — the acceptance criteria's own description doesn't ask for one. Fixed-order
is simpler, fully testable without extra plumbing, and the orbit's own construction order (ring,
then ring, then straight down) is already a sensible walking path.

**A target near straight down exempts azimuth entirely**, in both `computeCoverage` and
`computeArrowGuidance` (threshold: elevation ≥ 85°). Azimuth is meaningless at the pole — a
reading with any heading at all should still count as covering (or being on-target for) the
straight-down slot, as long as the phone is actually pointed down.

**No anchor yet means no arrow guidance yet.** `computeArrowGuidance` requires a real anchor;
`overlay.ts` simply doesn't call it until at least one frame has been accepted
(`reportAcceptedFrame`), showing "Capture the first frame to start." instead of inventing a
meaningless default anchor at 0°.

**Elevation comparisons use plain subtraction, not the circular `angularDistanceDeg` helper** —
caught while writing `orbit.ts` itself, not after: unlike azimuth, elevation isn't a wraparound
quantity in this story's range, and reusing the circular helper for it would be numerically
harmless here but conceptually confusing to a future reader.

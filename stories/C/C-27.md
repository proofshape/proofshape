## Why this exists

Today the supplier walks to a target, then taps the shutter. The tap shakes the phone at the
moment of capture, and it is easy to tap while still moving. Once C-26 shows when the phone is on
target, the app can take the photo itself and move the arrow to the next target.

**This is a new behaviour after M5's feature freeze** (Nov 13; `docs/sprint-plan.md`, "Nothing
new is started after this date"). @TabeenRaoof chose to write it up as its own story, so the team
can accept or decline it in review without holding up C-26. C-26 is now Done. This claim asked
the team for an explicit exception to the freeze, and the team granted it on 2026-11-23 **with
auto-capture off by default** (Notes, 2026-11-22 and 2026-11-23).

## Acceptance criteria

- **The first frame is still a tap.** It anchors the orbit's zero heading (`anchorHeadingDeg`), so
  there is no target to capture against before it.
- **After that, a frame is taken automatically** once the live reading has been on the next
  target (C-26's green) for 0.6 s and has stayed within 3° of where that hold began. It goes
  through the same exposure, blur and duplicate gates as a tap, and the same upload, rollback,
  resume and VLM-tip handling. The values are named constants.
- **It never fires:**
  - while an upload is in flight;
  - while the session is finishing;
  - without a live session;
  - once the orbit is complete;
  - within 1.5 s of its last attempt;
  - with the on-screen switch ("Take the photo automatically when on target") off.

  The manual shutter keeps working throughout.
- **The switch is off by default** (the freeze exception, Notes 2026-11-23). Until the person
  capturing turns it on, the app behaves as main does without this story: every photo is a tap,
  and the on-target line says to take the photo.
- **A gate rejection on an automatic frame** shows the gate's message, marked as automatic. It
  doesn't advance coverage, as with a tap.
- **A photo that fails to upload while the switch is on** (a network error, or the server rejects
  it), whether automatic or tapped, turns the switch off and says so, instead of retrying while
  the phone stays on target. If the session is gone, the message doesn't offer a retry. A tap
  restarts the hold and the retry gap. *(Added at #420's reviews, 2026-11-24.)*

## Tests

- `capture/src/auto_capture.test.ts`, for the pure dwell logic:
  - nothing fires before 0.6 s, and it fires at 0.6 s;
  - a 3.01° move restarts the hold;
  - leaving the target resets it;
  - the 1.5 s retry gap holds;
  - it is off when disabled.
- `shell.test.ts`, with the injected clock:
  - the switch starts off, and a held on-target reading takes nothing until it is turned on;
  - one upload after a held on-target reading with the switch on;
  - none before the first frame, during an upload, after `complete`, or with the switch off;
  - a rejected automatic frame leaves coverage unchanged;
  - a failed automatic upload (server rejection, or no network) turns the switch off and isn't
    retried; so does a failed tap; a gone session says only that auto-capture is off;
  - a tap the gate rejects isn't followed by an automatic photo within the retry gap;
  - a reading before the motion permission is granted doesn't enable capture, whether the
    permission is then denied or granted.
- `overlay.test.ts`: turning the switch off updates the on-target line without a new
  orientation event, and does nothing once the overlay is disposed (after Finish).

The written device check is a full iPhone orbit filled by auto-capture, with the switch turned
on, then Finish, reconstruction and the report, recorded in the notes.

## Implementation notes

### 2026-11-19: implementation (@TabeenRaoof, with Claude)

- **`capture/src/auto_capture.ts` is new: pure and timer-free.** `stepAutoCapture` is fed each of
  C-26's guidance updates (one per orientation event) with the time, and answers `fire`. Its
  constants:
  - `AUTO_DWELL_MS = 600`;
  - `AUTO_STEADY_DEG = 3`, the largest change in any of alpha, beta or gamma, wrap-aware through
    `angularDistanceDeg`;
  - `AUTO_RETRY_MS = 1500`.

  Only `on-target` can start or continue a hold, so `idle` (before the first photo) and
  `complete` never fire.
- **`shell.ts`:**
  - The shutter's click body is now `attemptCapture(trigger)`, so both paths share the gates,
    upload, rollback, persistence and VLM tip.
  - Auto acts only while the shutter itself is enabled, which covers session, camera, gyro, no
    upload in flight and not finishing.
  - Automatic status lines read "Auto: …".
  - A switch, on by default, turns auto off, and the on-target line then says "take the photo"
    instead of "hold steady". *Superseded 2026-11-23: the switch is off by default (the
    2026-11-23 note below).*
  - A 150 ms flash confirms each shot.
  - The clock is `options.now`.
- **Tests:**
  - 7 pure tests in `auto_capture.test.ts`.
  - 5 shell tests against the contract stub:
    - a held reading takes frame 2;
    - nothing before the first photo;

### 2026-11-24: review fixes (#420, @dalwalyk)

- **A failed automatic upload turns auto-capture off** (the blocking finding). A network error or
  a server rejection used to be retried every retry gap for as long as the phone stayed on
  target, sending a new photo each time. Now the switch goes off and the status adds "Auto-capture
  is off now — tap to retry, or turn it back on." Gate rejections still retry: that is what the
  retry gap is for.
- **A tap restarts auto-capture's hold and retry gap.** A tap the gate rejected could be followed
  by an automatic photo on the next reading, overwriting the person's own message.
- **The overlay's reading counts only after the motion grant.** The overlay listens from page
  load; C-27 had made its readings set the shell's gyro reading, so on Android or desktop a
  reading before any grant could enable capture. It now counts only once the shell's own
  listener runs.
- **The shutter's state is refreshed before auto-capture reads it.** The overlay's listener runs
  before the shell's for the same event. No test can show a difference today: every change that
  should block capture already refreshes the state at once, so the stale case could only keep
  the shutter disabled for one event. It's kept as a guard, and removing it fails no test.
- **The 11 C-27 shell tests:**
  - after the first tapped photo, holding on the next target takes the next photo by itself;
  - does not fire where the photo would count for an already-covered slot;
  - never fires before the first photo, however long the phone is held;
  - the switch starts off, and a held on-target reading takes nothing until it is turned on;
  - switched off again, holding on target takes nothing and the status says to tap;
  - never starts a second capture while an upload is still in flight;
  - an automatic photo the server rejects turns auto-capture off instead of retrying (new);
  - an automatic photo that can't reach the server turns auto-capture off instead of retrying
    (new);
  - a tap restarts auto-capture's hold and retry gap (new);
  - a reading before the gyro is granted doesn't enable capture (new);
  - an automatic frame the gate rejects says so, uploads nothing and leaves coverage alone.
- **Mutations, each applied and reverted:** without the switch-off, both upload-failure tests
  fail; without the tap reset, the tap test fails; without the grant check, the gyro test fails;
  without the refresh, nothing fails (above).
- **Checks:** 371 tests pass across 26 files; tsc, eslint and prettier are clean.
- **The device check above ran on `d273d7c`, before these fixes.** *Corrected at @dalwalyk's
  re-review:* this note first said the fixes leave the happy path unchanged. They don't: the
  overlay's `onGuidance` now sets the gyro reading and refreshes the shutter on every event,
  including the ones after each accepted photo, so every capture runs new code. The device check
  was run again on the merging code (`660689c`, below).

## Why this exists

Nothing in `capture/` can display a GLB yet, and three.js (named in the pinned stack, §9) is not
even a dependency. The proposal's own description of what the user sees — "a 3D model appears in
the browser seconds after the last frame" — has nothing behind it client-side. C-10 gives the
page a `glb_url` to point at; this story is what renders it.

## Acceptance criteria

- Given a `glb_url` from C-10's completed result, three.js loads and renders it in a canvas sized
  to the viewport, with touch-drag orbit and pinch zoom.
- A "download GLB" control using the same `glb_url`, so the raw model stays retrievable even if
  in-browser rendering fails for some reason.
- A `failed` status, or a `complete` status with no `glb_url`, shows a specific message in place
  of a blank or broken viewer — no silent failure, per `AGENTS.md`'s rule.

## Tests

The loader is invoked with the right URL, and the fallback message renders without ever calling
the loader on a failed/missing-URL result — both testable against a mocked `GLTFLoader`, no WebGL
needed for either.

Manual check (device, iOS/Safari version, steps, result): actual WebGL rendering, and whether
orbit/pinch gestures behave correctly on a touchscreen, are not things happy-dom (no WebGL
context) can verify — the same class of exception C-02/C-03 use for behaviour that needs a real
browser's graphics stack.

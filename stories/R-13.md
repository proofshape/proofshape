# R-13 · Per-stage latency instrumentation

**Area:** recon · **Tier:** 1 · **Estimate:** 3 h
**Depends on:** R-07
**State:** Claimed
**Owner:** @TabeenRaoof

---

## Acceptance criteria

- Every stage timed and logged.
- Prints a table per run: stage, seconds, share of total.
- Recorded for all three backbones on the same capture.

## Notes and decisions

**Not closing this story yet.** Two of the three acceptance criteria are done and tested; the
third ("recorded for all three backbones on the same capture") can't be, because
`recon/colmap_runner.py` doesn't exist on `main` yet -- R-12 is still an open PR -- and even once
it merges, producing a real measurement needs the shared Lightning GPU, which this session
doesn't have. Per this project's standing rule against closing a story on an unmet criterion or
inventing a measured value, `State` stays `Claimed`, not `Done`, and there's no completion
record yet. What's left: R-12 merges, then whoever has GPU access runs all three backbends on
`s-04` with this code and records the real table here.

**What actually existed already.** `vggt_runner.py` and `mast3r_runner.py` already time their
own internal stages into a `timings` dict, already embed it in `run.json`, and already print it
stage-by-stage. The two real gaps were: `find_capture_frames` was never individually timed in
either runner, and nothing anywhere computed a share-of-total percentage -- and the *unified*
`reconstruction_runner.py` CLI (the one meant to be backend-agnostic) was actually the one place
that threw away the per-stage detail each backend's own `main()` already had, printing only
`total_s`.

**Design: one shared, pure formatter (`recon/timing.py`), not a logging framework.** "Logged"
here already means "persisted in `run.json`," which the existing `timings` dict does; neither
runner uses Python's `logging` module anywhere, and adding one would be solving a problem this
story doesn't have. `format_timing_table(timings: dict[str, float]) -> str` takes the dict
exactly as each runner already builds it, requires `total_s`, and is the only thing all three
entry points (`vggt_runner.main`, `mast3r_runner.main`, `reconstruction_runner.main`) call to
print their table -- removing three copies of the same loop. `find_capture_frames` is timed at
the call site (it runs in `run_on_capture`, before the model-specific function it's an input
to), and prepended into the timings dict so the table still reads in chronological order.

**Scope: "three backbones" means the reconstruction step itself, not R-07's fusion.** The story
depends on R-07, but its acceptance criteria say "backbones" -- VGGT/MASt3R/COLMAP -- not the
downstream TSDF fusion/mesh stages, and `tsdf_fusion.py` has no timing of its own to begin with.
Reading `Depends on: R-07` as a scheduling dependency (R-13 opened up once R-07 landed), not a
request to also instrument fusion -- flagging this reading here rather than silently assuming it,
in case that's wrong.

**No numeric latency target exists anywhere, and this story doesn't invent one.** The M2 gate in
`docs/sprint-plan.md` says "the latency table decides interactive vs batch... built only if the
table shows it is nearly free" -- qualitative only, no seconds or budget written down anywhere.
This table is what a human reads to make that call; it isn't a pass/fail check in code.

**A pre-existing design choice, not something this story changes:** every runner's final
`run.json` write uses `json.dump(..., sort_keys=True)`, so the *on-disk* key order is always
alphabetical regardless of when each stage actually ran -- only the in-memory `timings` dict
(and the printed table, built from it before the sort) preserves chronological order. Caught
this the hard way: an early test asserted chronological order on the on-disk JSON and happened
to pass by alphabetical coincidence on one runner's stage names but not the other's; fixed to
check the in-memory dict, which is what the table-printing code path actually uses.

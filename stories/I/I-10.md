## Why this exists

I-09 computes the per-feature pre-check; this story is what makes that check resolve to a real,
end-to-end verdict outcome rather than a dangling flag, wiring "Unverifiable" through to
`getVerdict` per the contract's frozen `Verdict` enum (`Pass`/`Fail`/`Rescan`/`Unverifiable` —
"Exactly these four values (proposal §7.2). No fifth value may be added without a decision
entry"). Today `getVerdict` can only answer 404 until a verdict exists; this story lets a
session's or order's verdict resolve to `Unverifiable` with `declared_at: intake` once I-09 has
already flagged it, independent of whether reconstruction ever runs. The proposal's own milestone
table frames this as a real system outcome, not a side note: "σ_floor above 3 mm → demo
tolerances move up and the Unverifiable path becomes the story." Sprint plan S5 lists it as its
own line item, distinct from the pre-check itself: "ingestion pre-check against measured
σ_floor, fed by the parsed spec; the Unverifiable path; automated test suite."

## Acceptance criteria

- When I-09 has flagged an order's feature(s) as below the σ_floor threshold, `getVerdict` (or
  the equivalent order-level check) returns a `VerdictResult` with `verdict: "Unverifiable"`,
  `declared_at: "intake"`, matching the frozen schema — not a 404, and not a verdict that waited
  on capture or reconstruction.
- `reason_codes` names which feature(s) were Unverifiable and why (tolerance vs. the measured
  σ_floor for the PO's required tier), for the report page to explain in plain language
  (`VerdictResult.reason_codes`'s stated purpose).
- The hard rule still holds here: an Unverifiable declaration is about method capability, never a
  disguised Pass or Fail — it carries no `regions` claiming `contributes_to_verdict: true`.
- Tests, written with the code: an order whose only critical feature is below σ_floor resolves to
  Unverifiable with no session or capture required.

## Notes and decisions

- **Open design question, not resolved here or anywhere else in the repo yet:** when *some* but
  not all of an order's critical features are below σ_floor, does the whole order become
  Unverifiable, or only the named feature(s), with the rest proceeding through capture to a
  normal Pass/Fail/Rescan? Proposal §7.3's "features below the floor are flagged" suggests
  per-feature flags survive into capture, but `VerdictResult`'s `verdict` is one enum value per
  session. Whoever claims this story must settle it and record it as a new decision — it should
  not be invented silently inside the acceptance criteria above.

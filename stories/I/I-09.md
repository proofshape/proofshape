## Why this exists

Proposal §7.3: "When the buyer enters tolerances, each critical feature's tolerance is compared
with σ_floor for the reference tier the PO requires. Features below the floor are flagged
Unverifiable by this method before any photo is taken, so the buyer routes them to a CMM
knowingly instead of discovering endless Rescans in the field." §7.4 ties this to the parsed-spec
shape: "That structure feeds the ingestion pre-check directly: each tolerance is compared against
σ_floor for the required reference tier, and anything below it is declared Unverifiable before a
single photo is taken." The buyer-facing side already reserves this exact slot: C-16 says plainly that "tolerances aren't
yet checked against the method's noise floor (I-09, not built). It shows no Unverifiable flag,"
and separately lists "the intake pre-check's results, which I-09 adds to this page later" as out
of scope for itself. G-04's own "Why this exists" names I-09 directly: "The verdict logic
can't set tolerances without it (I-07, I-09)."

## Acceptance criteria

- Given an order's parsed spec table (§7.4's shape — `name`, `kind: hole|face|edge|overall`,
  `tolerance_mm`, `critical`, the same shape C-16 collects and R-34 stores), compares each
  feature's `tolerance_mm` against `k · σ_floor` for the reference tier the PO requires (the
  table's Unverifiable row: "tolerance < k·σ_floor for the reference tier this PO requires").
- Uses G-04/D-073's measured board-reference height σ_floor for height-like `face`/`overall`
  features and R-37/D-078's measured board-reference in-plane σ_floor for `hole`/`edge` features.
  Sheet/card tier floors don't exist and never will: those reference tiers are cut (D-083), not
  invented or assumed equal to the board floors.
- Runs at order/spec-entry time (`declared_at: intake`, before any session or photo exists),
  matching the glossary's "declared Unverifiable at intake, before any photo is taken" and the
  contract's own description of `declared_at: intake`.
- Tests, written with the code: a feature whose tolerance sits below `k·σ_floor` is flagged; one
  above is not; an order with no parsed spec yet produces no flag (D-004: no CAD/spec, no verdict
  machinery, nothing to check yet).

## Notes and decisions

- **G-07's chosen `k` for this story's formula (2026-11-17, D-077): k ≈ 0.70** (measured 0.688,
  `consumable_k_estimate` — total error against `max(sigma, sigma_floor)`, the exact quantity
  this story's `tolerance < k·σ_floor` row uses). **Not 0.25** — that figure answers a different
  question (sigma vs. per-vertex scatter alone, offset removed) and is too small for this row:
  at 0.25, the Unverifiable threshold would fall to 0.215 mm, below every offset G-07 actually
  measured (up to 0.73 mm), undoing what σ_floor exists to cover.
- **Known residual gap, not resolved here:** even at `k ≈ 0.70`, `0.70 × 0.86 = 0.60 mm` is
  still below `s-04`'s own 0.73 mm offset (D-077). This story's Unverifiable check as currently
  specified would still under-flag a tolerance between 0.60 mm and 0.73 mm on a part shaped like
  `s-04`. Whoever claims this story needs to decide how to close that gap — a higher `k`, a
  higher `sigma_floor`, or a change to this row's own formula — not silently inherit the gap.
- The sheet and card reference tiers are cut (D-083); this scopes itself to the board tier,
  the only one that exists, rather than faking a number for the other two.
- Caught on review: `k·σ_floor` needs `k` itself (G-07) as well as σ_floor (G-04) — the original
  draft's Depends on named only G-04, inconsistent with I-07's own dependency on both.
- **A feature with `tolerance_mm: null` (A-03) is refused, never defaulted** (caught on review,
  @TabeenRaoof, #320). C-16 makes the buyer fill every null before submitting, but R-34 stores
  the spec as an opaque object (D-032), so an order created any other way can still carry one.
  This story must treat a null tolerance as a reason to refuse the order's spec outright, not as
  `k·σ_floor` compared against nothing or a silently assumed value — the same "no invented
  number" discipline A-03 itself applies.
- **Malformed tolerance values are refused too.** R-34 stores an opaque spec, so a value that
  bypasses A-03 can be a string, boolean, non-finite number, zero, or negative. Those are not valid
  positive millimetre tolerances; refuse them explicitly rather than crashing an order read or
  classifying an invalid value as Unverifiable/ok.

### 2026-11-17: implemented

New `inspect/inspection/intake_check.py`: `D073_SIGMA_FLOOR_BOARD_MM = 0.86`,
`D078_SIGMA_FLOOR_IN_PLANE_MM = 5.278`, and `D077_K = 0.70` (named constants citing their
decisions, not re-derived), `check_intake_spec(spec) ->
list[dict]` — per feature in `spec["features"]`, `"unverifiable"` (tolerance below
`k·σ_floor`), `"ok"` (at or above it), or `"refused"` (missing, null, malformed, or invalid
tolerance, never defaulted). A spec with no `features` key, or an empty one, returns `[]` (D-004: nothing to
check yet) — this also makes it safely backward-compatible with every pre-existing placeholder
spec shape in R-34's own tests (`{"tolerance_mm": 4.0}`, `{"critical_region": "hole"}`), which
have no `features` key at all.

Wired into `recon/service.py`: `OrderResponse` gains `intake_check: list[IntakeCheckResult]`,
computed **fresh from the stored spec on every read** inside `order_response()` (used by both
`createOrder` and `getOrder`) — never persisted into the stored order record itself, so a
future change to `k`/σ_floor is reflected on the next read of an *existing* order rather than
frozen at creation time. No change to `OrderStore`'s write path or stored schema.
`contracts/openapi.yaml`'s `Order` schema gains the same field, additively (not in `required`),
plus a new `IntakeCheckResult` schema object.

**Board tier only, by design, not by oversight.** Nothing in this codebase derives which
reference tier an order *requires* from its CAD size or anything else -- `reference_tier_used`
(`recon/service.py`) is an *output* of capture, decided well after intake. The sheet and card
reference tiers are cut (D-083), so the board is the only tier that will ever reach this
module. This selects between the board tier's measured height floor (D-073) and in-plane floor
(D-078) according to feature kind -- not a silent assumption that every order uses the board,
the only tier that exists.

**The residual gap this story's own notes flagged above is not fixed here, by design.** The
real measured `k ≈ 0.70` and `σ_floor = 0.86 mm` are used as-is (threshold 0.602 mm); no higher
number was substituted to make the `s-04` 0.73 mm offset disappear from the gap — doing that
would be exactly the "dressed-up tolerance" D-003 exists to prevent, and D-077 explicitly left
that tradeoff for a team decision this story doesn't make unilaterally.

No `declared_at` field was added to `IntakeCheckResult` (unlike `VerdictResult`, which this is
deliberately a separate, smaller shape from — most of `VerdictResult`'s fields, like `regions`
and `orientation_ambiguous`, don't apply before a photo exists): every `check_intake_spec`
result is inherently intake-time by construction, since nothing else calls it.

### 2026-11-17: review found a real kind-blindness bug (PR #372, @mbj1994)

The first version read no `feature["kind"]` at all and applied the height floor to every
feature — a `"hole"`/`"edge"` tolerance (an in-plane measurement) could be wrongly marked `ok`
against a floor measured for an out-of-plane dimension. Concrete example from the review: a
1.0 mm edge tolerance was `ok` (1.0 ≥ 0.70×0.86 = 0.602 mm) when it should not have been.

**R-37's measured in-plane floor applies to `"hole"`/`"edge"`.** R-37 (PR #364) merged with
D-078's board-reference in-plane `sigma_floor = 5.278 mm`; these kinds use `D077_K × 5.278 mm`
(3.6946 mm). A 1.0 mm tolerance is Unverifiable, while a 5.0 mm tolerance is ok. `"face"` and
`"overall"` continue to use D-073's out-of-plane height floor; the remaining kind-to-dimension
mapping is an explicit assumption below.

**`"face"`/`"overall"` keep the height floor, as a named assumption, not a verified mapping.**
A-03's `SpecFeature.kind` enum (`hole`/`face`/`edge`/`overall`) has no kind that unambiguously
means "the vertical dimension G-04 measured" — `face`/`overall` are the closest plausible
reading, stated as such in the module's own docstring, open to correction once a real
kind-to-tier convention is written down. An unrecognised or missing `kind` is refused, never
guessed.

### 2026-11-17: review found two more real bugs (PR #372, @TabeenRaoof)

**1. Malformed `features` shapes crashed `createOrder`, and corrupted every later read of that
order.** `check_intake_spec` assumed `spec["features"]` was always a list of objects. R-34
stores a spec as opaque, unvalidated JSON, so a buyer-supplied `{"features": null}`, a non-list
`features`, or a non-dict list entry reached `for feature in spec.get("features", [])` /
`feature.get(...)` directly and raised, which `recon/service.py` does not catch — a 500 on
`createOrder`. Because the order is saved *before* the response is built, the order was still
stored, so every later `getOrder` on it also 500'd (the check runs fresh on every read).
Separately, `{"name": 7, ...}` reached `IntakeCheckResult(feature_name=7, ...)`, which raises
because `feature_name` is typed `str`. Fixed: `check_intake_spec` is now total (never raises). A
missing or null `features` key still returns `[]`; a non-list `features` value, or a non-dict
list entry, becomes one `"refused"` result each; a `name` that isn't a non-empty string is
replaced with a placeholder rather than passed through.

**2. `"face"`/`"overall"` against the height floor recreated the first review's bug.** The
previous fix's own stated assumption — treat `face`/`overall` as the out-of-plane dimension —
turned out to be exactly the kind of guess D-003 warns against: a `face`/`overall` feature can
just as plausibly mean an in-plane dimension, and picking the smaller of the two measured floors
when the axis isn't stated under-flags the feature (a 1.0 mm `overall` tolerance was `ok` against
0.602 mm, when the in-plane threshold is 3.6946 mm). Fixed: `face`/`overall` are refused instead,
the same way an unrecognised `kind` already was — no floor is assumed when the spec doesn't say
which dimension is checked. This needs no new decision: refusing makes no claim, unlike keeping
either floor would have.

**The in-plane floor has its own version of the residual gap above, now recorded here too.**
D-078's 5.278 mm is the nearest-rank p95 of only 11 real edge comparisons; at that sample size
it is also the *maximum* measured edge error. So `k * 5.278 = 3.6946 mm` sits below the worst
edge error R-37 actually measured, the same shape of gap as `s-04`'s 0.73 mm height offset
against the 0.602 mm height threshold, and a larger one. Not fixed here, for the same reason: a
tuned-up `k` or `sigma_floor` would be the "dressed-up tolerance" D-003 exists to prevent.

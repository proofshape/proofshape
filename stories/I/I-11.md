## Why this exists

No CAD, no verdict (D-004). The proposal names STL, OBJ and GLB as the three accepted CAD
formats (§4, §9), but I-02 deliberately scoped itself to ASCII/binary STL and GLB, deferring OBJ
to this story so I-02 stayed one session: "OBJ is deferred to I-11 (titles-only), so this story
stays one session" (`stories/I/I-02.md`). This story closes that gap. It genuinely depends on
I-02, not on nothing — it extends the exact same `inspection.cad.load_mesh(path, *, scale=1.0)`
dispatcher I-02 builds, rather than starting a second, parallel loading path; there is nothing to
extend until I-02 merges.

## Acceptance criteria

- `inspection.cad.load_mesh` gains an `.obj` branch alongside its existing `.stl`/`.glb` ones,
  returning `(vertices_mm, faces, units)` in the same shape as every other format. Face lines
  with more than 3 vertices (a quad or larger polygon) are triangulated by a simple fan from the
  face's first vertex — adequate for the convex prism-shaped specimens this project's own CAD
  files are (G-01/G-02, `fixtures/reference_cad/`), not a general polygon triangulator.
- OBJ has no unit metadata, the same situation STL is already in: treated as millimetres by the
  same project convention I-02 already states for STL, not silently assumed to be metres.
- `vn` (vertex normal), `vt` (texture coordinate) and other non-geometry OBJ directives
  (`g`, `o`, `mtllib`, `usemtl`, comments) are parsed past, not acted on — this story loads
  geometry only, the same scope cut the proposal's own CAD-I/O line draws ("STL/OBJ/GLB only",
  no mention of materials or textures).
- The combined-formats rejection message (`_SUPPORTED_MESSAGE` in `inspect/inspection/cad.py`)
  is updated to name OBJ too, and I-02's existing tests that assert its exact wording are updated
  alongside it in the same commit, not left to drift.
- No new dependency: OBJ's relevant subset (`v` and `f` lines) is plain text, parsed with the
  same hand-rolled approach I-02 already chose over `trimesh` for STL and GLB.

## Tests

Unit tests in `tests/test_cad_loading.py` (extending I-02's file, not a new one), written
alongside the code (D-029): a triangle-only OBJ; a quad-face OBJ that needs fan triangulation; an
OBJ with interleaved `vn`/`vt`/comment lines, confirming they don't affect the returned geometry;
`f v/vt/vn` per-corner face syntax, confirming only the vertex index is used; and a malformed or
empty OBJ rejected with a message naming the supported formats. No manual check needed.

## Notes and decisions

- Negative (relative) OBJ face indices are a named non-goal: every OBJ this project actually
  reads comes from its own small set of specimen/reference CADs (G-01/G-02), none of which use
  relative indexing. If a buyer-supplied file needs it later, that is a new story, not a silent
  addition here.
- Written against `inspect/inspection/cad.py` as it stands in I-02's own pull request (#172) at
  the time of writing. If that code shifts materially before I-02 merges, whoever picks this up
  re-reads it rather than trusting this story's exact line references.

2026-10-26: Implementation. `_load_obj` reads `v`/`f` lines only; every other directive (`vn`,
`vt`, `g`, `o`, `mtllib`, `usemtl`, comments) is skipped by tag, not dispatched on. Each face's
per-corner token is split on `/` and only the first (vertex) field is used, so `f v`, `f v/vt`,
`f v/vt/vn`, and `f v//vn` all resolve the same way. Faces are fan-triangulated from their first
vertex, then run through the same `_deduplicate_triangle_soup` helper STL and GLB already use, so
all three formats return the same canonical shape. Non-positive (relative) face indices raise a
clear error rather than being silently misinterpreted, matching the non-goal noted above.
`_SUPPORTED_MESSAGE` now names OBJ; I-02's own test asserting its exact wording was updated in
this commit, not left to drift. No new dependency — OBJ parsing is plain text via `str.split`.

Mutation-tested both of the loader's non-obvious lines by hand: replacing the fan triangulation
with a sliding-window scheme fails exactly `test_load_obj_quad_face_is_fan_triangulated`, nothing
else; replacing the vertex-token split with the *last* `/`-separated field (so a `vn` or `vt`
index would be used instead) fails exactly `test_obj_face_uses_only_the_vertex_index`, nothing
else. Full suite 570 passed (was 545), ruff and `ruff format --check` clean,
`check_story_states.py` consistent.

2026-10-27: @TabeenRaoof's review of PR #210 caught a real bug: the tag/argument split used
`line.partition(" ")`, which only splits on a single literal space. A tab after the tag (some
exporters write one) merged into the keyword, so the line was skipped silently and every later
vertex index shifted — a quiet wrong answer, not a loud failure. Reproduced with their exact
repro, a 10×20 rectangle with a tab after `v`: the loaded triangle came out
(0,0)-(10,20)-(0,20) instead of the authored (0,0)-(10,0)-(10,20), with no error raised. Fixed
by splitting the whole line on any whitespace (`line.split()`) instead of a single space, so
tabs and runs of spaces are both handled. Added
`test_obj_vertex_and_face_lines_may_be_tab_separated`, mutation-tested by reverting to
`partition(" ")`, which fails exactly that one test, nothing else. Full suite now 571 (was 570).

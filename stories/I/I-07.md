## Why this exists

This is the decision the whole inspection lane exists for. Proposal §7.2 gives the exact table:

| Verdict | Condition |
|---|---|
| **Pass** | Every critical region Observed with σ ≤ tolerance / k, and no Observed deviation above tolerance |
| **Fail** | An Observed deviation exceeds tolerance by more than k·σ at that location |
| **Rescan** | A critical region is Unobserved or high-σ; registration is ambiguous; or the only deviation lies in an Unobserved region |
| **Unverifiable** | Declared at ingestion: tolerance < k·σ_floor for the reference tier this PO requires |

The hard rule governs every row: "Geometry that was not observed never fails a part and never
contributes to a Pass. It can only trigger a Rescan" (proposal §7.2; AGENTS.md). Issue #157 binds
this story specifically and explicitly: `compute_vertex_sigma` can return σ ≈ 0 from two
near-identical residuals at n=2 observations — "the 'zero spread means infinite precision'
trap... I-07 (verdict logic) must then use `max(σ, σ_floor)`, never raw σ, for every Observed
vertex... Done when: I-07's story file carries the `max(σ, σ_floor)` rule as an acceptance
criterion, citing this issue."

## Acceptance criteria

- Implements proposal §7.2's four-row table exactly for `declared_at: post_reconstruction`
  (Unverifiable's intake-time path is I-09/I-10's job), using I-06's per-vertex `_DEVIATION_MM`/
  `_DEVIATION_MEASURED` and R-10's per-vertex σ.
- For every Observed vertex, uses `max(σ, σ_floor)` — never raw σ — in both the Pass condition
  (σ ≤ tolerance / k) and the Fail condition (deviation > tolerance + k·max(σ, σ_floor)), citing
  issue #157 directly in the implementation.
- Produces a `VerdictResult` matching the frozen contract (`contracts/openapi.yaml`) exactly:
  `verdict` (`Pass`/`Fail`/`Rescan`/`Unverifiable`), `declared_at: post_reconstruction`,
  `orientation_ambiguous` (from I-05's `AmbiguityCheck.orientation_ambiguous`), `regions` (each
  with `name`, `provenance`, `deviation_mm` only when `observed`, and `contributes_to_verdict` —
  which must be `false` whenever `provenance: unobserved`, a structural rule
  `tests/test_contract.py` already enforces across every committed example), and `reason_codes`.
- `k` and σ_floor are consumed as inputs only (G-07's chosen `k`, G-04's measured σ_floor) — never
  invented or re-measured here; both stories reserve that measurement to the ground-truth lane.
- Tests, written with the code: synthetic (I-01) cases for each table row — a clean part → Pass;
  a planted deviation beyond tolerance → Fail; an Unobserved critical region, a deviation lying
  only in an Unobserved region, or an ambiguous orientation (I-05's s-05 case) → Rescan; a vertex
  with σ≈0 from n=2 agreeing observations is clamped to σ_floor rather than auto-passing (the
  #157 regression test, named explicitly).

### 2026-11-17: `max(sigma, sigma_floor)` restricted to out-of-plane only, per D-073

The first implementation floored *every* comparison with `D073_SIGMA_FLOOR_BOARD_MM`, regardless
of whether the worst-deviation vertex was a wall (in-plane) vertex or a top-face (out-of-plane)
one. D-073 says explicitly that the 0.86 mm figure covers out-of-plane (height) comparisons on
the board reference only, and that "most Observed vertices are wall vertices, i.e. in-plane" —
so the first pass was silently applying a floor the decision forbids using there on most real
sessions, caught before this story was called done rather than after.

Fixed in `inspect/inspection/verdict.py`: each Observed, measured vertex is now classified
out-of-plane or in-plane using `recon.cad_size_check.compute_height_above_board` and G-07/D-077's
own percentile convention (top 10% of this session's own height distribution), reused rather
than reinvented. The two pools are evaluated independently against their own worst-deviation
vertex: out-of-plane keeps the floored-sigma Fail/Pass/high-sigma logic unchanged; in-plane uses
raw sigma (no floor exists yet, pending R-37) — a real, well-measured in-plane defect still
Fails (D-073 withholds the floor, not the ability to catch an obvious defect), but a NaN raw
sigma (R-10's "can't even assess this" marker, with no floor to neutralise it the way
out-of-plane's does) Rescans as insufficient evidence (`f"{name}_in_plane_insufficient_evidence"`)
rather than risking a false Pass or Fail off the #157 trap with nothing to defend it — matching
R-16's own `insufficient_evidence` resolution to the identical ambiguity. `recon/service.py`'s
`get_verdict` now also reads the session's `fusion/tsdf_fusion.json` board plane (the same file
`run_post_reconstruction_measurement` already writes) to pass through.

Also fixed in the same pass: `tests/test_verdict_endpoint.py`'s "asymmetric box" fixture
(50x20x25mm) is still 4-fold orientation-ambiguous under real registration — a rectangular box
keeps 180-degree rotational symmetry about each axis even with three unequal dimensions, which
the original comment's "no two dimensions equal" reasoning missed. Confirmed directly against
real `registration.global_register`/`check_ambiguity` (not assumed), then swapped for the scalene
right-triangle prism (`g02_03_right_triangle_40x30x20mm.stl`), confirmed unambiguous the same
way — this is what let the end-to-end tests actually exercise a clean Pass at all.

### 2026-11-17 (second pass): per-vertex evaluation, D-078's in-plane floor, and three other
fixes from PR #379's review (@TabeenRaoof)

The review found the previous note's design still wrong in a way the synthetic tests didn't
catch, because they only ever planted one defect vertex per pool. Three fixes, each with its
own regression test in `tests/test_verdict.py`:

1. **Pool-worst-only evaluation missed vertices other than the single largest-deviation one.**
   Proposal §7.2's own wording binds *every* Observed vertex, not whichever one a pool's
   `argmax` happens to pick — the reviewer gave three concrete cases (two planted vertices each)
   where a different vertex's own margin should have driven a Fail or blocked a Pass, and the
   single-worst-vertex design missed it. Fixed: `_evaluate_pool` now checks every vertex in a
   pool -- Fail if *any* vertex's deviation exceeds `tolerance + k * sigma_eff` at that vertex;
   Pass only if *every* vertex's deviation is within tolerance *and* every vertex's sigma_eff is
   within `tolerance / k`; Rescan otherwise. This also exposed a second bug in the same old Pass
   branch: it checked the pool's sigma against `tolerance / k` but never checked the deviation
   itself against raw tolerance, so a deviation that cleared the sigma-scaled margin but still
   sat above tolerance could Pass outright -- proposal §7.2's Pass row requires "no Observed
   deviation above tolerance" independent of sigma.
2. **D-078/R-37 landed a real measured in-plane floor (5.278 mm) while this story was open,
   superseding the previous note's "no floor exists yet, pending R-37" framing.** In-plane
   sigma is now floored at `D078_SIGMA_FLOOR_IN_PLANE_MM` via `np.fmax`, the same way
   out-of-plane already floors at D-073's 0.86 mm -- which also resolves a NaN-handling bug the
   reviewer separately flagged (the old in-plane NaN check used the pool's group-wide `np.max`,
   not the comment's claimed "worst vertex," so one unrelated NaN wall vertex anywhere forced
   every feature to Rescan; flooring via `fmax` makes NaN behave identically to out-of-plane,
   so the separate `_in_plane_insufficient_evidence` reason code and Rescan path are gone --
   superseded, not merely redundant). **This is a real, large floor, not a smaller number than
   D-073's**: a wall-side defect now needs to clear `tolerance + 0.70 * 5.278` to Fail, and
   `tolerance` itself must be at least `0.70 * 5.278 = 3.69 mm` before the in-plane pool can ever
   Pass. Reported honestly, matching D-078's own "a large measured floor is recorded rather than
   tuned downward": this means most real sub-millimeter tolerances will Rescan on the in-plane
   pool specifically, not fail silently or get a free Pass.
3. **A verdict race: `getVerdict` could return a final-looking Rescan for a part that was never
   actually measured.** `run_session` marks `reconstruction.status: "complete"` and persists the
   record *before* calling `run_post_reconstruction_measurement` (so a crash in the latter can't
   leave the former unpersisted) -- a request landing in that window previously read the missing
   `ambiguity` key as `registration_failed` and returned a Rescan indistinguishable from a real
   one. Fixed in `recon/service.py`'s `get_verdict`: a missing `ambiguity` key now returns the
   existing `404 verdict_not_available` (reused, not a new code), and `registration_failed` means
   only "measurement ran and recorded an error," never "measurement hasn't run yet."

Two smaller fixes from the same review:

- **The 422 refusal fired for *any* feature's missing/null `tolerance_mm`, but the contract's
  own 422 description already said "a critical spec feature."** Fixed: only a feature with
  `critical` true (or missing -- refuse, don't assume, the same discipline a missing tolerance
  itself already gets) and a missing/null tolerance is refused; an explicit `critical: false`
  feature with no tolerance contributes nothing instead of aborting the whole verdict.
- **A malformed spec (`features` not a list, or an entry not an object) crashed instead of
  refusing.** `recon/order_store.py` stores a buyer-supplied spec as an opaque, unvalidated
  dict, matching I-09's own "refuse, don't crash" discipline for the identical input -- both
  shapes now raise `RefusedToleranceError` the same way a missing tolerance does, rather than an
  uncaught `AttributeError`/`TypeError` `getVerdict` would have had to let through as a 500.

Recorded, not fixed here (team decisions / other stories' scope):

- **Scope difference from I-09, by design:** I-09 refuses `face`/`overall` features at intake
  because nothing says which axis they check, judging only `hole`/`edge` against D-078. This
  module classifies by *vertex* height instead, consistent with its own "what a region is in
  v1" resolution -- every named feature, any kind, judged against the same global per-vertex
  measurement. A `face`/`overall` feature here is judged against whichever pool(s) its
  measurement's worst vertices fall into, not refused for axis ambiguity. Intentional for v1 (the
  two stories answer different questions, at different times), but worth a team decision before
  Tier 3 binds features to real CAD regions.
- **`TOP_REGION_PERCENTILE`'s top-10%-of-this-session's-own-height-distribution convention,
  reused from G-07/D-077, was tuned on G-04's calibration-cube-shaped specimens.** A part whose
  top face is a very different fraction of total surface area (very tall and thin, or very flat
  and wide) could be misclassified at the margin. Not measured or fixed here -- flagged for
  whoever next relies on this convention outside G-04's own specimen shapes.
- **Real golden-data check (@TabeenRaoof): running this story's own logic against `s-04`/`s-05`
  found both flagged `orientation_ambiguous` (one genuinely, one a known I-05 false-near-duplicate
  bug) -- and if ambiguity is ignored, both known-good parts Fail at every tested tolerance, from
  issue #292's board-skin ring sitting inside the 10 mm footprint margin (R-35 already measured a
  partial fix and left #292 open). Not this story's bug or this story's fix -- #292 is already
  tracked -- but worth re-checking before X-03 (the first integration point that depends on both
  I-07 and I-05/G-09's real parts), since this is the first time #292's effect on an actual
  verdict, not just a raw measurement, has been shown.
- **Contract version bump to 1.4.0, `tolerance_missing`/422, needs D-031's sign-off.** Bumped in
  this PR as the technical change; D-031 requires both other team members' approval, at a sprint
  boundary (or a recorded exception, per PR #335/PR #346's precedent) before merge -- not granted
  here, and PR #372 (I-09) touches the same file and will need to agree which of 1.4.0/1.5.0 it
  takes once both are on the same head.

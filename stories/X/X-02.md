### 2026-11-15: latency decision and the screen-photo check, re-run for real

**Criterion 1 — batch vs interactive.** Recorded as D-071 (`docs/decisions.md`): every backbone's
measured total (VGGT 80.21s, MASt3R 265.90s, COLMAP 80.63s/refused, all from R-13's real T4 run)

**Criterion 2 — screen photo rejected end to end.** Re-ran A-01's live check for real
(`scripts/check_vlm.py`, free tier, billing account "ProofShape (free tier)", pinned
`gemini-3.5-flash-lite`), against the golden `s-04` capture plus two new owner-supplied controls
(`fixtures/data/vlm_checks/screen_photo.jpg`, `wrong_part.jpg` — a real phone photo of a laptop
screen, and a photo of an unrelated toy, neither committed, matching A-01's own owner-local
convention). Full output: `fixtures/data/vlm_checks/x02-vlm-evidence.json`.

The screen-photo control's second frame came back exactly as the gate requires:
```
same_part: false, screen_photo: true
hint: "Please take a live photo of the part on the calibration sheet instead of photographing
a screen."
```
This is A-01's observation surfaced as A-11's hint field, on a real API call, not a replayed
fixture — the integration proof this criterion asks for. The wrong-part control also correctly
flagged `same_part: false` with a hint naming the mismatch ("a toy duck... does not match the
yellow wedge in reference frame 0").

**Honest caveat, not swept under the rug:** 5 of the golden capture's 7 sampled frames came back
`unchecked, reason: api_timeout` — only frames 25 and 29 actually completed, both correctly
`same_part: true`. Both controls' calls succeeded on the first attempt. The timeout rate on the
golden run is a real observation about this run, not a code defect — A-01's own design already
treats a timeout as `unchecked`, never a silent pass, so nothing here contradicts that story's
guarantees. Not investigated further; flagged for whoever next relies on a low golden-capture
timeout rate.

### 2026-11-15: real-phone session, the guidance loop end to end

**Device:** iPhone 18 Pro Max, iOS 27.2, Safari. **Setup:** `npm run dev:device` in `capture/`
(contract stub, no live reconstruction backend — D-040), opened on the phone over the same
Wi-Fi at `https://<LAN-IP>:5176/?order=PO-48213-A`, self-signed certificate accepted once.

**Steps:** granted camera and gyro permission, tapped Start, walked an orbit around an existing
G-02 specimen on its reference sheet, tapping Capture frame as the arrow overlay guided to each
slot, then Finish session.

**Arrow (C-07):** confirmed consistently pointing toward the direction actually needed to move
the phone, matching C-07's own real-device sign-check.

**Frame gate / orbit coverage (C-06, orbit coverage logic):** 17 total captures taken, only 7
advanced the covered-slot count. No `Frame rejected (...)` status text was observed on any of
the uncounted ones. A follow-up repro (reload, Start, one capture held deliberately still)
showed "Frame accepted, continue to next guided view" with no duplicate flagged — i.e. gate
rejection *did* render correctly when it actually fired, just not during the original walk.
**Conclusion, inferred rather than directly instrumented:** the covered-count tracks distinct
orbit slots (`orbit.ts`'s `nearestEligibleSlotIndex`), not total accepted uploads — a frame can
be genuinely accepted (no gate rejection, no error) and still not advance "covered" if it lands
on an already-covered slot. The likelier explanation for 17 captured / 7 covered is repeated
captures landing on already-covered slots, not 10 silent gate rejections. Not proven by direct
observation (the original walk wasn't screen-recorded), so this is the most parsimonious read
of the evidence, flagged as inferred for whoever next touches this path, not asserted as fact.

**Finish and report:** completed cleanly — the stub returned a demo GLB (downloaded), the
report page rendered with a reference-tier observation fraction and no warnings for this run.

**Guidance loop, in practice:** the arrow, the gate and orbit-coverage scoring all worked
together in one real session — guided to each slot, accepted or (when it actually happens)
rejected in real time, covered count advancing correctly, session finishing into a report.
Criterion 3 satisfied.

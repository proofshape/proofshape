## Why this exists

The whole capture pipeline depends on live camera access working in Safari on a real iPhone —
not a desktop browser's dev tools, not a simulator. iOS Safari has real gotchas here: `getUserMedia`
is refused outside HTTPS (localhost excepted), and only works when called directly inside a user
gesture, not deferred. Confirming this now, on real hardware, while the thread is still thin,
means C-04 onward gets built on a proven assumption instead of discovering a platform blocker
after the full app shell already exists around a wrong one.

## Acceptance criteria

- On a real iPhone, served over HTTPS (Safari refuses `getUserMedia` outside HTTPS/localhost, so
  this cannot be checked on a local plain-HTTP dev server), tapping a camera button on C-01's
  page triggers the permission prompt and, once granted, shows a live preview from the rear
  camera.
- Denying the permission is tested too, and shows a specific, visible message — not a blank
  screen or a silent failure (`AGENTS.md`'s no-silent-failures rule applies here as much as it
  does to backend code).
- The permission call happens directly inside the tap handler, not after an intervening `await`
  or callback that would make Safari treat it as no longer a user gesture.

## Tests

This is the canonical case `AGENTS.md` names for a written manual check instead of an automated
one: a device permission prompt cannot be economically automated. Record it as a manual check —
device model, iOS version, Safari version, the steps taken, and what happened for both the grant
and the deny case — not as "no tests," and not as a placeholder for tests to add later.

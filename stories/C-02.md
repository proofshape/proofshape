## Why this exists

The whole capture pipeline depends on live camera access working in Safari on a real iPhone —
not a desktop browser's dev tools, not a simulator. iOS Safari has real gotchas here: `getUserMedia`
is refused outside HTTPS (localhost excepted), and only works when called directly inside a user
gesture, not deferred. Confirming this now, on real hardware, while the thread is still thin,
means C-04 onward gets built on a proven assumption instead of discovering a platform blocker
after the full app shell already exists around a wrong one.

## Acceptance criteria

- On a real iPhone, served over HTTPS (Safari refuses `getUserMedia` outside HTTPS/localhost, so
  this cannot be checked on a local plain-HTTP dev server), tapping a camera button on C-01's
  page triggers the permission prompt and, once granted, shows a live preview from the rear
  camera.
- Denying the permission is tested too, and shows a specific, visible message — not a blank
  screen or a silent failure (`AGENTS.md`'s no-silent-failures rule applies here as much as it
  does to backend code).
- The permission call happens directly inside the tap handler, not after an intervening `await`
  or callback that would make Safari treat it as no longer a user gesture.

## Tests

This is the canonical case `AGENTS.md` names for a written manual check instead of an automated
one: a device permission prompt cannot be economically automated. Record it as a manual check —
device model, iOS version, Safari version, the steps taken, and what happened for both the grant
and the deny case — not as "no tests," and not as a placeholder for tests to add later.

Everything short of the actual device prompt *is* automated, in `capture/src/camera.test.ts`:
`describeCameraError` for each denial reason, the unsupported-context (no `navigator.mediaDevices`)
path, the grant path setting the video preview, and — the one that actually guards this story's
hardest criterion — a test proving `getUserMedia` is called synchronously inside the click
handler, with no intervening `await`, by checking the call already happened immediately after
`button.click()` returns.

## Notes and decisions

**Not closing this story yet.** Two of the three acceptance criteria are genuinely checkable only
on a real iPhone, over real HTTPS, by a human tapping the button — I have no device and no
network path to one. Everything else is built and tested: `capture/src/camera.ts`
(`mountCameraCheck`, `describeCameraError`, `isGetUserMediaSupported`), its full test suite, and
the HTTPS dev-serving setup needed to even attempt the manual check. `State` stays `Claimed`
until the manual check above is actually run and filled in.

**HTTPS dev serving, opt-in rather than default.** Vite dropped auto-generated certs after v3 —
there's no `--https` CLI flag anymore (checked `vite --help`), only a `server.https` config
option or a plugin. Added `@vitejs/plugin-basic-ssl` and a new `npm run dev:device` script
(`HTTPS=true vite --host`), read by `vite.config.ts` to conditionally add the plugin and bind to
the LAN — `npm run dev` (C-01's existing desktop workflow) stays plain HTTP, since it doesn't
need a self-signed-cert browser warning. Verified both modes actually serve: `dev` on
`localhost` only, `dev:device` on both `localhost` and the printed LAN IP, checked with `curl -k`
against each.

**The synchronous-call requirement is real, automatable, and was already proven to catch a
regression.** `getUserMedia` must be the first thing the click handler does — no `await` before
it — or Safari can treat the user gesture as expired. happy-dom has no `navigator.mediaDevices`
at all by default (checked directly), which turns out to help: a test can assign a fake
`getUserMedia` that just records when it was called, click the button, and assert the call
already happened *before* the test does anything async. Verified this actually catches the bug
it's meant to catch: temporarily made the handler `async` with a leading `await
Promise.resolve()` before the `getUserMedia` call, confirmed two tests failed for exactly that
reason, then reverted.

**Scope: this is the permission check, not C-05's live camera.** The preview video only proves
`getUserMedia` works; nothing here wires the stream into actual frame capture or the upload flow
C-01 built — that's C-05 ("live camera") and later stories. Mounted as its own section
(`#camera-app`, alongside C-01's existing `#app`) rather than merged into `page.ts`, to avoid
touching C-01's already-shipped, already-reviewed code for an unrelated concern.

**Error messages, not codes.** `describeCameraError` maps the four `getUserMedia` rejection names
that actually matter for this device (`NotAllowedError`, `NotFoundError`, `NotReadableError`,
`OverconstrainedError` — the last because the rear-camera `facingMode: "environment"` constraint
can fail on a device without one) to a specific sentence each, falling back to a generic-but-real
message for anything else — never a blank status line.
